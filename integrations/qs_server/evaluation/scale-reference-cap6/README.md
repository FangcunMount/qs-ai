# 量表综合洞察引用上限 6：最小发布候选

此候选允许每条综合洞察引用 **2～6 个不同维度**。没有更换模型、修改输出格式、修改校验器、增加自动模型调用，或覆盖任何 v6 资产。随同本批代码将生产每人每日解读默认额度从 10 调整为 20，机构每日 1024、单测评每日 3 及并发额度保持不变；已用额度不重置。当前为候选，尚未做真实生成评测、人工审核或生产发布。

## 发布材料

- [Profile v7](profile-v7.json)：从现有 v6 复制，只修改 Profile 版本、Prompt 版本及维度上限。
- [Prompt v7 草稿](prompt-v7-draft.json)：包含真实 v6 源引用、编辑内容和理由；通过现有草稿创建、修订、冻结流程产生正式指纹，不伪造冻结来源。
- [评测根套件](suite-root-v1.json)：独立身份，七个生成案例各五次、一个 preflight。三个案例覆盖 4、5、6 个同级维度；其余四个生成案例及 preflight 原样保留，包含层级、缺失信息和不可信指令边界。全局引用数量断言上限同步为 6。
- [候选清单](candidate-manifest.json)：核对 Profile 指纹、套件字节指纹及预算。Prompt 正式指纹来自实际冻结回执，因此清单不预填。

`evidence_refs` 的现有 Schema 上限是 **所有引用合计 6 条**，不是六条维度外再额外附加辅助引用。四或五条维度引用可加辅助引用，但六条维度引用不能再加总体结果。正文必须得到本条证据支持，重复、未知、父子组合及安全违规仍须拒绝。不要求每条洞察凑满六个维度。

## 上线顺序

1. 校验当前生产资产：源 Profile 必须仍为 `participant-scale-score-range-default@v6`，指纹与候选清单一致；Prompt 源版本、指纹及包摘要与草稿文件一致。核对 `v7` 尚未被其他内容占用，当前生成路线仍使用已验证的 `balanced_text_v1@v8`。任一事实不符则停止，重新从真实源准备新版本。发布后核对参与者有效 `daily_user=20`，包括环境覆盖、部署上限和显式组织策略；显式组织策略仍为 10 时不得声称全体用户已经生效，需要通过既有配额治理流程另外调整。
2. 部署本批 qs-ai 兼容代码。改动仅增加新根套件的固定身份及显式初始化入口，不更改线上生成规则，不涉及 qs-server 或管理后台发布，不涉及数据库迁移。生产部署暂停标记需按现有发布流程处理，不自行解除其他维护作业的控制。
3. 使用实际部署环境及既有凭据显式初始化根套件：`python -m qs_ai.bootstrap.import_scale_reference_suite --imported-by <操作人>`。该命令仅初始化根套件，幂等核对原字节与引用，不创建评测、不启用候选、不激活发布指针；既有评测政策及语义资产必须已初始化。
4. 在管理后台从草稿文件的 `source` 创建新 Prompt 草稿，目标为 `cross-dimension-participant-scale@v7`，再提交 `content` 修订并冻结。保留每个操作的 command ID、revision 和回执；超时先查原回执。
5. 注册 Profile：使用 `profile-v7.json` 的完整 Definition（服务端会规范化）；`source` 为候选清单中的源 Profile；`prompt` 用新冻结回执的完整资产引用；生成路线用现场核对的 v8 完整资产引用。注册回执中的 Profile 指纹必须与清单一致。
6. 从本批根套件派生注册一个新原生评测套件，绑定 Profile v7、新 Prompt 和原生成路线，保留根套件所有断言。不从 v6 根套件派生，否则会继承“最多 3”的旧全局断言。
7. 创建评测，核对 source、manifest、gate policy、execution policy、语义审核路线及预算。单次七案例×五次为 **35 次生成调用**；语义调用另计。继续满足既有正式评测、语义审核及人工审核门槛，人工关注四至六维度的正文证据一致性与可读性。单元测试通过不替代真实评测，不宣称保证所有未来输出成功。
8. 核对评测及最终审核回执后，将新发布配置显式切换为对应量表选择器的 active publication；记录原指针与新指针身份、版本和摘要。通过合法新请求验证合格 Artifact、QS 接收和页面展示。

上述生产部署、资产写入、真实评测调用与正式激活尚未执行；正式发布仍由用户确认。

## 两次旧失败请求

本次两次失败测评的已接单请求仍冻结原 Profile v6。它们的普通重试继续沿用原配置，不能因发布 v7 而假定已修复。本批不改写旧响应或旧请求，不直接更新 Session、不补写 Artifact。

发布后可先验证新请求。旧请求恢复单独决定：沿用现有合法重新发起解读入口时必须生成新 request ID、确认原参与者当前授权，并验证前端确实展示该新请求；若需要在原请求上恢复，则另行实施已暂缓的显式选新配置恢复方案。

## 回退与观察

回退时通过原发布治理流程恢复原 active publication，不修改任一已接单任务的配置。v7 已接单请求及历史成果继续保留。观察维度数量失败、证据/层级/安全失败、生成及交付通过率、延迟和调用次数；合格成果仍以实际业务接收及页面显示为准。
