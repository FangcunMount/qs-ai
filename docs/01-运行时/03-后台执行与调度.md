# 后台执行与调度

QS 接受一条报告生成请求后，模型不会在接单事务里立即执行；一个已 Start 的评测 Run 也不会一次性跑完整个 Suite。**后台循环反复尝试推进已持久化的工作，数据库决定本轮能取得什么所有权，模型调用证据决定恢复时还能做什么。** 增加轮询次数、重启进程或租约到期，都不会自行授予重新发送模型请求的权限。

本文按 `766b2aa` 的业务源码核对，沿生成 Job、评测候选和消息积压三个例子说明调度。配置数值来自仓库默认文件或代码固定值，未读取部署实例的环境变量、实时队列或供应商调用数据；不能据此判断线上启用了几个 consumer、是否使用候选并发模式。

## 四个 loop 的“完成一轮”含义不同

正式 [`serve`](../../src/qs_ai/bootstrap/server.py) 在同一事件循环和 APP 容器内装配以下后台组件。生成、评测的每轮 attempt 都新建 REQUEST 作用域；一个 consumer 要等当前 attempt 结束，才能执行下一轮。

| 组件 | 一轮执行什么 | 返回值如何影响下一轮 |
| --- | --- | --- |
| `generation` | `ExecuteNext.once(lease_seconds)`：领取一个 Job，执行、维持租约并提交结果 | 没拿到 Claim 返回 `False`；取得 Claim 且结果成功提交返回 `True`，包括提交业务失败结果 |
| `evaluation` | `EvaluationWorker.once()`：至多恢复一项、结束一个取消，或推进一个 Run 的 preflight/模型步骤 | 有推进返回 `True`；无可选工作或普通执行步骤发生 `CheckpointConflict` 返回 `False` |
| `mq_relay` | `MessagingRuntime.step()`：Publisher ready 后扫描已提交的消息 Outbox | 未 ready 返回 `0`；成功扫描后也返回 `0`，所以每个成功批次结束后仍有空闲等待 |
| `diagnostic_retention` | `prune(Transactions)`：删除一批过期 `operations_runtime_milestones` | 返回删除行数；大于零就立即再扫，零或捕获异常后才等待一小时 |

`True` 表示“这轮已经处理了工作”，不是“模型回答合格”。例如授权已撤销时，生成 worker 可以提交 `access_revoked` 并返回 `True`；评测恢复也可以提交 `result_unknown` 并返回 `True`。队列长度、业务成功数和 attempt 返回值不能互相替代。

MQ Subscriber 另有两个生命周期组件，分别接收命令和业务 ACK。它们由消息 SDK 接收网络消息，不通过这四个 loop 拉取生成或评测任务；`messaging.max_in_flight` 约束各 Subscriber，与 `worker.concurrency` 没有同一个计数器。

## consumer 如何继续、等待和停止

[`run_loop`](../../src/qs_ai/bootstrap/daemon.py) 创建 `concurrency` 个 asyncio consumer，每个 consumer 顺序调用同一个 attempt。它没有额外的内存 Job 队列，也不把一个 Job 拆给多个 consumer。`concurrency` 必须在 1–32；`idle_seconds` 必须大于零，`max_backoff_seconds` 不小于 idle，`shutdown_seconds` 可以为零。

一次正常返回会清零该 consumer 的连续失败次数：truthy 返回立即继续，`False/0` 则等 `idle_seconds`。普通异常只记录组件、异常类型和连续失败次数，不记录异常正文；等待时间为：

```text
min(max_backoff_seconds, idle_seconds × 2^连续失败次数)
```

失败次数从第一次异常的 1 开始，最多记到 16。使用仓库的 idle=1、max_backoff=30 时，连续异常后的等待依次是 **2、4、8、16、30、30… 秒**。这只是下一次 attempt 的时间，不是同一次模型调用的重发计划。

假设一个生成 consumer 面前有 J1、J2、J3：J1 提交完成后返回 `True`，紧接着尝试 J2；J2 提交阻断结果也返回 `True`，紧接着尝试 J3。队列清空后返回 `False`，才等一秒。如果领取 J2 时数据库连接失败，consumer 等两秒再重新进入领取流程；别的 consumer 有自己的失败计数和进度。

stop 可以打断 idle 和 backoff 等待。stop 设置后循环不进入新的 attempt，已经进入的工作可在 `shutdown_seconds` 内排空，并继续维持自己的租约；超时才取消剩余任务并等待清理。消费者在 stop 之前意外结束或被取消，会使整个后台组件失败，继而由服务监督器启动关闭流程。关闭顺序见 [生命周期与优雅关闭](04-生命周期与优雅关闭.md)。

## 默认值、可配置值和固定算法

[`Settings`](../../src/qs_ai/config.py) 的优先级为显式构造参数 → `QS_AI_` 环境变量 → 合并后的 `configs/default.yaml` 与 local/production 文件；不隐式读取 `.env`。环境变量用 `__` 分隔嵌套字段，例如 `QS_AI_WORKER__CONCURRENCY`。因此源码默认值、配置文件值和实例实际值是三个不同层次。

| 参数或行为 | 仓库默认/固定值 | 实际控制什么 |
| --- | --- | --- |
| `generation.enabled`、`evaluation.enabled` | default.yaml 均为 `false` | 正式服务是否创建对应 loop；开启还须满足依赖预检 |
| `worker.concurrency` / idle / max_backoff / shutdown | `1 / 1s / 30s / 130s` | 生成 consumer 数、空闲、技术异常和排空等待 |
| `worker.lease_seconds` | `30s`，配置须 ≥3s | 生成 Job 租约；heartbeat 间隔为 TTL/3，默认 10s |
| `evaluation.concurrency` / idle / max_backoff / shutdown | `1 / 1s / 30s / 130s`；production 文件仅将 shutdown 覆盖为 `190s` | 评测 consumer 和 loop 等待；不等于每个 Run 的并发槽数 |
| `evaluation.candidate_mode_enabled` | Python 默认 `false` | 新 Run 使用 `serial_v1` 还是 `candidate_v2`；已有 Run 读自己的持久执行模式 |
| `evaluation.parallel_calls` / `per_run_parallel_calls` | Python 默认 `1 / 1` | 进程内评测模型调用上限 / 每个 Run 的候选槽领取上限 |
| `model_capacity.deepseek/zhipu` | Python 默认各 `total=2`、`generation_reserved=1` | 进程内每家 Provider 的共享容量及评测可用部分 |
| MQ Relay concurrency / batch | server 强制 `1`；Relay 固定取最多 `20` 条 | 同进程一轮 Relay 只有一个扫描，批内顺序 publish |
| `delivery.idle_seconds` / max_backoff / shutdown | `1s / 30s / 15s` | MQ Relay loop 的等待和排空；`delivery.batch_size`、`max_retry_seconds` 未传入当前 Relay 算法 |
| 评测租约与续租 | step 固定租约 `5min`；候选 heartbeat 固定 `30s` | 与生成的 `worker.lease_seconds` 无关；serial 步骤没有该候选 heartbeat |
| 诊断清理 batch / idle / shutdown | 固定 `1000` 条 / `3600s` / `5s` | 清空过期诊断积压；诊断记录保留天数默认 `30`，由 diagnostics 配置 |

默认文件并不是一套可直接启动的线上配置：MQ 默认也关闭，而正式 `serve` 要求启用 MQ 及完整依赖。这里列值是为了理解算法，实例启用状态与配置取值须从实际部署核对。[default.yaml](../../configs/default.yaml)、[production.yaml](../../configs/production.yaml) 不能证明运行状态。

## 生成：数据库领取与模型发送是两个时点

[`MySQLExecutionStore.claim`](../../src/qs_ai/infrastructure/persistence/mysql/execution.py) 查询两类 Job：已经到 `available_at` 的 `queued`，以及 `lease_until` 已到期的 `leased`。按 `available_at, id` 取最多 20 个候选，按 **Session → Job → execution_leases** 顺序加锁；Session/Job 使用 `SKIP LOCKED`，允许其他 consumer 跳过正在领取的记录。

查到候选还不代表能执行：Session 必须仍以该 Run 为 active Run，状态须为 queued/running，原租约须过期，并通过业务活跃容量检查。取得所有权的事务同时做三件事：Job `attempt+1`、Session `running()` 导致版本增加、租约 `fence+1`，然后写入 Job 的 fence/expiry 和 Run 状态，提交后才返回 Claim。这三个数分别表示领取次数、Session 版本和所有权代次，没有相同数值的要求。

后续读取冻结证据、提交模型调用标记、记录响应和完成结果，都校验同一个 Claim：Session 状态/active Run/版本、Job leased 状态/fence，以及执行租约 fence/有效期。提交前还会检查租约是否仍有效。heartbeat 续期更新 `execution_leases.expires_at` 和 Job `lease_until`，不增加 fence，也不领取新的 attempt。

例如 worker A 领取 J1，取得 fence=7；A 暂停到租约失效，worker B 重新领取同一 Job，取得 fence=8 和新的 Session 版本。A 即使后来收到模型响应，也不能以 fence=7 更新结果。fence 的作用是挡住旧写入；它不表示供应商已经停止执行 A 的请求。

[`ExecuteNext`](../../src/qs_ai/application/execution/worker.py) 在 Claim 取得后并行运行工作与 heartbeat。续租失败会让当前本地工作被取消，异常交给 loop 退避；取消本地 coroutine 并不能证明外部模型请求未执行。冻结事实来自存储，执行前、接受结果前分别回查授权；证据缺失不会重新读取最新报告来填补快照。

### 租约恢复后，到底能否调用模型

[`DurableGeneration`](../../src/qs_ai/application/execution/generation.py) 在发送前先提交 `execution_model_calls` 的 `dispatched` 记录；响应随后单独持久化，Artifact 和 Session/Run 结果再在完成事务中提交。重领 Job 后先读这条调用记录，行为如下：

| J1 被中断时的持久证据 | 后续 Claim 可以做什么 | 模型调用 |
| --- | --- | --- |
| 尚无 `execution_model_calls`，例如 A 正在等待本地 Provider 容量 | 校验 Claim 和原冻结请求，取得容量后提交发送标记并执行 | 可以进行该 Run 的首次发送 |
| `response_received` 且响应正文已保存 | 校验 invocation/model 与冻结请求，复用响应完成结果 | 不重新调用，不等待模型容量 |
| 已有 `dispatched`，响应没有成功持久化 | 提交 `provider_result_unknown` 对应的阻断结果 | 不重新发送 |
| 已有 `unknown` 或 `failed` | 复用 unknown/原失败事实，按原 Run 完成处理 | 不因失败被标记为 retryable 就重新发送 |

模型容量等待发生在调用标记之前，没有持有数据库事务，但 Job 已 leased，heartbeat 仍须持续。若已经存在 durable call，则恢复不会再占用一个 Provider token；它是在处理已发生的调用证据。

同一 Job 已领取三次后，再次进入到期扫描会被标记 `dead`，Session/Run 阻断为 `attempts_exhausted`，避免无限崩溃循环。这个分支提交了状态但不返回 Claim，所以本轮 `once` 返回 `False`。业务容量不足则把 Job `available_at` 延后一秒后尝试其他候选，不增加其领取次数；已活跃的容量预留跨租约恢复保留，在完成本次结果提交或阻断耗尽的 Job 时释放。底层规则见 [`participant_capacity.py`](../../src/qs_ai/infrastructure/persistence/mysql/participant_capacity.py)。

这里的重领处理属于原 Run 的恢复。用户授权 Retry 后新建 Run、保留原始事实/配置及新调用预算，是另一条业务路径，见 [执行恢复](../03-基础设施/execution-recovery/README.md)。

## 评测：一轮可以只恢复，也可以只做 preflight

[`EvaluationWorker.once`](../../src/qs_ai/infrastructure/persistence/mysql/evaluation_worker.py) 依次做以下判断，前一步返回有进展就结束本轮：

1. 扫描并恢复一个过期 serial checkpoint。
2. 扫描并恢复一个过期候选 SlotClaim。
3. 结束一个可排空的取消请求。
4. 选择一个可推进的 collecting Run；没有 preflight 记录则只提交 preflight，否则执行一个生成或语义评测步骤。

普通选择要求没有 `cancel_requested`、没有活跃的 Run 级 checkpoint；候选模式还检查已领取 SlotClaim 数小于 `per_run_parallel_calls`。选择按 checkpoint version、run_id 排序，最多一条，不是按创建时间保证 FIFO。SQL 读取只是提示，数据库 checkpoint CAS 或候选 Claim 的事务校验才确定归属；读取 Session 在模型 I/O 前关闭，organization 从持久 Run 取得。

因此 Requested Run 不会被后台自动 Start；awaiting_review、blocked、canceled 也不会被普通执行查询选中。collecting 的 Run R1 首轮可能只做 preflight、返回 `True`，下一轮才开始第一个模型步骤。在 serial 模式下，两个 consumer 同时读到 R1，其中一个取得所有权，另一个遇到 `CheckpointConflict` 返回 `False`，等待 idle 后再读；candidate 模式下，两者也可能分别取得不同候选槽。无论哪种模式，都不会在冲突的当前 attempt 内直接重试同一次模型调用。

### serial 与 candidate 的恢复证据不同

执行模式保存在 Run 上。切换 `candidate_mode_enabled` 会影响新建 Run，worker 按已有 Run 的 `execution_mode` 选择路径，不批量改写旧 Run。

| 机制 | `serial_v1` | `candidate_v2` |
| --- | --- | --- |
| 执行所有权 | Run 级 checkpoint，一次一个步骤 | 按 `(run_id, case_id, slot_ordinal)` 领取候选；不同候选可重叠，单候选内仍有生成与语义步骤次序 |
| 租约 | prepare/dispatch 设置五分钟有效期 | 五分钟有效期；执行期间每三十秒续到当时的五分钟后 |
| 响应提交 | 完成事务内接受响应与进度，没有候选模式的独立 response receipt | 先独立提交 response receipt，再提交 Candidate/completion/Run 进度 |
| 过期 prepared 且没有 dispatch ledger | 释放 preparation、增加 checkpoint version；后续轮询重新安排未发送工作 | 释放 SlotClaim、增加 Run checkpoint version；后续轮询可重新领取 |
| 过期 dispatching | 记录一次 `result_unknown` completion、恢复审计并阻断，不能从“没有结果”推断没发出 | 有 receipt 则重建原步骤、完成投影；没有 receipt 则记录 `result_unknown`，均不发送模型请求 |

候选回执恢复仍校验原 Claim、执行/调用身份和观察到的 expiry；它不是把同一正文换个 invocation 再交给模型。serial 恢复也要求精确 expectedVersion、invocation、观察到的 expiry、组织和 collecting 状态。若原 owner 刚续租或另一消费者已完成，恢复校验会冲突，不能覆盖新状态。具体入口是 [`evaluation_recovery.py`](../../src/qs_ai/infrastructure/persistence/mysql/evaluation_recovery.py) 和 [`evaluation_candidate_recovery.py`](../../src/qs_ai/infrastructure/persistence/mysql/evaluation_candidate_recovery.py)。

举例：R1 候选 C1 的响应已保存，但进程在完成 Candidate 前退出；C2 的模型请求已发出，回执还没保存。租约到期后，恢复轮把 C1 的 receipt 投影成 completion，不新增供应商调用；另一个恢复轮把 C2 标为 unknown，不重新发送。unknown 会限制继续调度，取消意图也不会抹掉这笔未解决的调用事实。

`cancel_requested` 先阻止新步骤。只有无 Run checkpoint、无 SlotClaim、未解决 unknown 数为零时，取消排空才能结束 Run；已在执行的调用仍需要完成或按证据恢复。不能把“收到取消请求”直接解释为“所有模型请求均已取消”。

### 恢复扫描有边界，没有全量遍历承诺

[`RecoveryCursor`](../../src/qs_ai/infrastructure/persistence/mysql/evaluation_scan.py) 是 APP 内共享游标。serial 每次按 run_id 扫最多 64 条；候选按 `(run_id, case_id, slot_ordinal)` 扫最多 64 条。遇到未过期记录就继续，每轮至多成功恢复一项；到末尾回绕。游标在解码/恢复前推进，因此坏记录或恢复冲突不会永久挡住后面的 Run，但坏记录仍可能令该轮抛异常、进入 loop 退避。

例如前 64 项租约均未到期，本轮恢复可以返回 `False`，然后继续普通工作选择；下轮从游标后的记录继续，而不是每次从第一项重扫。进程重启丢失游标后重新扫描也安全，因为游标只是扫描优化，所有权和恢复依据都要重新从数据库校验。它没有持久调度优先级或跨进程公平性的保证。

## 并发：consumer、候选槽、Provider 容量不能互换

一个 APP [`ModelCapacity`](../../src/qs_ai/application/execution/model_capacity.py) 同时服务报告生成与评测。它按 Provider 计算总活跃调用数，评测还受全进程 `parallel_calls` 和该 Provider 的 `total-generation_reserved` 上限约束；计数检查和修改在同一事件循环内同步完成。

使用代码默认值 DeepSeek total=2、generation_reserved=1、全进程 evaluation parallel_calls=1：

- 一个评测调用已使用 DeepSeek 时，另一个 DeepSeek 评测不能开始，剩余一个 Provider 名额可供报告生成。
- 两个报告生成已使用 DeepSeek 时，新生成等待 token 释放；评测尝试取得 token 失败，会回滚本次准备/领取，不提交 dispatch，也不发出模型请求。
- 只有报告生成时，它可以使用两个名额。`generation_reserved=1` 约束评测最多使用一个，并不把一个 token 永久闲置。

这三个例子描述容量算法；默认 consumer 只有一个，不能据此声称默认实例实际同时发生了两次生成。要让候选真正并行，还须有足够的 `evaluation.concurrency`、`per_run_parallel_calls`、global evaluation 和 Provider 容量，以及 Run 内可执行的候选。增加 `per_run_parallel_calls` 但保留一个 consumer，不会自动生成更多执行协程。

生成取得不到 Provider token 会等待，保留 Job 租约并继续 heartbeat；评测取得不到 token 则本轮让步，不把一个等待者长期留在已提交的候选 Claim 上。两条路径均在提交模型 dispatch 前取得容量。候选模式的 token 在响应/完成路径退出时释放，异常和本地取消也走释放逻辑。

数据库还控制两类业务容量：Participant 的组织/用户/Assessment 日预算与活跃预留，Evaluation 的启动预算与活跃 Run。它们限制业务准入和运行规模；`ModelCapacity` 限制本进程此刻的供应商调用。数据库共享预留、SlotClaim 和 CAS 可以协调多个实例的业务状态，**Provider token 计数却会随实例数累加**，并非分布式限流。

扩成两个实例时，每个实例都有自己的 total=2，不能继续把这个配置解释为集群只会出现两个 DeepSeek 调用。并发配置还会增加 Claim、heartbeat、恢复与完成事务的频率；所有组件共用 APP Database，仓库默认池为 5、overflow 为 5。模型 I/O 期间不占事务，有助于释放数据库资源，但不能消除多实例的数据库竞争。容量装配见 [`RuntimeProvider`](../../src/qs_ai/bootstrap/providers/core.py)、[`EvaluationProvider`](../../src/qs_ai/bootstrap/providers/evaluation.py)。

## MQ Relay：重发消息，不重做生成或评测

[`MessagingRuntime`](../../src/qs_ai/bootstrap/messaging.py) 先启动所有配置的 Publisher，ready 后才启动两个 Subscriber；Relay 在 Publisher 未 ready 时返回 `0`。ready 后它调用 [`MQRelay.step`](../../src/qs_ai/infrastructure/workflow_transport/mq_relay.py)，随后仍返回 `0`。用仓库 idle=1s 时，即使积压未清空，每批结束也等一秒；并非有消息就连续高速清空。

Relay 每轮从已提交 Outbox 取最多 20 条，关闭读取事务后顺序 publish，再用独立事务写投递状态。server 强制一个 consumer，Relay 内 asyncio gate 拒绝同进程重入；gate 不跨实例，不能证明两个进程不会同时发布同一条消息。

例如积压 45 条满足 pending 条件的消息、Publisher 正常：第一轮最多取 20 条，完成批内 publish/状态提交后等一秒，再开始第二轮。耗时还包含 20 次 publish，不能用“每秒 20 条”计算吞吐。Broker confirmed 使消息进入等待业务 receipt 的状态；被明确 rejected 则 hold；结果不确定则按 `min(60, 2^min(attempts+1,6))` 秒延期。已尝试八次的记录进入 `delivery_budget_exhausted` hold。

消息延期与 loop 退避也不同：Broker 返回 unknown 可以正常写 retry，随后 loop 按 idle 等待；数据库或 publish 抛出普通异常，才触发 consumer 的 2/4/8… 秒退避。Subscriber 的最多八次消费尝试属于接收链，另有计数，不能与 Relay 的发布次数混算。

Relay 使用原消息 identity、正文 hash 与 wire 重发已有消息，既不领取 Job，也不创建模型 invocation。新状态事件在原业务事务里写入；历史结果的投递归属迁移需明确 handoff，不由普通扫描自动接管。消息确认与业务接受的边界见 [可靠消息](../03-基础设施/messaging/README.md)。

## 诊断保留：一小时是清空后的等待

[`prune`](../../src/qs_ai/infrastructure/persistence/mysql/runtime_milestones.py) 仅删除 `expires_at < UTC_TIMESTAMP(6)` 的 `operations_runtime_milestones`，按 expiry 排序、一次最多 1000 条并提交。记录默认保留 30 天；调用、Artifact、审批、Publication 和消息 Outbox 不在这条删除路径里。

若启动时有 2300 条过期诊断，loop 依次删除 1000、1000、300，三个正数返回都立即进入下一轮；再得到 0 才等待 3600 秒。发生异常时，server 的包装函数捕获异常并返回 0，同样等待一小时，而不是抛给通用 loop 触发业务组件失败。它既不进行模型重试，也不是严格整点运行的定时任务。

daemon、model_capacity、worker_frozen_evidence 三个测试文件可以独立验证循环、本地容量和冻结事实规则。MySQL/NSQ 集成测试需要一次性环境，真实模型质量与部署行为则另行验收；不能把纯测试通过外推到其它范围。

现场排查积压时，先确定等待发生在哪个阶段：未到 `available_at`、Claim 被他人持有、业务容量不足、进程 Provider token 已满、unknown 阻止继续、消息等待业务 receipt，或者仅处于 idle/backoff。随后核对实例启用状态、有效配置、持久 Claim/调用证据与运行指标。重启和提高 concurrency 只改变调度机会，不解决上述业务阻断条件。

维护入口 [`bootstrap/worker.py`](../../src/qs_ai/bootstrap/worker.py) 默认执行 readiness probe；`--once` 至多运行一个持久 Job attempt。它不是第二套常驻生产 worker，也不绕过 Claim、租约、容量或模型证据规则。
