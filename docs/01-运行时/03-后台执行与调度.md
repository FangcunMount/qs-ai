# 后台执行与调度

## 本文回答

生成、评测、MQ Relay 和诊断保留如何被调度；什么可以重新轮询，什么不能重新发送。

## 结论

`run_loop` 只负责有界并发、空闲等待、技术失败退避和停止领取。持久化状态机负责任务领取、租约、版本、模型调用与业务结果。重新运行一次 attempt 不等于重新调用一次模型。

| 组件 | 一次 attempt | 业务推进边界 |
|---|---|---|
| generation | `ExecuteNext.once(lease_seconds)` | 领取一个 Job、维持租约、执行并提交结果 |
| evaluation | `EvaluationWorker.once()` | 先恢复，再排空取消，再执行一个可推进步骤 |
| mq_relay | `MessagingRuntime.step()` | 只扫描既有消息 Outbox；不接管历史结果 |
| diagnostic_retention | `prune(Transactions)` | 过期诊断记录；不驱动业务或模型重试 |

## 通用 loop

[`run_loop`](../../src/qs_ai/bootstrap/daemon.py) 验证 `concurrency` 在 1–32，空闲等待为正且最大退避不小于空闲时间。每个 consumer 顺序调用 attempt；返回 false/0 则等待 `idle_seconds`，成功处理工作则继续。异常只记录错误类型和失败次数，采用有界指数退避。stop 等待可打断空闲与退避。

任何 consumer 未经 stop 提前退出，包括被意外取消，都使整个后台组件失败，进而触发服务监督器排空。stop 已设置后不再领取新 attempt，但已经进入的 attempt 可以在关闭期限内完成。

## 生成调度

`ExecuteNext.once` 从存储领取 Claim。数据库对 Session、Job 和 Lease 校验，fence token 每次重新取得所有权时递增。生成工作的 heartbeat 以 TTL/3 续租；工作和 heartbeat 竞争完成，续租失败会停止当前工作。冻结证据只从持久化存储读取，授权在执行前和接受结果前分别复核。

模型调用前先提交 dispatched marker，响应另行提交；恢复复用 durable response，dispatched/unknown 不重发。最终 Artifact 和状态提交仍要求 Claim 的版本、租约及 fence 有效。完整失败窗口见 [执行恢复](../03-基础设施/execution-recovery/README.md)。

## 评测调度

`EvaluationWorker.once` 的优先级是：恢复旧 checkpoint → 恢复候选槽 → 排空取消 → 选择 collecting Run → 执行 preflight 或模型步骤。选择查询只是提示，checkpoint CAS 与槽 Claim 才决定真正所有权。组织来自 Run，不来自扫描者输入。

`serial_v1` 和 `candidate_v2` 是持久 Run 的执行模式。候选模式允许同一 Run 有多个候选槽，但并发仍受 per-run、global evaluation 与 provider 计数限制。活跃 checkpoint 由恢复流程处理，不能被普通 polling 当作新步骤重复执行。CAS 冲突返回本轮无进展，下一轮重新读取，不在当前 attempt 直接重试模型。

## 消息与诊断调度

MQ Relay 在统一服务中只有一个 loop，且并发固定为 1；内部 gate 也拒绝同时扫描。Publisher 未 ready 时返回空操作。Relay 使用已提交 Outbox，而不是从业务状态推测消息。解读历史结果的归属变更只能经过明确的受控 handoff，不能由普通 Relay 自动扫描接管。

诊断保留每小时尝试一次；失败返回无进展，避免诊断故障重启业务 loop。过期诊断不会删除模型回执、任务、Artifact 或消息证据。具体保留实现见 [可观测性](../03-基础设施/observability/README.md)。

## 选择、代价与限制

有界轮询可以依靠数据库获得恢复依据，且便于在单一关闭过程中停止领取；代价是空闲延迟和扫描成本。事件驱动唤醒可以减少延迟，但不能取代数据库领取和恢复判断。异常退避缓解依赖不可用，不证明任意失败具备安全重试条件。

多副本可竞争数据库任务，但本地模型容量会按副本累加。扩容需要同时审查 provider 额度、数据库池、候选槽和重复消息行为，不能仅增加 `concurrency`。
