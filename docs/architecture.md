# 架构基线（初始化阶段）

> 本文保留初始化时的边界记录。2026-09-11 完整设计见 [项目设计](design.md)，实施顺序见 [路线图](roadmap.md)。以下边界仍适用，完整设计进一步明确了分层、Dishka 装配和执行一致性。

## 职责

qs-server 继续掌握 Testee 档案、测评、标准报告、主体归属和业务事实授权。qs-ai 引用用户、组织和 Testee 标识，负责未来的解读会话、补充问答、证据快照及成果。AI 服务不复制用户系统，不直接读取 qs-server 数据库。

业务会话、原始证据与成果必须能脱离 LangGraph 检查点独立读取。AI 推断不能自动成为 Testee 事实；用户自述保留回答者、适用时间和来源，不能只按账号混合记忆。

## 目标运行结构

一个仓库构建 API 和 Worker 两种进程。API 持久化请求并返回，Worker 执行 LangGraph。等待回答时持久化问题和检查点并释放资源。任务表、租约、幂等、并发控制和恢复机制待业务契约确定后实现；当前没有伪装成可靠队列的后台任务。

同一会话的状态推进需串行约束；恢复时验证主体权限和会话版本。框架检查点不保证外部模型调用或成果写入恰好一次。结果未知不能直接无条件重试。

## 数据库

使用独立 MySQL 数据库及账号。可以复用现有云实例，但上线前确认版本、容量、连接预算与备份恢复。业务字段使用关系表，必要的结构化快照用 JSON。业务迁移与检查点迁移分开发布。SQLAlchemy 连接池仅供业务访问，检查点连接由适配层管理。

## 模型

目标支持 DeepSeek、GLM、OpenAI。先共用业务契约与基础 Prompt，再按具体模型/接口评测必要适配。初始化阶段不接入 Provider，不要求 API Key，也不会读取或调用现有模型凭据。

## 后续批次

1. 定义 qs-server 事实快照协议、主体授权链及业务会话模型；实现单报告真实生成和持久化执行。
2. 实现同类多报告关联、主动提问、回答后恢复；验证重复提交、重启、旧流程版本恢复和证据引用。
3. 按评测结果扩展跨类型解读、可管理的长期记忆、多模型选择。

上线证据分开记录：代码测试、真实 MySQL、真实模型、跨服务授权、客户端体验、部署运行。任何一层通过都不替代后续层。
