# qs-ai 替代现有 AI 解读：M1–M5 执行与验收计划

状态：2026-09-11，用户同意以目标模式持续推进；本文件是本轮任务与验收的权威计划。M0 已发布，M1–M5 尚未验收。旧路线图 P0–P5 保留技术设计参考，其编号不对应本计划。责任边界见 [迁移决定](migration-boundary.md)。

## 目标与范围

主目标：qs-ai 完整承接 qs-server 当前支持的 AI 测评解读，包含输入组织、Prompt 与发布、模型调用、执行恢复、成果及评测管理；qs-server 保留业务入口、权限、标准测评事实、可靠发起和结果接收展示。替代完成后退役旧生成引擎和专属配置，不长期维护两套权威实现。

“AI 测评”指标准测评后的 AI 解读，不迁移 Testee、评分、标准报告或用户权限体系。首个案例复用 QS 已调配好的 Prompt、模型与参数、输入规则和输出约定，不同时更换模型来混淆对照结果。

本轮不包含主动追问、多报告、跨类型综合和长期记忆的新增产品建设；保留已实现的相关骨架和兼容契约。现有业务中实际已使用的功能必须纳入迁移清单，不因上述排除而丢失。

- [AI 草稿 PR #6](https://github.com/FangcunMount/qs-ai/pull/6) 与 [QS 草稿 PR #82](https://github.com/FangcunMount/qs-server/pull/82)：本轮规划时核实仍开放、未合并。M1 复核差异后继续，不重复实现、不直接视为生产完成。
- 现有 MySQL 持久任务、租约/心跳、状态 Outbox 与 gRPC 投递是基础。worker 单次执行、deliver 单批投递不等于常驻进程；当前状态事件不等于完整成果回传。

## 依赖与完成口径

M1 → M2 → M3 → M4 → M5。M3 清单分析可提前开展，生产切换须遵守前置验收。QS 旧代码按模块在替代验证后逐步清理，M5 作最后关闭检查。

任务状态使用：待做、进行中、待验收、完成、受阻。只有提交代码不算完成。每项验收记录提交/PR、测试或故障场景、环境、运行链接、结果及剩余限制；涉及上线时还要记录 deployed SHA 和实际业务证据。模拟模型、替身权限、本地数据库测试不能代替生产业务验收。

## M1：真实报告与现有案例接入

交付：一条可复用的授权事实链、一个有版本记录的现有案例包，以及完整迁移清单。

任务：

- M1.1 追踪 QS 业务入口→配置发布→事实/输入→Prompt→模型→校验→成果→展示，记录实际文件、调用者、数据表、配置、后台入口、事件和共享依赖；每项标注迁入、保留、兼容或删除，以及对应验收和替代任务。
- M1.2 盘点当前实际支持的测评类型、使用中的 Prompt/release、模型参数和输出契约；选择一个已有稳定结果的案例。固定合法测试报告、原结果、版本和来源，避免在仓库保存可识别个人信息或凭据。
- M1.3 复核并收尾两端草稿 PR，与最新 main 对齐。提供不可变报告版本、主体、维度事实和来源；qs-ai 不直连 QS 数据库，不接受调用方任意伪造的主体。
- M1.4 从 QS 业务入口授权发起，定义执行前、后续事实读取和展示时的权限复核与撤权行为；异步任务不持有用户短期令牌。授权依赖故障不得放行。
- M1.5 将案例的完整 Prompt、变量规则、缺失值处理、供应商/模型参数、输出 Schema 和解析约束作为 qs-ai 固定发布版本；记录来源版本与内容摘要。核对现有凭据能否通过部署配置安全复用，不在聊天读取密钥。

验收门槛：

- 全部已发现的现有 AI 能力都有归属和后续任务，无未分类共享依赖；形成可供 M4/M5 勾选的完整清单。
- 合法案例可经 QS 入口到达 AI，读取准确的报告版本；同一 request_id 重放不重复建任务，相同键不同内容明确冲突。
- 覆盖合法主体、跨组织/跨 Testee、撤权、报告不存在/版本变化、权限服务故障；拒绝场景不得触发模型调用。
- 对照案例的输入字段、语义、缺失值和输出约定一致；来源及版本可追溯。若必须改变映射，记录理由并增加差异验证。
- 两端契约、数据库集成及 CI 通过，所需事实接口发布后完成真实服务身份联调；明确尚未调用模型的证据边界。

## M2：首条真实解读闭环

前置：M1 验收通过。交付：一种测评的生产闭环及可持续运行的执行、投递进程。

任务：

- M2.1 以 M1 固定版本接入真实模型；持久记录执行所用事实、Prompt、模型和参数版本、调用回执及失败分类。完善正式成果、结构/事实引用校验；不合格输出不能标记成功发布。
- M2.2 实现常驻任务消费、空闲等待/错误退避、有限并发、租约续期、取消、优雅退出和健康信号。隔离旧 worker 写入；外部调用结果未知时不盲目宣称失败并重复收费调用。
- M2.3 完整成果与 Outbox 同事务接受；定义成果传输或按引用读取方式，校验大小、版本和身份。实现常驻投递、重试、接收确认、去重和对账；投递失败只重投成果，不重新生成。
- M2.4 QS 完成可靠发起及接收投影，绑定请求、主体、证据与成果版本；旧事件不覆盖新状态，保持现有查询/展示契约或提供明确适配。
- M2.5 部署消费与投递服务，设置通信地址、只读证书、资源和数据库连接预算；配置必要的队列积压、过期租约、投递失败与进程健康可观测性。
- M2.6 从原 QS 产品入口完成真实模型生成和结果展示，对照原案例；必要时覆盖实际客户端，不能用后端测试替代界面验收。

验收门槛：

- 至少一例真实生产请求由 QS 发起，AI 执行并保存完整成果，QS 接收并展示；关联 request_id/session_id/artifact、双方版本、调用回执与脱敏结果证据可查。
- 重复请求、重复/乱序回传、worker 被终止并恢复、投递前后断线、领取过期及旧 worker 迟到、取消与完成竞态均有可重复验证；不丢已接受任务、不重复接受成果、不倒退状态。
- 模型超时/限流/格式错误、数据库或 QS 暂时不可用均呈现可解释状态和有界重试；人工可识别并处理未知结果。
- 事实数值、等级、主体、版本和引用不得错误，必需输出字段齐全；不产生无来源事实或越权内容。与原案例比较不要求文字逐字一致。
- 精确 SHA 的 CI、生产进程健康、数据库迁移和业务验收分别记录。完成一次安全的发布回退演练，证明新会话不会送给旧引擎。

## M3：AI 管理与发布能力接管

前置：M2 首条闭环通过。交付：qs-ai 成为 AI 配置、执行与质量管理的唯一写入权威。

任务：

- M3.1 按 M1 清单迁入 Prompt/Profile/release、模型路线与参数及实际在用的评测和质量发布规则；不要逐行翻译 Go 类。统一配置归属和版本引用。
- M3.2 实现草稿、校验、发布与回退流程及审计记录；运行中的任务绑定不可变版本，发布新版本不改变在途执行。
- M3.3 迁入执行记录查询、调用用量/时延、失败定位和受控重试；重试区分生成、投递与未知结果，保留前后关联和操作记录。
- M3.4 现有管理入口通过 QS 代理或专用适配访问 AI。操作者授权继续复用现有体系；qs-ai 校验可信调用和必要的操作上下文，不自建用户系统。
- M3.5 执行配置迁移与条目对账，保留旧来源 ID/版本映射；切断对应 QS 旧管理写路径。删除已无调用者的旧模块。

验收门槛：

- 通过实际管理入口完成“修改草稿→校验/评测→发布→生成→切回上一版本”；不通过质量门槛的版本不能发布。
- 每次生成准确追溯到不可变配置；并发发布和重放不产生双重生效；历史运行仍可读取原版本。
- 管理读写与越权拒绝均验收；配置迁移条目、引用和版本对账无差异或有逐项解释。
- 已迁移配置不存在双写权威；完整失败链可定位，受控重试有审计。QS 页面功能保持可用。

## M4：全部现有测评逐批切换

前置：M3 管理闭环通过。交付：M1 清单中的全部现有 AI 能力在 qs-ai 可用，生产新流量全部切换。

任务：

- M4.1 按测评类型/Prompt 路线拆迁移批次；覆盖不同维度结构、边界等级、缺失事实及长报告。每批固定样本与旧结果基线。
- M4.2 自动检查数值、等级、引用、Schema、安全边界；对表达、规则遵循和结论依据做可追溯质量评审。每类默认至少正常、边界、缺失三种可适用样例；特殊类型补充分支覆盖。
- M4.3 按类型或允许名单逐步放量，每个请求只能选一个引擎。开始每批前固定流量范围、回退触发和观察窗口，禁止用生产用户请求双生成作对照。
- M4.4 根据现网基线确定超时、完成率、P95 时延、队列年龄、投递延迟、连接数和成本预算的数值门槛；记录查询口径和窗口。无基线先采集，阈值未确定不得全量放行。
- M4.5 完成容量与故障恢复验证、告警触发验证、备份恢复演练，按批次验证客户端展示和历史访问。共享生产环境不进行破坏性故障注入，使用隔离任务/测试环境。

验收门槛：

- M1 功能/类型清单覆盖率 100%；全部必需结构、事实准确性及访问隔离检查通过；质量评审无未解决的阻断问题。主观质量不能仅以模型自评分替代。
- 每批达成预先记录的运行与质量阈值；最后一批至少观察连续 24 小时并包含实际合法请求。无流量不能视为稳定性通过，可用授权的合成任务补充证据。
- 所有生产新请求只进入 qs-ai；旧在途任务可查可排空，历史成果不受影响；停止新流量可回退且不会把新会话交给旧引擎。
- 重大事实错误、越权、任务丢失或终态覆盖立即停止该批新流量；修复与回归后重新观察。

## M5：qs-server 旧 AI 实现退役

前置：M4 全量切换验收通过；交付：唯一生成/管理引擎和可维护的 QS 业务边界。

任务：

- M5.1 核实旧入口零新流量、旧执行任务全部排空，未决结果和失败任务逐条处置；对账已接受请求、终态成果和 QS 投影，差异归零或有明确业务处置。
- M5.2 按 M1 清单删除旧 AI Provider、输入/Prompt/生成/校验、调度/恢复/评测管理及专属 RPC/事件消费者、装配代码、依赖、配置和测试。保留 QS 的事实、权限、可靠投递、接收幂等与历史读取适配。
- M5.3 停用专属旧进程与事件订阅，确认无共享调用后移除旧凭据和部署注入；共享 IAM、证书、MQ、数据库资源不得误删。
- M5.4 历史成果和审计记录使用原来源/版本读取或显式映射；验证备份可恢复。本轮不自动 DROP 历史表、删除业务数据或撤销共享凭据。需不可逆清理时先形成对象清单、恢复证据和具体操作，再取得明确授权。
- M5.5 发布清理版 QS，完成核心测评/标准报告、历史 AI 查询及新解读回归；更新配置说明、值班/故障处理和恢复手册，移除失效开关。

验收门槛：

- 清单每个旧职责均有替代证据或明确保留理由；搜索、依赖构建、调用链检查证明 QS 不再装配或调用生成与 Prompt 发布旧实现。
- 生产旧 AI 进程、订阅和专属密钥注入停用；新请求全部由 AI 执行，历史与标准测评查询正常。
- QS 清理版 CI、生产 SHA/健康、新解读与历史查询验证通过；至少连续 24 小时无旧生成调用，并有新链路实际请求证据。
- 保留表/历史适配清单及后续数据保留决定明确。保留必要历史数据不阻碍代码退役；破坏性数据删除不是本轮目标完成前提。
- M1–M5 证据齐全且无未关闭的阻断项，才能将整体目标标记完成。

## 目标模式执行规则

1. 每轮读取本计划与当前验收记录，核对 Git/PR/生产实际状态，从首个未满足门槛推进；用户新消息默认调整当前计划，不丢弃总体目标。
2. 每次选择可独立交付的小批任务，保护未提交工作。qs-server 同时有其他任务推进，必须使用本迁移任务专属的 codex/ 分支与独立 worktree；不得切换其他任务的工作目录、混入未提交改动或提交无关内容。开始前核对分支、worktree 占用及工作区状态；已有草稿先复核归属后复用，不覆盖其他任务。qs-ai 同样使用任务分支。协调两端协议发布顺序，保持过渡兼容。
3. 完成适用的测试和代码审查后，持续推进 PR、CI、授权范围内的部署与验收。纯文档变更不主动发布生产；测试通过不代替部署或业务证据。
4. 每批更新任务状态和证据：任务 ID、提交/PR、测试、生产版本、验收场景、实际结果、下一步。等待真实观察窗口或外部输入时如实记录，不以估计通过验收。
5. 凭据通过现有安全部署渠道配置。遇到缺少账号权限、必要产品判断或不可逆操作，仅提出具体缺口；继续不依赖该缺口的工作，不重复请求已有授权。
6. 整体目标只有 M5 门槛满足才完成。临时失败、工期长或一个里程碑完成不能关闭目标；阻塞状态按目标工具的重复阻塞规则处理。
