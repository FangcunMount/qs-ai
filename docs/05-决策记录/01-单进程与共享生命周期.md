# 单进程与共享生命周期

## 结论与证据状态

当前已采用一个 asyncio loop、一套容器与数据库池、一个组件监督器。本文是基于当前约束的设计分析，不声称还原首次实施时的历史动机。基线为 `c977cb9`，完整现行规则见 [运行时设计](../01-运行时/README.md)。

## 问题与约束

HTTP、gRPC、生成、评测和消息都依赖数据库，执行还共享提供方并发预算。接单、业务提交、消息收发和关闭之间有明确顺序：未通过预检不能接单；Subscriber 要等 Publisher ready；业务排空期间 Publisher 仍需工作；借用应用池的消息资源不能先关闭池。

如果各职责自行启动容器、安装信号或创建投递 loop，池数量和扫描所有权会分散，健康状态也可能只覆盖其中一部分。

## 候选与选择

| 候选 | 优点 | 必须承担的代价 |
|---|---|---|
| 当前统一进程 | 资源所有权清楚，本地模型预算直接共享，关闭顺序可核查 | 共享故障域，局部组件失败导致服务重启 |
| 每职责独立进程 | 故障/资源可独立隔离与扩容 | 额外池、分布式provider容量、跨进程就绪/排空与唯一投递责任 |
| 单进程但组件自行重启 | 部分错误可局部恢复 | 资源与旧task残留风险，需要监督状态与重装配协议 |

统一进程把 APP 资源共享与 REQUEST 操作隔离结合起来。监督器把任何已装配组件提前退出视为失败，生成/评测开关决定是否装配该组件；不开启某类执行也不能回退到旧投递口。

## 风险、失败边界与限制

启动只是资源与必要前提校验，ready 不是模型或业务验收。进程退出后恢复依赖数据库的 lease/fence、dispatch 与 receipt，不能用内存 Task 状态判断模型是否执行。

本地 `ModelCapacity` 不协调多个副本；进程扩容会放大提供方并发。单进程也仍有日志writer线程和阻塞文件读取线程执行器，不能把“单事件循环”理解为全部 I/O 均无线程。

## 重新决策条件

当真实负载、故障影响或运维需求证明统一故障域不可接受时，可以分拆执行/消息角色。新方案需要明确池预算、provider全局限流、重复扫描容忍或唯一所有权、各角色preflight/readiness、关闭依赖和混合版本恢复，不仅更改启动命令。
