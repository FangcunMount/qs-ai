# 单进程与共享生命周期

当前 `bootstrap.server` 将 HTTP、mTLS gRPC、生成、评测和消息组件放在一个 asyncio loop、一套 Dishka 容器和一个APP数据库池内，由一个监督器管理启动、失败和关闭。组件不各自注册信号或启动第二套投递调度器。这个选择让资源与排空责任可追踪，也接受了一个重要代价：任何已装配的关键组件异常退出，都使整个服务退出。

这是按 `766b2aa` 未变业务源码记录的现行选择，核对日为2026-10-06。下面理由根据当前实现边界归纳，不追认某次历史会议或框架选型过程。具体装配见 [单进程架构](../01-运行时/01-单进程架构与启动装配.md)，对象寿命见 [资源所有权](../01-运行时/02-Dishka作用域与资源所有权.md)。

## 要解决的是三个具体的所有权问题

假设生成worker刚接受成果，同事务写出结果事件，此时服务收到SIGTERM。消息资源要继续把已提交事件交给Broker，接收侧可能还要结算在途命令/ACK；如果一个独立worker先关闭共享池，其他组件就无法完成原事务。如果Publisher先退出，会阻断仍在排空的传输和技术失败移交；已提交的首回执仍保留在Outbox，等待后续投递。

另一个约束是本地ModelCapacity：生成和评测要共享每provider的总token与生成预留，不能各建一个“相同配置”的计数器，然后都认为有空余容量。数据库事务却相反：大家共享连接池，但每轮操作要新Session，不能把同一长事务共享给所有task。

因此需要明确池、授权channel、模型token、Publisher/Subscriber、信号和组件task由谁创建和最终关闭；“都在同一个服务里”不足以自动形成这些保证。

## 现行选择怎样落实

| 边界 | 实际措施 | 仍不保证什么 |
| --- | --- | --- |
| 资源装配 | RuntimeProvider的APP池/授权channel/ModelCapacity；REQUEST对象借用，Transactions.open每轮新Session | 同池不等于同事务；token不是集群全局限流 |
| 启动 | 先TLS与数据库exact-head/依赖检查；Publisher ready后Subscriber，再形成整体ready | ready不探测真实模型质量，也不自动迁移/安装业务资产 |
| 执行 | 生成/evaluation消费者按有效concurrency创建；MQRelay嵌入现有supervisor | 多consumer不改变Run原执行模式或持久预算 |
| 故障 | Component提前正常结束也视为关键组件失效，整体触发stop；没有组件热重装协议 | daemon一次可恢复错误的退避与Component退出不是同一层 |
| 关闭 | 同时通知组件停止，再按依赖排空；Subscriber停止接入，Publisher保留至业务组件排空，最后资源/日志关闭 | 不承诺所有积压已投递或QS已经Stored |
| 进程重启 | 原Job/Lease/fence、dispatch/receipt与claims决定接手行为 | task已取消不证明供应商未执行，内存消失不重置原预算 |

[server](../../src/qs_ai/bootstrap/server.py) 只建立一个loop/容器，统一持有SIGTERM/SIGINT；Uvicorn的capture_signals不另接管信号。[lifecycle.supervise](../../src/qs_ai/bootstrap/lifecycle.py) 管理Component和RuntimeState，关闭预算与超时取消并不等价于强制撤销外部调用，详见 [生命周期](../01-运行时/04-生命周期与优雅关闭.md)。日志writer与文件读取executor仍用线程，“单loop”不表示所有工作都无线程。

数据库池默认5连接+5overflow是单实例连接预算，MySQL Session仍按操作隔离。MQ SDK借用池和宿主根事务，不dispose池、不抢先提交；消息自己的HTTP/NSQ资源由宿主明确start/stop。资源规则不靠“运行在一个进程”推断，代码中仍须逐个所有者落实。

## 为什么当前不拆进程或热重启组件

| 可选方案 | 它能改善的问题 | 必须新增的责任 |
| --- | --- | --- |
| 当前统一进程 | 本地token自然共享；就绪/信号/排空与APP资源由单一所有者协调 | 共享故障域；角色不能分别滚动升级和扩容 |
| API、生成、评测、Relay独立进程 | 某类故障与CPU/连接资源可隔离，各角色独立扩容 | 每角色池预算/就绪；跨进程provider容量；Relay扫描所有权；混合版本和关闭协议 |
| 单进程内自动重启故障Component | 可缩短局部故障停顿 | 必须证明旧task/claim和channel都已结束、旧资源不残留；重新建立ready与依赖顺序 |

当前代码没有独立角色的完整装配/热重装协议，旧worker/evaluation/integration入口是维护探针或已退役入口，不能作为拆分方案的替代。拆一个常驻Relay出来但沿用当前无分布式claim的扫描，可能重复PUB；Inbox幂等保护业务效果，不等于已经解决扫描排他或重复传输成本。

共享故障域的理由不是“单进程一定更快”。当前收益是把已有所有权规则具体落在一个可监督运行单元内；是否满足流量和故障预算，需要现场压力、连接和排空证据。

## 哪些证据会触发重新决策

当真实观察表明某角色持续挤占资源、单个组件故障的影响超出可接受范围，或者必须独立升级/扩容时，应重新决策。新方案先给出角色→池/事务/信号所有者表，并验证如下实际故障窗口：

1. 生成已dispatched、旧实例失权，新实例不二次发送，原响应可恢复。
2. candidate两实例乱序完成、旧claim失效、取消意图和unknown仍保留。
3. Relay在PUB后失去结算，重新扫描保留首wire，QS原Inbox/Stored语义不变。
4. 滚动期间旧实例停止接入，新实例只在自己heads/密钥/依赖匹配后ready，共享表与旧冻结资产可读。

外部供应商容量需要跨实例协调或明确账号总额预算。仅复制ModelCapacity对象、增加进程数或部署副本，不是这个方案的实现与验证。

## 决策的验证依据

[test_single_server](../../tests/test_single_server.py) 检查统一装配、loop/监听与故障传播；[test_runtime_lifecycle](../../tests/test_runtime_lifecycle.py) 检查整体就绪、关键组件失败及排空；[shared_runtime_pool集成](../../tests/integration/test_shared_runtime_pool.py) 检查共池、独立操作事务与借用资源不关闭宿主池。进程内容量和旧owner隔离另见 [并发设计](../03-基础设施/concurrency/README.md)。

这些测试能保护现行边界，不能证明生产峰值吞吐、供应商账户总并发、积压最终排空或用户结果已经验收。将来拆分时要更新本记录的约束、替代方案和故障证据，不能只修改部署命令并保留原决策说明。
