# 原事务消息与业务确认

## 结论与证据状态

当前使用原业务事务中的Inbox/Outbox与嵌入式NSQ Relay，保留QS原业务接收确认。宿主拥有应用池、根事务和生命周期，SDK与消息适配器借用资源。本记录是基于当前约束的设计分析，不把更换Broker或中央Relay当作已经采用的方案。

## 问题与约束

业务提交后再单独PUB会产生“业务成功、消息未产生”的窗口；先PUB再提交会产生“消费者看到不存在的业务”。重复命令不能重复冻结或产生第二次效果；Broker确认不能代替QS原接收流程；旧结果历史身份与投递预算也不能因迁移被重置。

## 候选与选择

| 候选 | 原子性与恢复 | 代价 |
|---|---|---|
| 当前原事务Outbox/Inbox | 业务、消息意图、首受理回执同库事务；原身份可重投 | 存储、Relay、ACK、held诊断与受控恢复复杂度 |
| 业务提交后直接PUB | 流程简单 | 本地提交与消息发送之间有缺口 |
| 中央Outbox数据库 | 可集中投递运维 | 跨库写入重新产生双写，不继承原事务原子性 |
| Broker事务消息 | 可以另建业务状态查询模型 | 需要独立协议与状态检查设计，不是普通适配器替换 |

当前接单 receiver 开根事务，业务适配器借用，最终统一提交业务、Inbox与首回执；状态事件在原业务提交前进入Outbox。Relay提交后传输原wire，Broker结果只推进技术阶段。QS STORED再完成消息confirm和原结果delivered，避免把技术成功升级成业务成功。

## 不变量、失败与代价

重复命令先读原Inbox决定，不重新执行业务CAS；同身份不同正文隔离。PUB Unknown可以重投同身份和首wire，消费者依靠去重处理；模型Unknown不能因此获得第二次发送许可，这两种重试责任独立。

历史handoff只能锁定精确原记录并改变归属，普通Relay不自动接管。handoff与ACK均保持原结果→MQ记录的锁顺序；不复活delivered记录，不重置attempt预算。

Outbox原子性保护的是本地数据库与消息意图。网络传输可能重复、ACK可能丢失、技术预算可能held；必须保留消息证据并受控处置，不能声称全链路exactly-once。JOSE保护与大载荷mTLS读取还增加密钥和端点运维要求。

## 重新决策条件

更换Broker时，应保持Confirmation/Outcome、首wire、逻辑预算和业务ACK含义。独立Relay可以借用业务数据库读取其Outbox，但不能把权威Outbox迁走后默认仍原子；需要明确扫描所有权、连接管理、关闭与重投证据。Broker事务方案需要另列事务状态检查、未知状态、历史兼容和故障验收。
