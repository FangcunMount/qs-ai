# 评测候选、门槛与审核设计

一次评测要回答：在同一组冻结资产、同一份案例和有限调用预算下，35 个候选是否完成，内容是否达标，两类审核人是否愿意为结论负责。生成成功只产生候选，语义裁判成功只产生质量证据；完整审核和门槛复算之后的 `approved` 才是发布可使用的评测结论。

本文以 MBTI 三主题方案的一次 Run 为例，解释从 `requested` 到审核终态的证据链。核对基线：`d9c3155`，2026-10-06；数值来自当前冻结策略契约，示例审核人和故障为说明机制而设，不代表某个真实 Run 已通过。

## Run 创建时固定 35 个槽位及两类预算

方案 Prepare 创建 Run 时只形成 `requested`，不启动模型。资产注册和这一创建动作的原子性见 [方案、资产与原子准备设计](../governance/01-方案资产与原子准备设计.md)。独立的 `EvaluationManagement.Prepare` 只返回计划预览，也不创建 Run。

`create_run()` 写入 `qs-ai-evaluation-run-creation/v1` 创建文档，并保存如下条件：

| 冻结内容 | 保存和后续使用方式 |
| --- | --- |
| 十一项 `EvidenceReleaseIdentity` | Suite、生成 Prompt、Profile、输入/输出 Schema、生成 Route、语义 Prompt、语义输出 Schema、语义 Route、执行策略、门槛策略，每项都有 `id/version/fingerprint`；整体另有 `release_fingerprint` |
| 可复算材料 | `suite_json`、两份策略 JSON、语义 Prompt 原文和输出 Schema；原生 Suite 还须匹配注册的 GenerationManifest，保存其 JSON 和指纹 |
| 槽位和预检 | `slots=[{case_id, ordinal, status:"pending"}, ...]`，另存一个 `preflight`；顺序和数量由冻结 Suite 决定 |
| 接受规则 | 新 Run 的 `acceptance_rule` 固定 `candidate-completion/v1` 的原文及指纹；不能靠当前代码版本猜测旧 Run 的规则 |
| 执行模式和审计 | `execution_mode` 列固定 `serial_v1` 或 `candidate_v2`；组织、请求者、原因、创建时间与初始转移进入创建文档，检查点版本从 1 开始 |

例如，三主题根的 Suite 是 `participant-mbti-single / three-topic-v1`，语义 Prompt 是 `mbti-single-semantic-evaluator / three-topic-v1`。它们同名或同版本也不能代替指纹核验；组织内派生方案使用自己的 Prepare 回执引用。两类根的完整身份见 [模板来源契约](../governance/02-MBTI模板与方案来源契约.md)。

这份 MBTI Suite 的 `MBTI-EVAL-001` 至 `MBTI-EVAL-007` 各有 5 个槽位，共 35 个；`MBTI-EVAL-008` 验证不适用输入应在模型调用前被拒绝。预检的 `provider_call_count=0`，按冻结 Suite 内 `profile_fixture.eligibility` 的维度资格规则计算拒绝原因，再核对预期断言；它不占第 36 个候选，也不占一次模型调用。

当前执行策略 `release-evaluation-bounded-recovery / v2` 的上限为：

| 项目 | 初次全部成功时 | 允许的上限 |
| --- | --- | --- |
| 生成 | 35 次 | 每槽位 2 次，整个 Run 70 次 |
| 语义裁判 | 35 次 | 每候选 2 次，整个 Run 70 次 |
| 人工审核 | 70 条签名 | 每候选恰好两角色各一条，不是额外调用预算 |

因此正常路径是 70 次模型调用，上限是两个阶段合计 140 次。已经外发的失败和 unknown 仍留在 dispatch 账本并占预算；进程重启、租约回收和换 worker 都不能清零这些账。启动还要经过组织容量准入和当前模型准入；新并发配置不能把保留的 `serial_v1` Run 改成另一执行模式。

## 用一个槽位区分调用、候选和裁判

取 `(case_id=MBTI-EVAL-003, slot_ordinal=2)`。其中 `slot_ordinal=2` 表示该案例的第二个固定样本；`execution_ordinal=1` 表示这个槽位的第一次生成尝试，两者不是同一个计数。

| 记录 | 这个槽位中保存什么 | 它允许下一步做什么 |
| --- | --- | --- |
| 一次生成执行 | `execution_id`、`invocation_id`、槽位、尝试序号、起止时间；终态 `GenerationCompletion` 保留 `succeeded/failed/result_unknown`、调用数、供应商 receipt、原输出、规范输出及 SHA-256、分类失败 | 成功才可接受 Candidate；失败由原分类和剩余预算决定恢复 |
| 被接受的 Candidate | 第一次符合生成输出契约的成功执行产生一个 `candidate_json`：候选 ID、`generation_execution_id`、规范输出指纹、接受时间、实际案例断言，初始 `review_ready=false` | 用这份规范输出做语义裁判；质量低不能换一份生成结果 |
| 一次语义执行 | 固定同一候选 ID 和输出指纹，用原语义资产得到 `SemanticCompletion`；成功回执保留五项分数和逐项 decisions，并记录 `accepted_semantic_execution_id`、语义断言，使候选 `review_ready=true` | 为原候选补齐可审核证据；裁判成功不表示分数及断言通过 |

生成输出是否满足 Schema、引用等契约，决定有没有候选；案例断言或语义分数是否通过，决定这个候选的质量。一个满足输出契约但声称“这种类型一定胜任某职业”的结果，仍须作为原候选留下，随后由硬断言、评分和人工审核阻断。不能再生成几个，从中挑出分数最高的一个替代它。

生成输出契约失败允许在原槽位内使用剩余尝试，原失败仍保存。语义执行失败则保留已经接受的候选，只考虑对该候选再做语义执行。冻结策略明确禁止 `quality_failure_replacement_allowed` 和 `semantic_failure_regenerates_candidate`。

自动恢复还受失败分类和白名单约束。当前允许生成 `provider_rate_limited`，语义 `semantic_provider_rate_limited`、`semantic_provider_no_message`、`semantic_output_schema_invalid`；输出契约失败走独立的生成替代规则。未知结果以及不在允许范围内的语义契约失败需要后文的人工决定，不能用一个通用“重试”按钮混在一起。

## 外部调用前后分别提交哪些证据

每次评测尝试的工作流只有 `prepare_dispatch → invoke_model → commit_receipt` 三个节点。准备事务读取原资产、取得持久所有权、保留模型容量、写入 dispatch 预算账，然后提交；供应商调用在事务外进行。完成事务核对执行身份和当前所有权，原子保存终态回执、候选或语义投影、Run 进度与版本。

两种模式对“响应已收到，候选投影尚未提交”的处理不同，不能把新路径的保障套到旧 Run 上：

| 故障窗口 | `serial_v1` | `candidate_v2` |
| --- | --- | --- |
| `prepared` 租约到期，账本证明尚未 dispatch | 精确核对版本、invocation 和观察到的到期时间后清除检查点，保留回收审计；不生成 unknown、不消耗外发次数 | 精确核对 slot claim 后释放该槽位，推进协调版本；同样不补造调用 |
| 已收到响应，终态投影前失败 | 没有独立的响应保存阶段；若原检查点仍为 dispatching，过期恢复形成 unknown | 先用独立短事务写 `evaluation_response_receipts`；若此原收据已保存，可按同一 claim、execution、invocation 和原完成时间恢复投影，不再调模型 |
| 已 dispatch，过期且没有可持久读取的原响应 | 原调用成为 `result_unknown`，不查询供应商、不重发 | 原调用成为 `result_unknown`；同样不通过重新调用猜测旧结果 |

candidate 响应记录绑定 `claim_version`，原编码内容和摘要必须一致；晚到 worker 不能倒填完成时间越过已失效租约。已经完成的同一 claim 重放读取已有终态，不再接受第二个候选。

并发模式下，多个槽位可独立执行，但 claim 领取、外发和结算使用数据库协调锁及精确 claim 身份。Run 的单调版本不要求每个在途 worker 使用同一个旧版本结算；真正结算的是它自己的持久 claim。未决 unknown 即使尚在等待排空也停止新派发，blocked 状态和取消意图同样禁止新派发；其他已经外发的调用仍能按原身份完成。只有活动 claim 排空后，协调器才把完整清单关闭，或绑定原失败进入 blocked；后到的成功不能覆盖先前失败的阻断证据。

预算按共享协调锁下的 dispatch 账本当前值检查，同时限制单目标次数和整个阶段次数。进程内限流只能减少同时外发数量，不能代替这些数据库条件。管理变更使用 `Transactions.commit(db)`：独立调用提交自己的事务；MQ 根事务借用包装器不提交、回滚或关闭宿主 Session，由接单根统一落库。资源和借用规则见 [Dishka 作用域与资源所有权](../../01-运行时/02-Dishka作用域与资源所有权.md)。

## G1/G2 先证明这份清单可以被评判

35 个候选全部 `review_ready`、且没有活动执行之后，Run 转为 `awaiting_review`，原关闭转移为 `candidate_evidence_complete`。这个状态允许审核，但不是可跳过原记录的证明。

`PreviewGates`、Finalize 和最终结论读取会通过 `load_snapshot()` 重建证据，主要检查三组关系：

1. **固定条件。** 组织和创建审计一致，整体 release 指纹正确；冻结策略、注册 Suite 及原生 Manifest 匹配，预算表策略与 Run 的原策略字节一致；35 个槽位和预检计划必须与 Suite 一项不差。预检按原时间重新计算，不能直接信任存储的 `passed`。
2. **调用清单。** 每个 dispatch 对应终态记录；execution/invocation 唯一，候选归属、输出指纹、接受的语义回执及 decisions 相互绑定；尝试序号连续、数量在原预算内，候选接受后不能另做生成，语义接受后不能再加一条裁判回执来挑结果。
3. **关闭历史。** 从原请求、启动、预检到唯一关闭的时间和转移合法。每条历史 unknown 都有精确绑定的阻断与人工恢复证据，语义契约例外也必须有原失败和授权；后续尝试不得早于授权。原调用和完成时间都落在收集区间，关闭指向最后完成的原语义证据。

因此 `unresolved_result_unknown_count=0` 只是要核对的索引，删掉原 unknown 或把计数改成零不会消除核证义务。复审后的历史门槛和签名也逐轮复算。

实现中 G1/G2 不是两个可编辑的持久布尔值。上述校验通过才构造 `GatePreview`，其 `gate_passes` 加上 `G1=True、G2=True`；证据缺失或绑定不合法会直接拒绝预览。一个只有 34 个合法候选的 Run 不能靠计算 `34/35` 来取得“其余门槛通过”的有效清单。

## G3 的分母取决于原 Run 的接受规则

新 Run 的 `candidate-completion/v1` 要求 35 个候选均有成功语义回执，`candidate_completion_rate=35/35=1.0`。技术成功率仍按原回执计算，但输出为 `observed_*`，threshold 为 null，不因这些观测本身拒绝 G3；首轮成功率和重试数也保留。

没有该冻结规则、也没有合法保留采用审计的旧 Run，沿用 `release-gates/v2` 的三个硬门槛：

| 旧 G3 指标 | 分子 / 分母 | 最低值 |
| --- | --- | --- |
| infrastructure_success_rate | 基础设施成功执行 / 生成与语义中 `provider_call_count=1` 的全部执行 | 0.98 |
| generation_contract_conformance_rate | 成功生成 / 有确定原输出且不是 unknown 的生成执行 | 0.95 |
| semantic_execution_success_rate | 成功语义执行 / 已外发语义执行 | 0.98 |

“基础设施成功”包括成功回执，也包括已经收到供应商 receipt、随后输出契约或指定语义输出契约校验失败的执行；它不表示内容通过。超时、限流、unknown 不算基础设施成功。unknown 即使后来获准替代，原调用仍在分母中。

例如 35 次生成均成功，某候选第一次语义调用限流，第二次成功，其余 34 次语义首轮成功。原清单有 35 条生成、36 条语义，基础设施成功率 `70/71≈0.986`，语义执行成功率 `35/36≈0.972`。旧规则因后者低于 0.98 拒绝 G3；新规则在完整合法恢复的前提下以 `35/35` 通过 G3，同时保留这次技术失败和恢复观测。G4、G5 都还要计算。

`acceptance_version()` 还识别保留的 `acceptance_rule_adoption`：原规则、组织内 Run 的 release 指纹、操作者/原因、关闭后采用时间、源版本及严格加一版本必须匹配。当前运行包没有提供该历史写命令；这是一条兼容读取规则，不是可以在管理界面随时切换策略的操作，也不能重写原创建文档或历史 Finalize。

## G4 同时检查稳定性、硬断言和两层分数

当前门槛策略为 `release-gates / v2`，同时核对以下条件：

| 质量条件 | 实际判定 |
| --- | --- |
| 案例稳定性 | 每个案例的 5 个候选中至少 4 个通过全部 case 断言；35 个候选合计至少 32 个通过 |
| 硬断言 | 任一 `hard=true` 或 `scope=default` 的断言组失败，直接拒绝 G4，不能用其他候选的通过抵消 |
| 单候选评分 | 五个字段恰好齐全，均为 1–5 的整数；每个候选都须达到对应下限 |
| 全体均值 | 对同一批 35 个候选计算各字段均值，各自达到门槛；不能删除低分候选再求均值 |

断言按 `(scope, type, ordinal)` 分组。相同组同时留下 `passed` 和 `failed/blocked` 时，失败优先；case 断言缺失也不能算通过。7 个案例若各只有 4 个通过，虽然都达到 `4/5`，总计 `28/35` 仍低于 32；某案例只有 3 个通过，即使全体达到 33，也不满足单案例门槛。

| 分数字段 | 每候选下限 | 35 个候选均值下限 |
| --- | --- | --- |
| faithfulness | 4 | 4.5 |
| cross_dimension_quality | 3 | 4.0 |
| suggestion_actionability | 3 | 4.0 |
| audience_clarity | 3 | 4.0 |
| concision | 3 | 4.0 |

例如 faithfulness 有 17 个 5 分、18 个 4 分，所有候选都达到单项下限，但均值 `157/35≈4.486`，G4 仍失败。反过来，一个候选只有 3 分，其余全部 5 分，即使均值很高，单候选门槛仍失败。两类失败都保留原候选，不能靠第二次生成或第二份语义高分覆盖。

三主题方案中 `cross_dimension_quality` 的义务是三主题解释质量，具体按原语义 Prompt 判定，不能继续套用旧“至少两轴”的目标。正文、引用和参考材料义务见 [MBTI 三主题输出契约](../interpretation/03-MBTI三主题与参考材料契约.md)。Schema、确定性断言、模型语义裁判分别产生证据；结构正确不直接证明自然语言忠实或有信息增量。

## G5 需要 70 条真实的责任签名

每个候选必须由两个不同的人分别提交 `assessment_semantics` 与 `safety_product`，结论为 `approve/reject`，同时有原因和服务端时间。一个人可审核多个候选，但不能占同一个候选的两个角色；同一候选同角色和同一候选同审核人都不能重复写入。一条 reject 即使其他 69 条 approve，也会阻断 G5。

例如 `user:42` 一批提交 35 条语义角色签名，`user:57` 再提交 35 条安全产品角色签名。每个批次为同一角色、1–35 个候选，审核人必须等于可信 scope 的操作者，不能由客户端为其他人签名；一批中任一签名不合法则整批拒绝。

接受批次前先锁检查点，再锁组织范围内的 Run，核对 `expected_version` 和无活动串行检查点，从原生成、dispatch、语义记录重建全部审核目标。`human_reviews` 追加与检查点从 N 到 N+1 在同一事务中写入。假设语义批次以 N 成功，安全批次必须使用 N+1；两个操作争用 N 时只有一个成功，另一个刷新原状态后才能提交。这个版本约束不是方案命令的 UUID 回执重放协议。

当前控制入口也有差别：治理 gRPC 的 Start 和 Cancel 已拒绝执行，接单通过 MQ 命令进入管理服务；Review、PreviewGates、Finalize、ReopenReview、ListUnknownExecutions 和 ResolveUnknown 仍由可信 QS 工作负载的治理 gRPC 调用。AI 使用 QS 委托 scope 核对组织和操作者，管理端权限校验由调用方负责，不能直接接受公网身份自报。

## Preview 和 Finalize 怎样把判断固定下来

`PreviewGates(run_id, expected_version)` 是无写入、无模型调用的复算。它可以展示 G4/G5 失败原因，但不形成批准。Finalize 要求 `expected_version`、`expected_passed`、原因和 `confirm=true`；不能仅提交客户端保存的预览 JSON。

Finalize 在首次读取前设置 REPEATABLE READ，锁检查点及组织内 Run，然后重读原证据、计算 G1–G5。若结果与 `expected_passed` 不一致则冲突返回，不写终态；符合时在同一事务把 Run 改为 `approved/rejected`，存储 `qs-ai-evaluation-finalization/v1` 完整门槛、指标、原因、裁定、release 指纹和审计，并严格推进一个版本。

完整审核是终结的前提。只有 69 条签名时，即使 G4 已经失败，也不能用 `expected_passed=false` 提前 Finalize 为 rejected，Run 仍须完成审核。70 条完整签名中有一个人 reject，或者前述均值失败，则可以按复算的 false 形成 rejected；不能换候选或编辑原签名把它改成 approved。

读取最终结论时也不直接信任 `gate_result`。`verified_final_snapshot()` 恢复原 Finalize 前的审核状态，在原决定时间重算，核对源版本+1、状态、最终转移及完整记录；存储结果被篡改时读取会失败。通过的 Run 仍没有改变在线指针，后续 Publish 还要锁定并重新核证它，见 [发布证据与生效指针设计](../publication/01-发布证据与生效指针设计.md)。

## 技术恢复分别授权什么

### unknown：确认接受额外调用风险，保留原未知事实

假设上述槽位第一次生成已 dispatch，但 worker 消失且没有可持久恢复的响应。恢复把原执行记为 `result_unknown`，该槽位没有 Candidate；unknown 不能证明供应商没有执行，也不能当作确定失败自动重发。

`ListUnknownExecutions` 要求原 Run 版本、无串行检查点且无活动 slot claim，重新核对原创建、dispatch、completion 和既有 resolution。列表提供原 execution/invocation、阶段、槽位或候选、尝试次数、时间、分类失败与目标/Run 预算，不查询供应商。`replacement_allowed` 是根据原预算计算的操作提示。

Resolve 必须绑定这个准确 `execution_id`，提交 `authorize_replacement` 或 `cancel_run`、原因、风险确认 `acknowledged_duplicate_call_and_cost_risk=true`、显式版本和确认。它锁定原检查点及组织 Run，candidate 模式另要求活动 claim 排空；原 unknown、既有决议和授权时间逐条核证，不能重复解决同一执行。

替代授权追加原执行的 resolution，原终态仍为 unknown；还有未解决调用时继续 blocked，全部解决后可恢复 collecting，下一步使用同阶段的新 execution/invocation、尝试序号 2。授权自身校验目标尝试余量，重新准入和派发还要满足 Run 预算、容量、取消意图和计划条件，所以授权成功不保证一定再调供应商。第二次又 unknown 时，没有第三次目标预算。`cancel_run` 的裁定仍保留原未知证据。

### 语义契约例外：只修复同一候选的裁判输出契约

语义输出 Schema 合法，却漏掉一个必须评判的 decisions 项，可能形成 `semantic_decision_contract_invalid`。当前冻结自动恢复规则不允许它直接重试；Run 在原失败处 blocked，Candidate 不变。

内部 `authorize_contract_recovery()` 是另一受限事务入口，当前治理 gRPC 没有公开它。授权需匹配组织、CAS、release 指纹、最后的 `semantic_recovery_not_allowed` 阻断与原 execution，确认原失败有 receipt 和规范输出、候选及输出指纹正确，没有后继尝试且目标及语义 Run 预算尚有余量。重新投影后，下一动作必须正是该候选的 ordinal+1，才保存 `semantic-contract-recovery/v1`、恢复 collecting。

下一次语义调用只添加指纹固定的修复指令：原检查项的 `(type, scope, ordinal)` 各返回一次，不遗漏、不重复、不增加，如实保留失败判断。它不编辑冻结 Prompt，不更换生成候选，不要求裁判判通过；第二次失败后也不会放出第三次调用。

### 取消：先停止派发，再排空已有所有权

有活动 candidate claim（包括 prepared）、串行 dispatching 检查点或未决 unknown 时，Cancel 仅在 collecting/blocked 保存 `cancel_requested`，推进版本并保留原状态和所有权。该意图阻止新调用；已外发的调用仍结算或恢复。unknown 的替代授权也不会消除取消意图。

只有检查点为空、claim 全部排空、unknown 全部解决，`finish_cancellation()` 才复用原审计形成 canceled。串行 prepared 且尚未外发时可直接取消，但把原检查点留为 `canceled_checkpoint` 审计。awaiting_review 的终止必须显式 `discard=true`，原因码为 `operator_discarded`；它不会删除候选和签名，也不会撤回已经发生的供应商调用。

## 复审只处理一类可证据绑定的语义矛盾

低分、案例稳定性失败、G3 失败和人工 reject 都不在 ReopenReview 的修复范围。可重开的 Run 必须已经 rejected、门槛 v2、G3/G5 通过，G4 所有原因仅为 `candidate_hard_assertion_failed`；这些失败还须精确来自原语义裁判的 `default / forbidden_claims_absent`。最多允许三个 reopen 记录。

例如原裁判把一句明确表示“不是岗位适配结论”的候选文案判为禁止主张，两个审核角色认为原 detail 与正文矛盾。重开事务先从原 Finalize 复算资格，保存前一轮全部 70 条签名、最终记录和源/新版本及时间，保留未受影响候选的签名，只移除当前受影响候选的签名让他们重新审核；原 Candidate、供应商输出、评分和关闭时间都不变。

纠正依据不是两个人普通 approve。两个不同角色都须提交 `semantic-contradiction-dual-review/v1`：同一候选的已接受语义 execution、语义输出指纹、断言序号、原 detail、候选中真实存在的摘录及理由。身份和原失败项须在候选断言、原语义断言及原 decisions 中一致；两个角色指向同一原失败项才形成有效裁定。

门槛复算据此派生该断言的 `effective_status=passed`，同时记录 `original_status=failed` 和两名责任人；不会改写模型原回执。单角色提交、摘录不在原文、其他硬断言或低评分都不能通过这条机制豁免。未重开的 awaiting_review 中也可提交这种绑定审核，形成相同受限裁定。

复审后的受影响候选必须使用不早于 reopen 的新签名；未受影响签名不能被删除或替换。后续读取、预览和 Finalize 逐轮重算历史门槛、转移和版本，历史限制最多三条且总尺寸不超过 2 MiB。清空历史或只保留最新 approve 不能绕过原拒绝记录。
