# 量表兼容与回执重建

增加 MBTI、Route v2 或候选并发，不能把已经接受的量表请求改成另一种输入、模型调用或输出协议。**当前量表保留 v1 事实、输入、输出和 Artifact；新路径显式分派，原响应恢复仍使用原配置和原身份。** 兼容证明需要说清比较的是规范 JSON、原请求字节、保留的历史投影，还是某条持久执行。

本文按 `766b2aa` 的业务源码核对，沿“一个量表维度没有标准建议，随后原模型响应已保存但成果提交中断”这个例子展开。仓库中的历史生产摘要只证明其记录时间的观察，本篇不查询当前环境，也不把历史 active 当成现在的 active。

## 哪些东西继续按原 v1 解释

| 对象 | 量表原路径 | 人格扩展后的处理 |
| --- | --- | --- |
| 标准报告快照 | `qs-report-snapshot/v1`，scale/score_range | 不加 pole_facts，不从类型描述补人格事实 |
| Profile 协议 | `ai-explanation-profile/v1` | 保留原严格字段与规范摘要，不默认补 MBTI scene/reference 字段 |
| 组装输入 | `ai-explanation-input/v1` | 原 Profile 的维度、常模、model_result、数量和引用规则 |
| 模型输出 | `ai-explanation-output/v1` | integrated_insights、suggestions、limitations 等原字段和来源标签 |
| 成果封装 | `qs-ai-artifact/v1` | 保留原输入/配置/调用/报告关联；三主题 Artifact v2 另有显式分支 |
| 正式发布 Session | `qs-published-snapshot-v1` | 继续绑定原 Publication；不能随新指针换输入 |
| 旧快照 Session 标签 | `qs-snapshot-v1` | 领域仍识别它；是否能重建某条历史回执须逐条核证 |

这里的 v1 是协议边界，不是 Prompt/Profile 的资产修订。测试基线的 Profile v6、Prompt v6 和 Route v8 都仍可处于这些 v1 协议中；不能看到资产 version 变大就迁移历史输入。

量表 selector 有精确模型、模型级和通用槽位；MBTI 则只有精确有限模型，见 [发布设计](../publication/01-发布证据与生效指针设计.md)。把一份真实 typology 模型身份塞进量表快照，原量表 `assemble_input` 会拒绝为 NotApplicable，不因此开放人格输入。

## 一次量表组装具体保留哪些事实

[assemble_input](../../../src/qs_ai/application/interpretation/input.py) 使用接受 Profile 的 InputPolicy，按 eligible/excluded code 筛选维度，再核验数量边界。原分数、派生分、等级、层级、常模与标准文本来自 QS；AI 不重新评分或变更风险等级。

例如维度 A 没有标准建议，维度 B 有一条标准建议：A 的 `standard_suggestion_refs` 应是空数组，B 的引用指向组装后真实存在的标准建议。若过滤掉父维度 P，子维度的 `parent_ref` 可以为空；是否允许跨维度解读中同时引用父子，又由输出策略单独约束。筛选输入和约束输出不是同一操作。

组装保留以下确定规则：

- 维度按 sort_order/code 排序，ref 为 `dimension:<code>`；raw/derived score、level 和可选 norm_context 沿原数据投影。空等级展示标签可保留原 level code 为标签，不猜翻译或 severity。
- 报告建议与轴建议形成有限标准建议集合，保留来源引用并去重；缺少建议时输出 `[]`，不会新造一条通用建议占位。
- 是否包含常模与 model_result 由原 policy 决定；context 只覆盖本次测评，允许 focus 只影响解释上下文，不补新个人事实。
- 完整 canonical 输入保留 source/Profile 元数据并用于 input fingerprint；provider_payload 只含 context/facts，不能把完整输入 Schema 原样套在这个较小投影上。

报告归属仍通过外层 EvidenceItem 与快照内 report/content_schema/outcome 身份核对。筛选后的数量合法、摘要一致，不能替代这层来源关联。

## null 与空数组：保留的 Go 对照不是完整字节相等

这是兼容边界中需要明确的一处差异：旧 Go assembler 的 nil slice 可编码为 `null`，而 v1 输入 Schema 要求 `standard_suggestion_refs` 为 array。当前 Python 对所有缺少建议的维度输出 `[]`，没有按 `qs-snapshot-v1` 与新 workflow 分成两种编码。

```json
{"standard_suggestion_refs": null}
```

与：

```json
{"standard_suggestion_refs": []}
```

不是相同字节，也不是相同 Schema 类型。`test_retained_go_input_assembly_parity` 先把**保留的 Go 结果**中这个字段的 null 改为 []，确认确实发生了至少一处归一化，再按解析后的 JSON 比较其余投影。它不能证明原 Go 完整输出字节等于当前 Python。

而且该测试当前不启动 Go assembler：[legacy_go_baseline.py](../../../tests/legacy_go_baseline.py) 读取固定 [legacy_go_contracts.json](../../../tests/fixtures/legacy_go_contracts.json)，核对文件 SHA 和其中的旧 source commit，按请求 hash 取当时保留的合成响应。它保护退休实现的有限对照样本，不能替代当前 Go/Python 运行互操作或任意历史报告兼容。

因此，历史记录若在 FrozenGeneration 中保留 null，当前重新组装得到 []，接受比较可能不相等。不能通过改写原 request/input fingerprint 来“修复”，也不能凭旧 workflow 标签承诺它仍使用 null 分支。需要取该原记录，区分旧输入构造、固定 Schema、原响应和真正消费者，再按受控恢复流程决定处置。

## 输出 v1 的来源和跨维度规则为什么仍需保留

[QSOutputParser](../../../src/qs_ai/infrastructure/qs_server/output.py) 拒绝重复 JSON key、NaN/Infinity、非对象和不满足固定 Schema 的内容；正式发布路径用数据库原输出 Schema 构造 parser。`validate_output` 继续按原 RenderPolicy 检查：

| 检查 | 例子与失败含义 |
| --- | --- |
| 原 insight/suggestion 数量、kind/category、actions 上限 | Schema 合格却超出该 Profile 的数量或允许类别，仍失败 |
| evidence_refs 解析 | 引用 dimension:A、standard_suggestion 或 model_result，必须在这份原输入存在；不能借另份报告的 ref |
| 每条 insight 的维度数量 | 同一个维度重复写两遍不算两个不同维度，model_result 也不替代跨维度依据 |
| 父子组合限制 | 禁止时沿完整祖先链检查，不能只排除直接父子而放过祖孙；输入层级环也失败 |
| 标准建议的来源 | Schema 要求 `standard_derived` 至少带一条 source_suggestion_ref，应用校验这些引用存在于原标准建议；来源标签是否如实仍需内容判断 |
| 安全与免责声明 | 原 Schema、RenderPolicy 与 safety validator 继续校验；关键词和结构规则有有限覆盖 |

来源标签表达内容出处，不是样式字段。标准建议的转述可与另一建议语义接近，但不能为去重将 `standard_derived` 改成 `generated_low_risk` 并清空来源。这样改标可能仍通过 Schema 和引用存在性检查；如实保留 provenance 是内容义务，程序的这两层检查不能完整识别。所有引用均存在，也不能证明文本忠实或具有跨维度信息增益；治理语义评分、人工审核与具体内容验收各自承担判断。

MBTI 单篇仍用 output v1，但增加类型冲突等场景规则；三主题则显式用 output v2。不能把新的三主题结构交给旧量表 parser，也不能靠容错删除字段后降级成 v1。

## 原请求与响应怎样经过版本分派

[JSONModelCallCodec](../../../src/qs_ai/infrastructure/persistence/model_call_codec.py) 的编码策略保留量表路径：普通 InputPolicy 使用原 TypeAdapter 编码；MBTI 的派生 policy 则显式编码其完整字段。`test_scale_request_original_bytes_are_preserved` 比较新编码和原量表编码，保护没有因人格字段扩展而无故改写量表 request。

Route 的分派看原 JSON 中是否存在 `format_version`：存在时按 ModelRouteV2 严格解码，不存在时按原 ModelRoute。字段超出所选类型或 v2 校验失败就拒绝，不能让 union 失败后丢掉 v2 字段退回 v1。新 endpoint、binding 或提供商容量设置也不能覆写原 request。

InputPolicy 按冻结 Profile definition 的 `schema_version` 选择 v1/v2/v3，字段集合必须精确。这里应区分实际校验范围：

- MBTI policy 解码会重新解原 published Profile 并比 policy；三主题还验证固定 reference projection、canonical/payload/messages 与摘要。
- 普通量表 codec 不执行上述 MBTI 专用 Profile 等式检查。正式发布请求的完整一致性继续由 `validate_generation` 从原 binding/Publication 重建 FrozenGeneration，并在派发与成果接受时比对；不能说 codec 单独证明了全部发布关联。
- 构建 Artifact 时又从原 EvidenceSet/policy 重组输入，要求完整 AssembledInput 相等；存储接受再用持久响应重建整候选。层次互补，不能省掉后一层。

恢复的 ModelResponse 是结构化持久值，包含 invocation/model/provider request ID、raw_output/validation_output 等，不是原 HTTP wire 导出。`execution_identity=None` 的响应编码继续省略该新增可选字段，避免向旧响应字节无故增加 null。

## 原响应已保存，恢复能做什么

假设量表 Run R 的 ModelCall 已 `response_received`，但 Artifact 的原事务因为 Outbox 写入失败回滚。下一次合法 Claim 读取原响应，重建输入、输出和候选；它不实例化一次新的供应商调用来追求相同文本。

| 原记录 | 恢复行为 | 仍需满足 |
| --- | --- | --- |
| request、response、binding 完整 | 本地重建和校验，尝试原成果接受 | Job可领取/预算未耗尽、当前Run/版本/fence有效、原资产/证据完整，两次当前授权通过 |
| dispatched/unknown，没有确定响应 | 保留未知调用，按原 Run 阻断 | 不因重启或数据库暂时恢复自动再发送 |
| 明确 failed 与 failure_code | 复用原失败 | 不把 retryable provider error 当作同 Invocation 重新调用授权 |
| 原冻结配置或输入不一致 | 拒绝恢复/接受 | 不读当前 active，也不使用脱敏 fixture 或最新报告替换 |

同一 Run/Invocation 的 Artifact ID 确定；原响应恢复成功不创造第二份业务成果。ParticipantRetry 是新命令、新 Run 和新调用预算，保持原 Session/配置/事实，不是修改原调用记录。完整提交、授权和业务 ACK 见 [解读成果设计](01-解读冻结输入与成果设计.md)。

历史摘要中的 Profile `participant-scale-score-range-default/v6`、Prompt `cross-dimension-participant-scale/v6`、生成 Route `balanced_text_v1/v8` 和语义 Route `semantic_judge_v1/v5` 指向那次观察的资产。当前请求恢复查它自己的不可变绑定；不从这些测试文件装配线上配置。

其中一次历史只读重建复用了已完成调用的 FrozenGeneration/ModelResponse/绑定/发布证据，重新编译、组装、验证和构造成果，未调用供应商。输入及完整 Artifact 相等只证明那一条原记录可重建；不是崩溃演练、重新生成成功、当前线上开放、MBTI质量或设备验收。

## 维护时如何按证明层次选择检查

| 变更可能影响什么 | 应核对的现有测试 |
| --- | --- |
| v1 Profile/输入规范字节、Prompt渲染 | [test_personality_extension_baseline.py](../../../tests/test_personality_extension_baseline.py)：固定 canonical/payload/hash 与消息hash；[test_profiles.py](../../../tests/test_profiles.py)：Profile解码和字段 |
| 量表选择、层级、建议和null归一化 | [test_input_assembly.py](../../../tests/test_input_assembly.py)：合成投影及保留Go结果比较，明确只有单字段归一化后JSON相等 |
| v1输出范围、祖先链、建议来源和安全分支 | [test_output_validation.py](../../../tests/test_output_validation.py)、[test_artifact.py](../../../tests/test_artifact.py)；结构和引用通过不外推自然语言质量 |
| 原量表请求编码、MBTI不能换绑量表、原响应复用 | [test_mbti_runtime.py](../../../tests/test_mbti_runtime.py)、[test_model_route_v2.py](../../../tests/test_model_route_v2.py)；使用有限替身，不证明任意历史请求可恢复 |
| 同一数据库事务内成果/状态/事件与原发布接受 | [test_artifact_acceptance.py](../../../tests/integration/test_artifact_acceptance.py)、[test_execution_configurations.py](../../../tests/integration/test_execution_configurations.py)；须隔离MySQL，skip不算通过 |
| 真实消费者能接受原/新版本 | 对应固定Go互操作与原QS接收契约，并按真实请求核对STORED和投影；不是保留Go fixture比较可以替代的层次 |

删除旧解码器或资产前，还需要准确的历史版本与未结请求清单、恢复处置及消费者证据。新增版本通过自己的测试，不自动证明可以清除旧路径；文档和源码中的兼容标签都必须回到原字节和实际入口核证。
