# 治理链与执行链

把一套新 Prompt 用到参与者报告上，需要先完成两件不同的事：**治理链证明这套配置按固定条件评测过，并决定新请求是否可以采用它；执行链把某次业务请求绑定到这套配置，生成、验证并交付一份成果。** 两条链通过不可变的 Publication 相接。

本文以“改进 MBTI 三主题解读，然后为一份 ISFJ 标准报告生成解读”为例，跟踪每一步读取什么、留下什么证据、下一步凭什么继续。组织、操作者和业务标识采用示意值，资产与契约版本来自仓库；这不是一份可直接提交的操作脚本。源码核对基线为 qs-ai `766b2aa`，跨服务边界沿用[系统定位与跨服务边界](01-系统定位与跨服务边界.md)中的 QS/IAM 基线。本文不声明某个环境已经安装模板、完成真实审核或采用相应发布。

## 一次工作怎样贯穿两条链

假设组织 `912` 的运营人员 `42` 要改善职业主题的具体性，又不改变 QS 已确定的 MBTI 类型、输入事实或参考材料。治理操作先经过 QS 管理入口的身份、机构关系与能力检查；AI 接收经 mTLS 认证的 QS 委托 scope，在该组织内处理工作区和评测。参与者稍后发起的报告解读仍由 QS 单独检查当前资源访问权。

```mermaid
flowchart LR
  C[从固定来源创建 Solution] --> S[保存 Prompt 与模型参数]
  S --> P[Prepare：冻结资产并创建 requested 评测]
  P --> E[MQ Start：评测进入 collecting]
  E --> V[生成、裁判、关闭候选证据]
  V --> R[双角色审核与 Finalize]
  R --> PUB[Publish：保存发布并移动 selector 指针]
  PUB --> A[参与者 Start：绑定原 Publication]
  A --> W[Worker：原配置、原输入、原调用]
  W --> ART[持久 Artifact 与完成事件]
  ART --> QS[QS 持久接收并返回 STORED]
```

图中没有跨服务大事务，也没有从“Prompt 保存成功”直达“线上配置已生效”的捷径。可用以下记录判断这次工作实际走到了哪里：

| 看到的记录 | 已经成立的事实 | 下一步仍缺什么 |
| --- | --- | --- |
| Solution 的新 `revision` | 工作区改动已经保存 | 尚需冻结和评测 |
| `prepared.run_id`，评测 `status=requested` | 全套资产及计划已冻结 | 尚需显式 Start，未调用模型 |
| 评测 `status=awaiting_review` | 候选、裁判及执行历史已完整关闭 | 尚需双角色审核和门槛最终决定 |
| 评测 `status=approved` | 该 Run 的最终门槛与审核已经通过 | 尚需 Publish；批准不会移动线上指针 |
| Publication 与 selector 的新 `version` | 之后符合准入规则的新请求可以绑定该发布 | 尚无某个参与者成果 |
| Session `status=completed` 与 Artifact | AI 已持久形成该请求的成果 | 尚需 QS 对原事件确认接收 |
| 原成果事件的 `STORED` ACK | QS 已按关联规则持久处理该事件 | 当前参与者读取仍需通过 QS 权限检查 |

## 治理链：把一次修改变成可供接单的配置

### 1. 创建并保存工作区：来源固定，修改尚未生效

运营人员可以从已保留的 `publication_id`、`source_run_id` 或精确 `template_ref` 创建 Solution，三者只能选一个。本例选择已安装的 MBTI 三主题模板。Create 读取数据库中的原资产，不会因为模板缺失就临时从初始化文件补建它。

这套根资产明确约束场景：

```json
{
  "selector": {
    "audience": "participant",
    "model_kind": "typology",
    "decision_kind": "pole_composition",
    "model_code": "MBTI_OEJTS",
    "model_version": "v64-report-202608-v1"
  },
  "scene_contract_version": "mbti-single-assessment/v2",
  "generation_policy": {
    "input_schema_version": "ai-explanation-input/v3",
    "output_schema_version": "ai-explanation-output/v2"
  }
}
```

这是[三主题根 Profile](../../integrations/qs_server/evaluation/mbti-themes/profile-v1.json)的字段节选。它决定生成 `personality / career / relationships` 三主题；运营人员不能通过 Save 把原量表工作区重新贴标成这个场景，也不能在修改 Prompt 时顺手换掉 selector、Schema、执行预算或门槛策略。

例如创建后工作区 `revision=1`，Save 带 `expected_revision=1`，保存修改后的 Prompt 草稿、生成模型参数与语义裁判参数，成功后成为 `revision=2`。生成模型和裁判模型是两份独立选择，实际 Route 还需通过允许模型与能力校验，不能只凭一个模型名称执行。

Save 同时核对 Solution revision 与关联 PromptDraft revision。另一入口若已经改过这个草稿，本次保存或准备会发生冲突，避免工作区显示一段 Prompt、实际却冻结另一段。已经 Prepare 的工作区不能继续编辑；下一轮改进应从固定来源另建工作区。

Create、Save、Prepare 各自带稳定 `command_id` 和原因。相同命令、正文与可信 scope 重放返回原回执；更换正文继续使用旧 ID 会冲突。命令回执也按组织及操作者隔离，组织 `912` 的另一操作者不能假借相同 ID 读取人员 `42` 的原回执。

### 2. Prepare：一次事务生成可评测的完整依赖

本例 Prepare 带 `expected_revision=2`。`MySQLSolutions.apply` 在锁定工作区和草稿后，借同一数据库事务完成以下操作：

1. 冻结当前 PromptDraft，形成固定模板、版本、指纹和包正文。
2. 注册生成 Route 与语义 Route，保留各自模型及参数。
3. 从原 Profile 派生新版本，绑定新 Prompt 与生成 Route；从原 Suite 派生新的评测资产。
4. 重新读取并核验全部资产与策略，保存五项生成 Manifest，以及包含评测 Suite、裁判和策略的十一项 ReleaseIdentity。
5. 以 `uuid5(solution_id, "evaluation")` 创建唯一评测 Run，保存 `requested`、初始 `version=1`、输入案例、候选槽位和冻结策略；保存 prepared 状态、工作区新 revision 与原命令回执。

这一步产生的 `prepared` 返回 `run_id`、`release`、`manifest` 和 `plan`。当前绑定的 `release-evaluation-bounded-recovery@v2` 计划是 **7 个生成案例 × 每案例 5 个候选 = 35 个槽位，另有 1 个预检**；生成和语义执行各最多 70 次，每个生成槽位、每个候选的语义执行最多 2 次。35 是需要接受的候选数，70 是有限执行预算，不能把预算理解成可以生成 70 篇后挑出最好的 35 篇。具体原策略见[冻结策略资产](../../integrations/qs_server/evaluation/policies.json)。

Prepare 不调用供应商，不自动 Start，也不发布。若冻结、资产注册、最终一致性校验或回执构造中任何一步失败，整个事务回滚，工作区不会留下“已准备但没有 Run”的半套状态。若客户端丢失返回，应查询或重放原命令，核对原回执；换一个命令 ID 不能证明上一次没有成功。

直接创建评测的治理接口同样要求完整固定 ReleaseIdentity，并形成 `requested` Run；Solution 路径已在 Prepare 中完成创建，不必再创建一个平行 Run。后续应始终使用 `prepared.run_id`。

### 3. Start 与模型执行：先接受命令，再逐条形成证据

运营人员确认计划后，由 QS 发送受保护的 `EVALUATION_START` MQ 命令，携带原 `run_id`、当前 `expected_version`、原因和 `confirm=true`。AI 的命令接收器验证 wire 与正文，在原接单事务中检查 scope、Run 状态、版本、模型与容量，再把 Run 从 `requested` 转为 `collecting`，连同 Inbox 决定和首回执 Outbox 一起提交。

`ACCEPTED` 在这里表示“已经持久接受启动决定”。它不表示预检、35 个候选或任何模型调用已经成功。保留在 proto 中的旧 `EvaluationManagement.Start` gRPC 当前返回 `FAILED_PRECONDITION`，不能用于绕开 MQ 接单。

后台评测先做冻结 Suite 的预检，再为 `(case_id, ordinal)` 槽位逐步运行生成和裁判。本例 `MBTI-EVAL-001` 的输入包含 `type_code=ISFJ`、四轴既定偏好与分数、三主题参考材料；生成模型只解释这些已知事实。槽位可以在创建时冻结的 `candidate_v2` 模式下并发推进；旧 Run 保持原 `serial_v1`，调高当前并发设置不能改变旧 Run 的计划或执行模式。

每一次外部调用都受固定身份和预算约束。下表中的“先独立保存原响应、再投影”屏障属于 `candidate_v2`：

| 步骤 | 保存或使用的证据 | 故障后可做什么 |
| --- | --- | --- |
| 领取并准备 | 当前槽位、租约 owner、execution ID、Invocation、固定输入/Prompt/Route/Schema | 失去租约的 worker 不能提交另一份结算 |
| 标记派发后外发 | 原派发身份和调用预算；模型 HTTP 在事务之外执行 | 已派发但没有确定响应时保留 `result_unknown`，不能猜测未调用 |
| 保存原响应 | 提供商 request ID、原响应、结束时间或明确失败及回执摘要；终态另保存输出字节与输出指纹 | `candidate_v2` 先独立提交原响应，投影中断可据原回执恢复，无需重调模型 |
| 投影 Candidate | 首个符合生成契约的输出与确定性断言 | 候选质量不佳不能授权替换它 |
| 语义裁判 | 同一候选输出指纹、独立裁判执行与原响应、评分和断言 | 裁判故障只能恢复该候选的语义执行，不能重新生成候选 |

输入由冻结 Suite、case 和生成配置重建，没有另一个独立的 `input_fingerprint` 字段。`serial_v1` 仍由 `finish_step` 一起保存终态，不具备上述独立响应提交屏障，不能把两种模式的恢复能力视为相同。评测图中的 `prepare_dispatch → invoke_model → commit_receipt` 只组织有限步骤；数据库槽位、检查点、租约和原响应负责恢复。LangGraph 本身没有另一个持久 checkpointer 可以代替这些证据。

### 4. 关闭、审核与 Finalize：质量不能由一次“模型成功”代替

只有全部槽位、预检、生成和语义回执、预算及恢复记录验证完整，并且没有未决 unknown，Run 才进入 `awaiting_review`。它不是“候选看起来够多了”的人工开关。即便后来某次调用成功，原 unknown 的核证、替代授权和调用历史仍需逐条说明。

审核人员阅读固定候选及对应裁判证据。每个候选需要两个不同人分别给出 `assessment_semantics` 与 `safety_product` 审核，附结论、原因和服务端时间；35 个候选需要 70 份审核记录，同一人不能为同一候选同时签两种角色。

例如语义裁判把某候选的 `faithfulness` 评为 `3`：即使五项平均分很好、两名审核人都喜欢它，当前冻结规则仍要求忠实性单项至少 `4`，不能发布。另一种情形是 35 个候选都有较高分，却有一名审核人给出 `reject`：G5 仍失败。完整签名和质量得分分别表达责任与内容判断。

| 门槛 | 这套配置必须证明什么 |
| --- | --- |
| G1/G2 前置核证 | 固定 release 身份与冻结评测文档一致，完整预检/候选/调用历史，预算与恢复授权有效，没有未决 unknown，原证据关闭时间成立 |
| G3 执行完成 | 新 Run 冻结 `candidate-completion/v1`：35 个候选全部具有成功生成及语义证据，完成率为 1.0；技术成功率、首轮率和恢复数作为观测 |
| G4 内容质量 | 每案例至少 4/5、总体至少 32/35 通过案例断言；硬断言失败阻断；五项语义分的单项下限与整体均值分别达标 |
| G5 人工责任 | 每候选两人两角色的完整审核，任何人工拒绝阻断 |

五项语义分为 `faithfulness / cross_dimension_quality / suggestion_actionability / audience_clarity / concision`。当前 G4 单项下限依次为 `4 / 3 / 3 / 3 / 3`，均值下限为 `4.5 / 4 / 4 / 4 / 4`。在三主题场景中，`cross_dimension_quality` 评价三主题解释质量，不能把旧量表跨维度目标原样套入。

七组冻结案例用于当前场景契约核查，不代表全部十六类型、全部业务输入的内容质量已经通过。旧 Run 若没有创建时冻结的接受补充规则，保留原 G3 计算，除非经过显式、审计的规则采用。旧策略中的 `0.98 / 0.95 / 0.98` 技术率门槛不能被新页面或新代码默默改写为观测值。

GatePreview 仅是某个 Run version 下的预览。Finalize 携 `expected_version`、`expected_passed`、原因与确认，锁住原 Run/检查点，重新加载证据并重算门槛。如果预览之后审核或版本变化，必须刷新，不能继续按旧预览批准。成功后才形成 `approved` 或 `rejected`，记录原 source version、release fingerprint、门槛结果、操作者与时间；此时 selector 指针仍未改变。

特定裁判矛盾可以按有限语义复审规则处理，但必须绑定原执行、输出指纹、失败断言、原 detail 和候选真实摘录；它不是任意编辑评分或重新跑模型的入口。完整规则由[评测设计](../02-业务模块/evaluation/01-评测候选门槛与审核设计.md)维护。

### 5. Publish：从批准证据到新请求的配置指针

本例首次在目标 selector 发布时，命令携 `expected_version=0`、`expected_active_id=null`、批准 Run 的 ID/当前 version、精确 `release_fingerprint`、原因和 `confirm=true`。这里 `0` 表示空槽位的初始指针版本，不是 Run version；如果该槽位已有发布，就必须使用实际读到的指针版本及 active ID。

发布事务先锁 Run/检查点，再锁 selector，重新核证最终审核与五门结果，重读五项生成资产并比对已评测 Manifest，复核生成和语义模型准入。随后创建不可变 Publication，并在同一次提交中把指针变为 `version=1`、`active_publication_id=新发布ID`，保存原命令回执和变更审计。客户端上传一个 `approved=true` 或一组资产引用，不能代替这些服务端证据。

该指针是**全局 selector 槽位**。Solution 属于组织 `912`，不意味着发布只影响组织 `912` 的参与者。MBTI 单篇和三主题使用同一个精确 selector；`scene_contract_version` 不在 selector key 中，本例发布三主题将改变这一槽位之后的新请求，不能宣称为单篇和三主题同时建立两个独立开关。

如果另一个操作者已先完成发布，本次旧 `expected_version/expected_active_id` 会冲突。应用不能自动刷新后重试覆盖；操作者需要看清新指针再重新作决定。同一原发布命令可按回执核对结果，不应在返回丢失时换 ID 再发布一遍。

停用清空指定槽位的 active 并增加指针版本；回退指向已保留的同 selector Publication，并重新核证原证据。它们不更换已经接受请求的配置，也不撤回已外发模型调用。量表还有较宽 selector 的兼容回落，MBTI 本例只有精确槽位；详细选择规则见[发布设计](../02-业务模块/publication/01-发布证据与生效指针设计.md)。

## 执行链：让这份发布产生一次业务成果

### 1. Start 绑定的是接单当时的发布

参与者为受测者 `7` 的测评 `42` 查看标准报告 `99`。QS 核对当前授权与业务来源，冻结标准报告快照，持久保存原请求及 MQ 命令。假设 `request_id=11111111-1111-4111-8111-111111111111`，其 snapshot 已有 `type_code=ISFJ`；该 request ID 标识这次原业务请求，不是评测 Run ID，也不是模型 Invocation。

AI 验证受保护 Start 的身份、正文、报告关联与输入适用性，创建自己的 Session、EvidenceSet 和执行 Run。`bind_configuration` 由报告导出 selector，找到接单时的 active Publication，在 Session 配置绑定中保存：

| 字段 | 本例绑定的含义 |
| --- | --- |
| `publication_id / publication_sha256` | 采用刚才发布的完整配置及其内容摘要 |
| `pointer_version` | 选取它时的指针审计版本，例如首次发布的 `1` |
| `selector_query` | 从这份 MBTI 报告得到的精确查询 |
| `evidence_set_id / evidence_fingerprint` | 采用的原报告事实集合与摘要 |

这份绑定与 Inbox 接单决定、Session/Run/Job、原请求映射、首回执和初始状态事件共享接单事务，提交之后 MQ 消费才能完成。接单不调用模型，也不在这里再次同步回查 QS 授权。

如果此后指针从 `1` 移到 `2`，新请求可能采用另一发布，本例已接受请求继续读原 `publication_id`。恢复时也核对它的发布摘要、原 pointer 审计、资产与原证据；发现损坏会阻断，不能从“当前默认”补一套新配置。

### 2. Worker 用固定输入执行，保存调用后再接受成果

Worker 领取 Job，以租约和 fence/CAS 防止旧 worker 结算。`ExecuteNext` 在执行前调用 QS `Authorize`，模型流程返回后、接受成果前再调用一次。QS 经 Testee → IAM Profile → 当前 ProfileLink 检查原主体关系并验证测评归属；报告事实已冻结，访问权没有冻结。

正式报告图按 `prepare → generate → validate` 推进：

1. Prepare 从原 EvidenceSet 和 Publication 构造 `ai-explanation-input/v3`，核对报告来源，并按 ISFJ 四个偏好选择冻结参考材料。
2. Generate 构造 `FrozenGeneration`，包含固定输入、Prompt、Route、输出 Schema、publication ID 和 manifest fingerprint。模型 endpoint 与凭证由网关持有，不序列化进该记录。
3. `DurableGeneration` 先提交原 Invocation 与请求，标记 `dispatched`，再外发。返回后保存原 provider request ID、模型响应及字节；已有 `response_received` 时复用原响应，已有 `dispatched/unknown` 而无确定响应时抛出 `provider_result_unknown`，不二次外发。
4. Validate 校验结构、引用、领域和安全规则，构建 Artifact 候选。本例包含三主题内容以及独立的参考材料正文和摘要；通用参考不会被混写成受测者实测事实。

评测阶段的语义裁判和 70 份审核证明的是这套发布的质量依据，**正式请求并不重新跑 35 个候选、语义裁判和人工双签**。它只有受固定配置约束的生成与接受校验。确定性检查也不能识别自然语言中的每一种错误，不能把已批准配置解释成每次文本质量必然正确。

第二次授权复核通过后，`MySQLExecutionStore.finish` 还会重新核对当前 Claim、Session/Run、EvidenceSet、Invocation、provider request ID、内容摘要和原配置，从持久原响应重建预期 Artifact 并比较。通过后一次提交 Artifact、Session/Run 完成、Job 结束与待投递状态事件。`artifact.id` 由原 `run_id + invocation_id` 确定生成，同一接受调用重放不会另造一篇身份不同的成果。

### 3. AI completed 之后，交付还要闭环

AI Relay 投递原状态/成果事件。QS 核对原 request、主体、Testee、Session 和事件版本，验证 Artifact 的报告来源、摘要和接收契约，再保存状态及成果投影，连同原事件的业务 ACK 一次提交。QS 不共享 AI 的 active Run，也不重新执行生成；Artifact 中 Run ID 的格式校验不能替代 AI 内部 Run 所有权检查。

Broker 确认只把事件推进到等待业务回执。AI 收到经验证的 QS ACK 后，还要匹配 `event_id / event_kind / event_body_sha256 / aggregate_key`，只有 `STORED` 才确认原事件交付；`TECHNICALLY_HELD` 会挂起交付。即使 QS 重复收到事件并返回原 ACK，这条关联也不能改变。

参与者随后从 QS 读取持久成果投影，读取入口另行检查当前权限。事件接收时没有额外执行一次 `CurrentAccess`；“成果已存储”不能永久授予原主体读取权。

## 把常见失败放回它实际发生的环节

| 现场现象 | 已成立的证据与状态 | 应如何继续 |
| --- | --- | --- |
| Prepare 返回前断连 | 可能已提交整套资产、requested Run 与命令回执，也可能全部回滚 | 按原 Prepare command ID 核对，不能假设失败后另建一套 |
| 某评测调用响应未知 | 原派发与预算存在，缺少确定响应；Run 可以 blocked | 按精确 execution ID 核证及受控授权，unknown 不等于供应商失败；不能自动重发或清掉计数 |
| 候选已形成，裁判失败 | 原候选字节和输出指纹已固定 | 在原候选上恢复语义步骤，不能因裁判失败重新生成更好文本 |
| GatePreview 后出现新审核记录 | 旧 preview 绑定的 Run version 已过时 | 重新读取、预览和明确 Finalize；不能用旧 passed 布尔继续批准 |
| Start 时没有匹配发布 | AI 保存 blocked、`configuration_unavailable` 及原拒绝回执，没有可执行 Job/接受配置 | 后来发布不改变原拒绝；同命令仍重放原决定。需由 QS 以新 request ID 发起新请求，不能用 ParticipantRetry 换绑 |
| 模型返回后原主体失去访问权 | 原模型响应可以已落库，接受前复核失败 | 记录 `access_revoked`，不接受候选为正式成果；授权依赖故障则是 `dependency_unavailable` |
| Artifact 已提交，QS 尚未 ACK | AI completed，但原事件仍未确认业务交付 | 重投原事件，保持 ID、正文/哈希和关联；不重新生成 |

### 重投与 ParticipantRetry 不是同一操作

传输恢复重投原 wire；同一命令的 Inbox/业务重放复用原决定，它不会创建新的业务 Run，也不授权再次调用模型。事件投递未知同样恢复原事件，与模型结果未知是不同状态。

ParticipantRetry 是经过 QS 管理授权、再核对原参与者当前访问权的**新业务命令**。它要求：Session 与原 Run 都为 `blocked`，Job 已结束或不存在，Session 已有接受配置；命令明确 `expected_run_id`、`expected_version`、原因、`confirm=true` 与 `expected_provider_invocations=1`。如果原调用为 `dispatched/unknown`，还必须显式接受 `accept_result_unknown_risk=true`。

受理 Retry 后创建新 Run 和 Job，保存从原 Run 到新 Run 的审计及新回执，但保留原 Session、QS request ID、EvidenceSet 和 Publication 绑定；存在原冻结模型请求时继续继承其字节。它承担一次新的外部调用预算，不能借机更换报告、Prompt 或发布。这也解释了为何“没有匹配配置的接单拒绝”不能通过 Retry 采用刚上线的配置：该 Session 根本没有可复用的接受配置。
