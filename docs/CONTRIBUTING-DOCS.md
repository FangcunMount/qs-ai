# qs-ai 文档维护约定

现行设计正文必须让读者能沿一次真实业务判断对象、状态、事务和失败结果。本文适用于根 README、`docs/00` 至 `docs/05`，以及配置、接入和部署说明；阅读入口见 [文档地图](README.md)。

## 先确定事实，再写解释

读取顺序是实际装配与调用方 → 用例/领域规则 → 事务与持久化 → 机器契约/配置 → 对应测试。proto 声明、类名、历史设计不足以证明入口当前可用。例如五个执行 RPC 仍在 proto 中，但实际 transport 在业务方法前拒绝；接口文章必须核对注册和拒绝路径。

| 来源 | 可以支持什么 | 不能直接推出什么 |
| --- | --- | --- |
| 当前入口、调用链、实现 | 何种条件下执行何种规则、怎样保存 | 某环境已启用、供应商已执行 |
| proto、Schema、manifest、迁移、配置 | 字段/字节/版本、表约束与默认值 | 所有声明已注册、旧数据全已补齐 |
| 既有测试和实际执行记录 | 断言保护的边界、对应环境的结果 | 未覆盖的崩溃窗口、质量或人工接受 |
| CI、镜像和部署证据 | 指定 SHA 的检查或运行身份 | 页面流程可用、用户接受内容 |
| 人工/设备/业务验收 | 明确版本、环境、样本上的观察 | 其他版本和全部流量同样成立 |

本仓库源码/契约使用相对链接；跨仓库链接固定 commit，指出谁拥有规则。正式正文不依赖个人机器绝对路径。文档校验不联网确认远程链接，引用者核对固定版本和实际内容。AI 不复制 IAM 的身份权威或 QS 的报告权威。

## 一篇正文的内容标准

开篇先说本文解决什么问题和当前规则，随后用一份合成请求或变更串起具体身份。示例 ID、状态、版本注明前提，不当作实际验收记录。真实字段与版本保留原名称，中文解释其业务含义。

每篇重要正文需回答以下问题，标题可按主题调整：

1. 谁发起、谁授权、资源由谁拥有？AI Profile 与 IAM Profile 是否容易混淆？
2. 创建哪些对象、怎样关联？哪些身份在重投、接手、Retry 中保留或变化？
3. 正常路径如何推进？原事务、派发、响应证据、Broker 与业务接收在哪里分界？
4. 提交前后超时分别意味着什么？CAS、旧 owner、取消和 unknown 如何处理？
5. 当前方案解决哪个窗口、接受什么代价？替代方案需要补哪些责任？
6. 哪条源码/测试支持结论？还有哪些运行或业务验收缺口？

“有幂等、有重试、有校验”不足以解释设计。写成可判断的规则：原 command UUID/正文一致读取首回执；Review 无 command receipt，成功后旧 Run version 再提交会冲突；响应 unknown 不自动补发。阈值、错误状态、摘要算法或 SQL 仅在帮助判断时展开。

机械保证与质量判断分开。Schema 合法和引用存在不证明内容确实源自标准报告；semantic judge 不替代双职责审核；Stored ACK 不证明页面已读或用户已接受。没有历史动机证据时，决策记录明示理由来自当前约束分析。

## 单一事实归属

| 正文位置 | 负责讲透的事实 |
| --- | --- |
| `00-总览` | 系统边界、对象关系、双链与代码/证据地图 |
| `01-运行时` | 装配、作用域、调度和进程关闭 |
| `02-业务模块` | 输入/成果、资产准备、评测审核、发布指针 |
| `03-基础设施` | 事务、恢复、消息确认、模型适配、容量、观测 |
| `04-接口与运维` | 调用方合同、操作步骤、停止条件与读回 |
| `05-决策记录` | 现行选择、替代责任、代价和重新决策条件 |

同一规则在所属正文展开，其余位置保留必要摘要和链接。例如运维引用 unknown 的设计，再给查询、确认、停止和应用顺序，不能另造自动重试语义。文档目录不创造领域上下文。

proto、Schema、锁文件、配置、资产和部署脚本继续由原目录拥有。修改机器规则同步解释；写文档不另存可执行定义。接口示例核对严格 JSON、optional 字段和返回 DTO，区分缺字段与显式 `false`。

## 闭包登记和实际验证

[document-closure.json](document-closure.json) 是复核索引。现行文章登记 path、owner、sources、review_scope、verify；source_catalog 保存来源文件 SHA-256。公共来源提交与逐篇复核范围一起判断，不能只看日期。

- 文档状态：`aligned`、`needs_review`、`drifted`、`planned`。
- 实现状态：`implemented`、`partial`、`planned`、`not_applicable`。
- 运行状态：当前闭包的 `runtime_status` 固定为 `unknown`；检查器拒绝其他值。环境绑定的部署、业务和人工结论另存日期证据，不把测试结果升级为运行验收。

`aligned + partial` 表示准确说明部分实现。source 摘要变化须沿影响规则重新阅读、修正文档、选择验证，禁止只更新 hash 绕过复核。新增文章登记归属及导航。

verify 写实际方法、依赖来源和局限。替身测试、MySQL 集成、真实 MQ/mTLS、供应商、人工验收分别记录。缺依赖或沙箱监听失败是未完成，不能算通过；重叠测试批次不相加。执行记录放闭包或日期证据，长期正文解释测试保护的行为与所需环境。

从仓库根目录执行基础检查：

```sh
uv run python scripts/check_docs.py
uv run pytest -q tests/test_docs.py
```

涉及契约生成关系时再运行对应检查：

```sh
uv run python scripts/generate_qs_proto.py --check
uv run python scripts/generate_workflow_proto.py --check
uv run python scripts/generate_messaging_proto.py --check
```

检查保护本地链接/锚点、覆盖、来源摘要、归档字节和部分关键事实；不理解全部自然语言，不证明全部接口行为。按主题选择有意义的既有测试。仅改说明不需要启动生产、真实模型、清库或破坏性故障实验。

## 历史与未完成项

`evidence/` 保存日期、完整版本、环境、方法、结果与局限；`_plans/` 保存未实施方案及验收缺口；`_archive/` 保留原始历史。去向登记在 [migration-map.json](migration-map.json)，原字节由归档摘要保护。

移动前明确继承正文和未完成项去向。归档不刷新历史日期/结论，不代表业务退役、清库或验收关闭；仍支持的旧版本须在兼容正文中保留。正文可回链历史缘由，当前行为必须核对实际代码。
