这里从持久记录解释系统怎样防止覆盖、重复执行和错误确认。第一次修改存储或执行实现，先读持久化，再按外部模型或消息的故障窗口进入恢复与交付；调整吞吐则从并发篇开始。

| 正文 | 读完应能回答的问题 |
| --- | --- |

| [执行所有权、调用回执与恢复](execution-recovery/README.md) | 接手 Job/Claim 后能继续哪一步？发送已提交而响应未存时为什么保留 unknown？原响应怎样重建成果？取消、替代授权和语义契约恢复分别保留什么？ |
| [消息接单、Outbox 与业务确认](messaging/README.md) | Inbox 如何保留首接单决定？业务状态和事件怎样一起提交？Relay 的失败预算如何分开？Broker PUB、订阅 ACK 与 QS STORED 各改变哪份记录？ |

| [业务额度、执行所有权与模型容量](concurrency/README.md) | 日额度、活跃槽、预算、lease/fence、candidate Claim 与本地 Provider 容量分别约束什么？锁序和版本怎样处理跨实例竞争与乱序完成？ |

## 按故障或改动选择路线

| 当前问题 | 推荐路线 |
| --- | --- |
| 新增表、事务或借用 SDK 适配器 | 持久化 → [资源所有权](../01-运行时/02-Dishka作用域与资源所有权.md) → 消息篇的原事务边界 |
| 超时后不知模型是否执行，或原响应尚未形成成果 | 执行恢复 → 模型网关 → [受控恢复操作](../04-接口与运维/06-排障与受控恢复.md) |
| 重复事件、等待业务 ACK，或 AI complete 而 QS 无结果 | 消息 → [QS 接入与接收契约](../04-接口与运维/02-QS接入与消息契约.md) → [排障](../04-接口与运维/06-排障与受控恢复.md) |
| 扩实例、增加 consumer 或调整候选并发 | 并发 → [后台调度](../01-运行时/03-后台执行与调度.md)，分别核对共享持久容量和进程内容量 |
| 指标异常、诊断过期或证据缺失 | 可观测性 → 对应业务记录；需要现场查询时转排障篇 |

本层维护机制与不变量；记录的业务含义由 [业务模块](../02-业务模块/README.md) 维护，循环和关闭顺序由 [运行时](../01-运行时/README.md) 维护，现场操作由 [接口与运维](../04-接口与运维/README.md) 维护。每篇分别注明源码、测试与环境证据的证明范围。
