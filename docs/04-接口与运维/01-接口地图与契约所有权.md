# 接口地图与契约所有权

qs-ai 的接单通道、治理通道、结果通道承担不同承诺。参与者请求由 QS 当前授权并冻结标准报告，再从 MQ 接单；能力预检和治理读取仍用内部 mTLS gRPC；成果经原事件及 QS 持久接收事务确认。浏览器或小程序不直接调用 qs-ai，也不能把旧 proto 中仍存在的方法当成当前可写入口。

例如页面提交一次报告解读：QS 返回202只证明自己的命令已经持久接受，随后命令回执证明 AI 受理或拒绝，成果事件再证明执行结果。一次 CheckEligibility available、旧 Commands.Start 的 proto 声明、或者 Broker PUB OK，都不能替代这三个节点。具体参与者请求例见 [QS接入与消息契约](02-QS接入与消息契约.md)。

本文核对未变业务源码 `766b2aa`、QS `2ccc2de44`，日期为2026-10-06。接口语义以声明、实际注册、身份校验、用例及原接收事务共同为准；本篇不推断当前部署开关或客户端呈现。

## 先按调用方找入口

| 调用方与方向 | 实际通道和用途 | 接受或返回的对象 | 所属边界 |
| --- | --- | --- | --- |
| 参与者 → QS collection → QS apiserver | QS HTTP来源/提交/操作对账/结果读取，内部参与者gRPC委托 | QS当前报告、原request/operation与公开结果DTO | IAM身份关系与QS资源权限在这里核验；客户端不提交任意事实快照 |
| QS → AI执行 | qs.ai.commands.v1 MQ | Start、Change、ParticipantRetry、EvaluationStart/Cancel的MessagingBody | 命令首决定与业务效果由AI原接单事务提交 |
| QS → AI预检 | Commands.CheckEligibility mTLS gRPC | EligibilityQuery → available/unavailable原因 | 只读、无额度预留、无Session/Job，实际提交重新检查 |
| QS → AI治理/诊断 | 受信scope的内部gRPC | 方案、资产、评测、发布、配额及运行投影 | QS当前capability先行，AI核对组织/操作者/CAS与业务规则 |
| AI → QS结果 | qs.ai.events.v1 MQ | CommandReceipt、InterpretationState、EvaluationState | 原事件幂等接收/投影/ACK Outbox同QS事务提交 |
| QS → AI业务确认 | qs.ai.acks.v1 MQ | 精确EventAcknowledgement | STORED是QS原事件持久接受；不是用户验收 |
| AI → QS当前访问核验 | AIWorkflowAccessService.Authorize mTLS gRPC | 原Actor/Testee/assessment集合 | 执行前与成果接受前核对当前授权，不向IAM直接取用户权限 |
| 双向大载荷读取 | MessagePayloads.Get mTLS gRPC | 原producer/destination/message_id/body hash/length/org reference | 读取原Outbox正文，无任意URL，无模型调用 |
| 运维 → AI HTTP | /healthz、/readyz、/metrics | 当前进程/数据库与固定聚合观测 | 无独立用户业务会话API；指标不是单报告成功证明 |
| AI →供应商 | 冻结Route的模型HTTPS | stage消息/Schema → ModelResponse | 一次协议调用、原身份与失败分类；接单和质量批准不归网关 |

MQ机制见 [可靠消息](../03-基础设施/messaging/README.md)，健康与指标口径见 [观测](../03-基础设施/observability/README.md)，供应商差异见 [模型网关](../03-基础设施/model-gateway/README.md)。

## proto 声明与运行时注册分别看

qs-ai持有 [workflow.proto](../../integrations/workflow/proto/workflow.proto) 与 [messaging.proto](../../integrations/workflow/proto/messaging.proto)，均使用 `qsai.workflow.v1` package。当前 [create_grpc_server](../../src/qs_ai/bootstrap/grpc_server.py) 始终注册Commands；宿主传入payload service时注册MessagePayloads；`grpc.governance_enabled=true` 才注册下表治理服务。关闭注册不撤销已经持久接受的任务，也不恢复旧执行写路径。

| 服务组 | 当前方法及职责 | 常见错误理解 |
| --- | --- | --- |
| SolutionManagement | List/Get/GetReceipt/GetModels；Create/Save/Prepare | Prepare原子冻结整套资产并创建requested Run，不直接生成或发布 |
| PromptDraftManagement / SemanticPromptDrafts | 源生成、版本化编辑、校验/冻结、原回执 | editable版本与不可变资产分开；冻结不等于评测批准 |
| ProfileManagement / SuiteManagement | 注册固定资产和生命周期/原注册回执 | Suite派生不继承原Run批准，Profile不是IAM用户Profile |
| AssetCatalog | List/Get/References共享定义 | 不返回私人原命令回执，也不表示asset正在线上active |
| EvaluationManagement | Prepare预览、Create、状态/容量/候选/原执行读取、Review/PreviewGates/Finalize/Reopen/unknown处置 | Finalize只固定评测approved/rejected，Publish是后续独立动作 |
| PublicationManagement | Publish/Rollback/Disable、当前状态、原命令回执与历史 | 全局selector指针变更不修改原Session绑定，rollback建立新指针版本 |
| ParticipantManagement | GetCapacity/GetExecution/GetRetryReceipt | Retry执行写入口已转MQ；读取不会自动恢复任务 |
| QuotaManagement | Status/Get/History/GetReceipt、Update/Rollback | 额度修订不是Run版本，也不释放原日预留 |
| RuntimeManagement / FlowManagement | 当前组织运行摘要、单/批投影、方案/发布流程视图 | 读取投影不构成调度、授权或业务验收 |

保留声明的五个执行方法为 Commands.Start/Change、ParticipantManagement.Retry、EvaluationManagement.Start/Cancel。[MQExecutionCutover](../../src/qs_ai/transport/grpc/mq_cutover.py) 在业务handler前拒绝，对应方法自身也调用reject_execution：不可信工作负载先PERMISSION_DENIED，可信QS为FAILED_PRECONDITION，固定详情 `MQ admission required; gRPC execution command not accepted`。配置开关不能使它们重新写入。

Results.Accept属于旧反向结果协议，不在AI server注册；QS仍保留 [Receiver注册](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/apiserver/transport/grpc/aibridge/results.go)供兼容明确拒绝。QS先验证qs-ai.svc客户端证书，再返回FailedPrecondition `result delivery requires MQ`，不会调用旧Service保存成果。不要把生成代码中的stub当作可用投递器。

## 工作负载、组织scope、关联ID不能互相代替

AI gRPC使用双向TLS，服务端要求客户端证书；[require_qs_workload](../../src/qs_ai/transport/grpc/identity.py) 进一步要求auth_context的transport_security_type=ssl、x509_common_name恰为qs-apiserver.svc，在REQUEST scope打开前执行。签发可信证书只是第一层，治理请求内组织/操作者仍须合法并与原资源一致。

QS从人类登录、当前ProfileLink/Testee或管理员capability判断访问权。参与者委托的purpose绑定发生在collection→apiserver；AI治理scope不携带这一参与者token，也不重新验证它。不能把一个浏览器自报的organization_id/operator_user_id包装成“可信scope”。具体调用方责任见 [治理接口](03-治理接口与可信委托.md)。

x-correlation-id只关联诊断，不授权；request_id、command_id、RunID、event_id、invocation_id、artifact_id各有独立作用。稳定UUID幂等也不等于所有写方法都接受command_id：评测Review/Finalize/Reopen/Resolve以Run版本CAS为主，Create复用稳定RunID，带首回执的方案/发布命令另按原command作用域重放。超时后选择哪种查询要按该原方法的契约，不能统一“换UUID再试”。

| 材料 | 权威来源与本地检查 | 变更必须保留的关联 |
| --- | --- | --- |

| QS报告/授权proto镜像 | [manifest](../../integrations/qs_server/manifest.json)固定QS提交1ce436d7…及两文件SHA | 仅这份probe/AIWorkflowAccess镜像，不等于最新QS完整参与者API |
| 标准报告快照 | QS从原Report+Outcome生成；AI严格校验source和版本 | report_id、content_schema/outcome组成的source_version、模型/四轴事实；不能从展示叙述猜新字段 |
| 量表input/output v1 Schema | [schemas manifest](../../integrations/qs_server/schemas/manifest.json)固定QS1b52081e…源与摘要 | 原完整Schema与Python额外业务校验；旧Go对照并非所有原字节完全相等 |
| MBTI input v2/v3、reference/Profile、output v2 | 原MBTI/三主题manifest及retained-assets保存身份；output v2权威为QS固定Schema | source事实、Profile场景、材料、输入/输出/Artifact版本显式组合；v1 manifest不覆盖v2 |

| 表结构与消息SDKmetadata | [Alembic账本](../../migrations/versions/)、0037/0038显式DDL与固定SDK | 同事务所有权、UTC迁移覆盖与不可删原证据；不是运行时自动修表 |

QS最新参与者protobuf字段比AI锁定probe镜像更完整是允许的：AI外呼只用镜像里已有的当前授权方法；三主题公开读取由QS自己的新proto/DTO承接。不要为“看起来一致”无审核覆盖vendored文件或更新manifest到未核证的最新提交。

Python生成入口可在已锁定依赖环境只做检查：

```bash
python scripts/generate_workflow_proto.py --check
python scripts/generate_messaging_proto.py --check
python scripts/generate_qs_proto.py --check
python scripts/check_docs.py
```

这些命令的前提是仓库锁定的Python/grpc_tools依赖。不带 --check会改生成代码，应作为协议变更提交并核验消费者。MQ生成器只在临时输入里把Go import root改为workflow.proto，保留既有Python descriptor名称；不能手改共享proto import来“修复”双语言生成。

本地check只证明当前proto/工具链/生成物相符。QS同步副本、Go/Python互操作、数据库原接收及运行版本各需独立验证；文档链接、wheel存在、CI配置存在都不代表该验证已在本次环境完成。

## 字段兼容还包括业务含义

optional bool的absent与false不同。例如Finalize.expected_passed必须显式存在，false表示确认复算拒绝；Cancel.discard的缺席不能被客户端强行当作true。oneof消息正文必须与MessagingKind一致，未知枚举不能变成默认Start；字符串status/schema_version也必须按消费者支持集合判定，不默认成功。

返回中的JSON字段也有明确边界。SolutionResponse.data_json、candidate evidence_json等是版本化对象，不是自由日志；客户端应核对内部schema_version、组织/资源与指纹。normalized_output是原验证字节，不宜当作可写草稿。Artifact.content_json hash覆盖实际字符串字节，参考材料hash另算；解析再编码后的“相同对象”不能拿来替原字节摘要确认。

QS公开 [WorkflowResult](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/collection-server/port/aiexplanation/workflow.go) 只暴露request/status/version/content、artifact/report/source与可选reference_material，不直接透出内部Artifact、模型调用、活跃Run或所有failure_code。运维需要的内部事实走当前授权的管理读取，不临时扩大参与者DTO。

协议升级应按“生产者字节→消费者解析→原事务接收→回执→原请求读取”核证。新消费者可以支持旧记录，但不能把旧记录改成新身份；新生产者使用新格式前，先确认目标消费者能按该格式保存和确认。原命令超时/未知按原身份对账，不将不确定结果升级成成功。
