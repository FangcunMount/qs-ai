# 排障与受控恢复

页面一直等待时，先找原请求和原命令，确认停在“QS 已提交”“AI 已接单”“模型已调用”“成果已接受”还是“QS 已存结果”。这几个节点分别落在不同事务里；重启服务、再次点击或换一个 command_id，不能补齐原操作的证据，反而可能创建第二份付费工作。

本文按实际查询入口说明如何取证、哪些动作可以明确授权，以及动作后该读回什么。QS 路由与查询结构按 `2ccc2de44bbd45e26d29e7e130da518cc32426f0` 核对。这里只给操作契约和示例，不据源码、健康探针或测试推断当前生产故障、部署状态或真实内容合格。

## 先取得原身份，再解释状态

先从原页面返回、原操作记录或已保存回执取得 request_id / command_id。对解读，再关联 Session、当前及原 Run、invocation；对评测，关联 Run、case/slot/candidate、execution；对消息，关联 producer/destination/message_id、body hash 与首次 wire hash。correlation_id 只串联某次通信尝试，不是业务幂等键。

QS 查询由当前登录用户的受保护组织/操作人上下文授权，不能在请求体填组织或用户冒充。普通排障优先走 QS 管理入口；内部 AI RPC 只接受受信 QS mTLS 工作负载。目标权限见 [治理接口与可信委托](03-治理接口与可信委托.md)。

以下 QS 地址均省略共同前缀 `/internal/v2/interpretation/ai-workflow`：

| 手上已有的身份 | 只读入口 | 首先保存的结果 |
| --- | --- | --- |
| 原执行写 command_id | `GET /operations/{command_id}` | operation_id、status、transport_status、decision/code、resource_id、receipt |
| 原 request_id | `GET /runtime/requests/{request_id}`；需要时间线再读末尾 `/timeline` | QS request 投影、AI availability/partial、各自 observed_at、AI 详情 |
| 只有报告、用户或 Session 线索 | `GET /runtime/requests?request_id=…` 或 session_id / assessment_id / testee_id / subject_id 筛选 | 原 request/session 关联、commands_pending、分页游标；不能以一页未出现判不存在 |
| 已知解读 Session | `GET /participants/{session_id}` | 当前 Run/version、failure_code、model_call_status、invocation、can_retry、unknown_result_risk |
| 原参与者 retry command_id | `GET /participants/retry-commands/{command_id}` | 原重试 Receipt；当前参与者权限仍会核验 |
| 原评测 Run | `GET /evaluations/{run_id}` | 当前 version/status、execution_mode、active_call_count、cancel_draining、原创建/取消/最终记录 |
| 评测已排空且当前版本已知 | `GET /evaluations/{run_id}/executions?expected_version=…` | 原 execution/invocation、阶段、ordinal、完成状态、正文长度和 evidence_json |
| 某条已完成评测执行 | `GET /evaluations/{run_id}/executions/{execution_id}/output?expected_version=…` | 原 raw/normalized 字节及各自 SHA-256，不是重新生成结果 |
| 未处置评测 unknown | `GET /evaluations/{run_id}/result-unknown?expected_version=…` | 原调用失败、目标/阶段已用预算、replacement_allowed 快照提示 |

路由依据为 QS [routes_interpretation.go](https://github.com/FangcunMount/qs-server/blob/2ccc2de44bbd45e26d29e7e130da518cc32426f0/internal/apiserver/transport/rest/routes_interpretation.go)。Runtime 和 participant 查询要求 OrgAdmin；评测读取要求解读审计能力，修改要求 OrgAdmin。操作查询还绑定原操作人的 scope，不是任意管理员跨人检索原 command_id 的通道。

AI 对应的只读 RPC 是 `RuntimeManagement/BatchGet、Get、Health`、`ParticipantManagement/GetExecution、GetRetryReceipt`、`EvaluationManagement/Get、ListExecutions、GetExecutionOutput、ListUnknownExecutions`。Runtime BatchGet 要求 1–50 个不重复规范 Session UUID，Get 恰好一个；Runtime Health 只接收 scope，不接 Session 列表。完整字段见 [runtime.py](../../src/qs_ai/transport/grpc/runtime.py)、[participant.py](../../src/qs_ai/transport/grpc/participant.py)、[evaluation.py](../../src/qs_ai/transport/grpc/evaluation.py)。

### 查询返回不完整时怎样读

QS Runtime 先读 QS 数据，再向 AI 读另一份快照，二者不是同一个跨库事务。`partial=true / ai_availability=unavailable` 表示 AI 详情未取得，已有 QS request 仍有效；不能把它解释成 AI 从未接单。列表没有 Session 时可以 `not_requested`，不代表 AI 健康或故障。

AI Runtime 在组织内读取一致性只读快照，明示 observed_at。详情最多返回 100 个 Run 尝试、100 个投递、300 个里程碑，另有各类 truncated 标记；`history_complete` 固定 false，旧里程碑可能不存在。Runtime 不读取报告、Prompt 和模型正文。旧 ModelCall 时间没有记录时区时标为 `legacy_timezone_unrecorded`，不能按今天数据库时区猜转换；历史时间边界见 [持久化](../03-基础设施/persistence/README.md)。

评测查询要求精确 expected_version，版本冲突先重新读取当前 Run，再核对原执行，不能只递增数字重试。候选模式活动 dispatch 尚无 completion 时，现行诊断实现只用全局 checkpoint 验证缺失完成证据，尚未用 slot claim 展示该窗口，可能返回 ABORTED；先读 active_call_count，待正常完成或到期恢复排空后再查原执行。这种读取限制不能证明调用没发送。unknown 查询也明确拒绝未排空的 checkpoint/claims。

## 症状一：启动失败或探针异常

没有监听成功时 HTTP 探针自然不可用，先定位 [启动装配](../01-运行时/01-单进程架构与启动装配.md)中的失败阶段。坏 gRPC TLS 在创建资源前拒绝；旧 Alembic head、缺消息观测结构等在各自预检阶段拒绝；部分组件启动后失败则由装配器清理已取得资源。不能以“关掉 MQ 后启动成功”证明原系统恢复，因为五个执行写入口已要求 MQ 准入。

在目标镜像、同一数据库配置环境中，现有数据库检查只读，不执行迁移：

```sh
python -m qs_ai.bootstrap.database_check --require-head
```

它比较镜像的 exact Alembic heads、当前 heads 和 MySQL 兼容性，成功输出 current/expected/mysql_version；失败仅输出安全类别/驱动代码。成功不替代 MQ 结构、证书或业务资产检查，见 [database_check](../../src/qs_ai/bootstrap/database_check.py)。JOSE 文件单独预检入口为 `python -m qs_ai.maintenance.messaging_preflight`，读取实际 QS_AI_MESSAGING 配置；它只检文件/密钥，不连接数据库、Broker 或模型。配置未启用 MQ 时也会完成，不能把这个输出当作 MQ 已启用。

服务已监听后分别读探针：

| 结果 | 可以据以判断 | 下一项针对性核对 |
| --- | --- | --- |
| healthz 503 | 运行器未被判 healthy | 原组件状态和对应失败事件 |
| healthz 200，readyz 503 | 健康与 readiness 不同；数据库或生命周期条件未满足 | readyz.database、Runtime Health.components、是否正在启动/关闭 |
| 两者 200 | 当前运行器及 readiness 条件成立 | 仍须查原操作/成果/业务 ACK，不据此宣称模型、发布或投递合格 |
| metrics 的 database_up=0 | 整份数据库指标快照采集失败 | 采集依赖/时限；积压项缺失不能当零 |

healthz 不检查数据库；readyz 组合数据库只读检查与 runtime.ready/healthy，禁用组件有独立状态。接口本身不验证所有 frozen assets 或供应商。探针实现见 [health.py](../../src/qs_ai/transport/http/health.py)，关闭时的可用窗口见 [生命周期](../01-运行时/04-生命周期与优雅关闭.md)。

## 症状二：提交后等待、超时或“MQ required”

QS 对新的执行写返回 HTTP 202、`status=submitted` 和 status_url，只证明 QS 原提交事务保存了命令与 Outbox，不是 AI 准入 Receipt。沿返回的同一个 status_url 读取：transport_status 是消息交接状态，decision/code/receipt 才描述 AI 对原命令的决定。即使 Broker 已确认，命令也可能仍 submitted。

AI 的兼容 `Commands/Start、Change`、`ParticipantManagement/Retry`、`EvaluationManagement/Start、Cancel` 五个 gRPC 方法经受信工作负载校验后固定返回 `FAILED_PRECONDITION: MQ admission required; gRPC execution command not accepted`。这是调用路径退役，不是模型故障；查询和治理准备接口继续保留，见 [mq_cutover](../../src/qs_ai/transport/grpc/mq_cutover.py)。换证书、直挂 servicer 或多次 RPC 重试不能解决它。

如果原 operation submitted、awaiting_receipt 或 held，保留原 command_id、首次消息身份和 body/wire 摘要，核对 QS Outbox、AI Inbox/command receipt、技术失败记录。此时还没有 AI Session 也可能正常：原命令在途，Runtime Session 查询不是替代 command receipt 的办法。取得明确 rejected 决定后，再按拒绝原因制定新操作；没有回执时不要另造 command_id 触发一份相同收费任务。

修改操作返回 UNAVAILABLE 或网络超时时，结果可能已经提交。MQ 执行写回查原 operation；publication、Profile 等治理写回查各自原 GetReceipt。404 可能来自 scope、原命令尚在途或尚无该类业务回执，不足以证明原操作没有效果。ABORTED 表示版本/状态冲突；重新读取和重新授权当前意图，不能把它当自动重试信号。接口边界见 [QS 接入与消息契约](02-QS接入与消息契约.md)。

## 症状三：生成 blocked，选择恢复还是新 Run

对原 Session 读取 participant 详情，并用 Runtime 的 attempts/milestones/deliveries 交叉核对。以下“可恢复”都指原配置可验证、当前参与者权限仍满足、执行组件和容量条件已恢复，不能只凭 failure_code 一项跳过其他条件。

| 持久事实 | 先确认什么 | 可授权的动作及回读 |
| --- | --- | --- |
| 准入即拒绝，无接受配置/Job/ModelCall | 原准入 Receipt、publication/额度/报告适用性具体原因 | 修正后另行明确发起新请求；Participant Retry 不能绑定后来配置补救这次拒绝 |
| queued/running，原 Job Lease 已过期 | 当前 active Run/版本、Job attempt/fence、原调用有无响应 | 正常 worker 重新 claim；观察新的 execution_claimed 及终态，不手工清租约 |
| response_received，Job 仍在可接手状态，成果事务尚未提交 | 原 request/response 与接受配置完整，校验/授权/事务故障原因 | 同一 Run 接手后本地重建；核证原 invocation 未变、Artifact 和状态事件同事务提交 |
| dispatched/unknown，缺原响应 | 原调用可能已经执行；未取得供应商结果 | 保留 provider_result_unknown；若批准重新收费，走显式 Participant Retry 新 Run |
| 明确 failed 或 attempts_exhausted | 原失败类型、现行 Retry 资格、额度、接受配置、参与者当前访问权 | 可显式批准一个新 Run；原失败/调用记录保留 |
| access_revoked 或固定资产损坏 | 当前授权或原资产的真正缺口 | 补齐合法前提再决定；不能以原快照合法或新 active 资产代替 |

已 blocked 且 Job done 的内容校验失败不能冒充“成果事务尚未提交”；response_received 只证明原响应保存了，不单独授权接手或 complete。`can_retry=true`、Runtime action.available 或 `new_model_calls=1` 是查询时的资格与费用提示，提交事务仍重查。Participant Retry 要求 stable command_id、expected_run_id/version、原因、confirm、expected_provider_invocations=1；unknown 时额外接受重复执行/收费风险。下面是合成字段示例，须由实际查询结果和明确的新重试授权替换，不是可直接用于生产的命令：

```json
{
  "command_id": "00000000-0000-4000-8000-000000000020",
  "expected_run_id": "00000000-0000-4000-8000-000000000010",
  "expected_version": 8,
  "reason": "已核对原未知调用，批准在原配置下新增一次解读执行",
  "confirm": true,
  "expected_provider_invocations": 1,
  "accept_result_unknown_risk": true
}
```

该 body 进入 QS `POST /participants/{session_id}/retry`，当前路径返回 202 operation，最终由 MQ 准入。保存原 command_id 查 operation，再读 GetRetryReceipt 与 Session 当前 Run；核证新 Run 已创建、source_run_id 指原 Run、原 ModelCall 未被覆盖，并继续跟踪新结果。重试超时不能生成另一个 command_id。机制与旧 Job 恢复的差异见 [执行恢复](../03-基础设施/execution-recovery/README.md)。

## 症状四：评测 blocked 或 cancel_draining

先读 Run 当前版本、创建回执/冻结 release、状态与活动数量。完成证据按执行列表定位，再按 execution_id 读取原正文；列表故意只给正文长度和证据，不能拿它做完整内容审查。取出的原 raw/normalized 字节有独立摘要，候选 normalized fingerprint 和裁判 output fingerprint 用途不同。

若原 dispatch 已过期，先让相应恢复路径接受原回执或写 unknown，不直接从活动执行跳进人工处置。candidate 有独立 response receipt，可以在投影崩溃后本地重建；旧 serial 没有这个独立提交窗口，缺完成证据只能保守 unknown。具体证据条件见 [执行恢复](../03-基础设施/execution-recovery/README.md)。

unknown 排空后，用当前版本读 result-unknown 清单，保存原 execution/invocation、失败、目标/阶段预算与 replacement_allowed。管理员可选择 `authorize_replacement` 或 `cancel_run`，向同步治理 `POST /evaluations/{run_id}/result-unknown/resolve` 提交 expected_version、execution_id、decision、reason、confirm 和 acknowledged_duplicate_call_and_cost_risk。AI 根据原执行重新核验，原 unknown 不会改为成功。替代提示也不保证整轮预算、容量或实际新调用成功。

处置后重新读 Run 与 resolutions，核证原执行仍为 result_unknown、本次审计只指向它。新执行若发生，应有新 ordinal/execution/invocation；还有其他 unknown 时保持 blocked。已有 cancel_requested 时，授权消除 unknown 不清掉取消意图，排空后完成 canceled，不据此启动新替代调用。cancel_run 也不证明供应商调用已撤销；若取消意图存在且还有其他未知，不能提前完成。

cancel_draining 表示持久取消意图，检查原 checkpoint/claims 和未解决数量。Cancel 经 QS MQ 提交，202 仍不是 canceled；回查原 operation 和 Run，只有 active_call_count=0、无活动 checkpoint、unknown 已处理并保存最终取消记录，才核证结束。awaiting_review 主动废弃要求 discard，与在途排空不同。

如果阻塞恰为 semantic_recovery_not_allowed、原明确失败为 semantic_decision_contract_invalid，转 [语义契约故障恢复](07-语义契约故障恢复.md)。未知调用、裁判对质量判 failed、预算耗尽或人工审核未通过不能使用该维护命令。最终 gates 不通过应读取原候选、断言、审核与冻结门槛，不删失败、改分数或伪造批准。

## 症状五：AI complete，QS 仍看不到结果

先绑定原 request/session 与 StateEvent：AI Runtime.deliveries 只显示 legacy interpretation_result_outbox 的摘要，不完整展示 MQ Outbox、Inbox 或技术失败；不能把 legacy attempts 当现行 MQ 投递预算。在受信维护主机可用独立只读盘点：

```sh
python -m qs_ai.maintenance.messaging_audit --max-rows 1000
```

需要明确配置原数据库 `QS_AI_MESSAGING_AUDIT_DATABASE_URL`。它在一致性只读快照中列 legacy interpretation_result_outbox、MQ Outbox/Inbox/quarantine 和模型/评测账本元数据，检查 body/wire 保存摘要是否匹配；不解密 JWE，不调用模型或 Broker，不授权恢复。缺表/字段或截断会 complete=false，退出码 2；失败退出码 1，不能推断空库或无积压。数据库名、schema heads 和 source_sha 用于核对目标，环境提供的 source_sha 仍须与实际镜像确认，见 [messaging_audit](../../src/qs_ai/maintenance/messaging_audit.py)。

| 看到的事件状态 | 下一项原身份取证 | 合法动作边界 |
| --- | --- | --- |
| staged / awaiting_receipt | 原 message_id/body hash/wire、available_at、排序前驱、QS Inbox/ACK | 正常 Relay 按原 wire 重投或等待 ACK；不是重新生成 |
| held | error_code、八次技术预算或 receiver_held、原失败记录 | 找具体故障与受控处置入口；当前没有万能 unhold/retry RPC |
| Broker PUB 已确认 | QS 原事件是否 STORED、业务 ACK 是否持久并回到 AI | Broker 确认不能置 legacy delivered |
| AI confirmed 且 legacy delivered | 原 ACK 必须匹配 event ID/kind/aggregate/body hash | 证明原交接结算；页面权限、读取和展示仍另核证 |
| 历史 legacy 未交付且 mq_owned=false | 原事件/source snapshot、旧发送者状态、首次 wire 有无 | 只适用经审阅的 legacy handoff；不会重置模型或消息预算 |

历史交接有只读 dry-run，可针对 1–20 个原 event ID：

```sh
python -m qs_ai.maintenance.messaging_handoff \
  --action dry-run --event-id '<原 event ID>'
```

它使用独立 `QS_AI_MESSAGING_HANDOFF_DATABASE_URL`，要求兼容 schema，返回原数据库/行快照与 manifest digest；不是消息重投或业务 ACK。apply 需要另行明确授权、审阅 manifest/digest、停 claimers/关闭准入的确认以及原密钥文件。逐行提交可能出现 partial/commit_unknown，必须核对原行再续做，不重新造 event ID；已交付或已移交记录不复活、首次 wire 不重封装。详细参数与前提见 [可靠消息](../03-基础设施/messaging/README.md)及 [messaging_handoff](../../src/qs_ai/maintenance/messaging_handoff.py)。

## 日志与指标只用于定位，不补造业务结论

结构化日志按 request/command/session/run/invocation/delivery_event_id 关联，阶段与 error_type/error_location 帮助定位；不得把模型正文、URL 凭据或任意驱动异常串塞入标识。日志丢弃/输出失败意味着诊断渠道存在缺口，不改变持久业务状态。实现见 [diagnostics](../../src/qs_ai/application/operations/diagnostics.py)。

`qs_ai_ready_jobs / expired_job_leases / pending_results` 是汇总积压；MQ 的 due_events 还包含到期 awaiting_receipt，不是已通过聚合排序的可发送数量。unresolved_model_calls 统计当前 unknown 或超过五分钟的 dispatched，与 Runtime Health 的 blocked 当前调用计数口径不同，均不是供应商查询结果。指标采集失败返回 database_up=0 / mq_observation_available=0 并省略积压值，不保留部分或旧值冒充本次完整快照；见 [metrics](../../src/qs_ai/infrastructure/persistence/mysql/metrics.py)和 [可观测性](../03-基础设施/observability/README.md)。

恢复后的证据应包含原身份、执行前后版本、实际授权/审计、原失败/回执保留和相应新状态。服务健康、单元测试通过、Broker PUB 成功、AI complete、QS STORED 与用户最终可读分别记录；不要把某一层验证扩大成下一层。

| 现有测试入口 | 直接核验范围 |
| --- | --- |
| [grpc_runtime](../../tests/test_grpc_runtime.py)、[runtime 集成](../../tests/integration/test_runtime.py) | 受信 scope、查询边界、有限详情、错误脱敏；不发模型 |
