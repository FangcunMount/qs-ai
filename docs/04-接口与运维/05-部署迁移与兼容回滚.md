# 部署迁移与兼容回滚

发布脚本把**已通过 main CI 的固定提交、准确镜像身份、原运行配置和目标数据库 heads**绑定起来，检查通过后才更新 current/previous。它不能把部署成功转换成质量批准或业务验收；镜像回滚也不能抹掉新版本已保存的 ModelCall、候选响应或 MQ 归属。

本文核对当前 `0040_module_table_names` 工作区的部署与存储转换边界，日期为 2026-10-08。以下生产命令用于已明确目标环境和版本的操作；本地隔离准备见 [配置与本地开发](04-配置与本地开发.md)，实际 Secret 与主机材料入口见 [serverA 部署](../../deploy/serverA/README.md)。

## 从哪个提交发布，先由 gate 决定

[`deploy.yml`](../../.github/workflows/deploy.yml) 有两种触发方式：手动 workflow_dispatch，或 main 的 checks 完成后 workflow_run。手动只能在 `refs/heads/main` 运行；自动要求检查成功、同一仓库，并且当前仓库变量 `AUTO_DEPLOY_ENABLED=true`。仓库文件里的条件不证明这个变量当前已开启。

两种触发都要有 40 位完整 SHA、该提交是 origin/main 的祖先，而且存在这个 SHA 对应的成功 **push** CI；PR 上一份成功检查不能替代这项 gate。手动 revision 留空采用工作流提交；rollback 的工作流 source SHA 也要通过 gate，但真正回退目标由服务器 state.json 的 previous 决定。

自动发布还用最新未过期 `qs-ai-deployed-*` artifact 提取已部署基线，经 [`deploy_scope.requires_deploy`](../../scripts/cd/deploy_scope.py) 比较基线到目标的变更。src/configs/migrations/integrations/deploy/scripts-cd、Dockerfile/依赖锁等触发发布，纯 docs 默认不触发；基线之前排队的旧自动运行不会把生产倒退。合并比较包含整段 runtime 变更，不能因 PR 最后一个 commit 只改文档而漏部署。artifact 是 gate 的历史输入，仍不是实时容器探针。

明确目标 SHA 后，手动入口为：

```sh
gh workflow run deploy.yml --ref main -f operation=deploy -f revision="$QS_AI_TARGET_REVISION"
gh workflow run deploy.yml --ref main -f operation=rollback
```

第一行的 `QS_AI_TARGET_REVISION` 应是已核对的完整 main SHA，第二行不能用 revision 指定任意回滚版本。提交操作后检查该次 workflow 的 gate、build、deploy 与部署回执；创建了 workflow run 不表示服务器已切换。工作流 concurrency group 固定为 qs-ai-serverA、`cancel-in-progress=false`，服务器另用文件锁防止与直接主机操作重叠。

## 镜像摘要、源 Image ID 和加载 Image ID 是三层身份

GitHub runner 按固定提交构建 linux/amd64 镜像，写入 `org.opencontainers.image.revision` 和 `QS_AI_RELEASE_SHA`，推 ACR 并得到 registry digest。qlume 组 ARM64 Mac mini runner 经 [`scripts/cd/deploy.py`](../../scripts/cd/deploy.py) 按 **registry@digest** 拉取，再导出镜像；运行它的机器架构不改变目标镜像架构。

| 身份或文件 | 绑定什么 | 校验入口 |
| --- | --- | --- |
| ACR digest | 注册表中这次构建产物 | 工作流 build 输出；打包按 digest pull |
| manifest 的 `image_id` / `image_identity` | 源 Docker daemon ID、归档原 config hash、完整 Config 指纹、rootfs layers、linux/amd64 与提交 label | `archive_identity`、`match_image`、`check_manifest_identity` |
| `archive_sha256` | 上传的 image.tar.gz 文件字节 | serverA 逐块算 hash，失败不 load、不迁移 |
| `loaded-image.json` | 源 ID/归档/digest 到 serverA 实际加载 ID 的绑定 | 加载后核验原 config/layers；完整回执不可覆盖 |
| `image.env` | Compose 实际使用的加载 ID | 成功绑定后改为 `QS_AI_IMAGE=sha256:…`，不继续靠可变 tag |
| live container `.Image` | 启动容器真正使用哪个 ID | verify 对每个服务检查，须等于固定加载 ID |

某些 containerd daemon 的 inspect ID 与原 config digest 不同，脚本不会只比较 ID 字符串或少数 Config 字段：它再次导出这个准确 loaded ID，核对原 config 与 layer 摘要，再接受等价身份。历史发布没有新回执时采用严格旧 ID 校验；不能凭“tag 还是同名”套用等价例外，见 [`deploy/serverA/deploy.py`](../../deploy/serverA/deploy.py)。

传输使用固定 serverA ed25519 主机公钥、StrictHostKeyChecking=yes、BatchMode=yes，并检查远端 hostname 为 servera。临时 registry auth、SSH 私钥及 known_hosts 放 runner 的私有临时目录；不依赖桌面 keychain，也不输出原驱动/Compose 错误正文。

## 运行配置和外部密钥要跟随哪份发布

每次发布建立 `/opt/qs-ai/releases/<sha>-<run_id>-<attempt>`，拒绝复用目录。runtime.json 保存本次数据库 URL、模型凭据和应用环境覆盖，权限600；它不能上传为普通日志或公开 artifact。manifest、loaded-image、verification 和 state 不含这些凭据。工作流 artifact 的 deployment-receipt.json 只记录实际 current 的 revision/release，所以 rollback 回执报告目标版本，而非工作流源版本。

[`runtime_config`](../../scripts/cd/deploy.py) 把工作流变量转换成应用嵌套变量。例如 EXECUTION_ENABLED → GENERATION__ENABLED，CANDIDATE_MODE_ENABLED → EVALUATION__CANDIDATE_MODE_ENABLED；布尔只接受字符串 true/false，并发范围1–32。Provider total 在这个部署路径至少为2，保留代码默认的一个 generation 槽；直接 Settings 的 total 参数范围与此入口不同。

模型阶段开启时，这个打包路径仍要求 HTTPS `QS_AI_MODEL_ENDPOINT` 与 DeepSeek 凭据，即使部署目录还包含智谱 binding；不能把宿主的“v2 binding 可执行”推断成部署脚本可以省略它们。智谱凭据独立传入，治理/模型 v2 写开关分别控制，新 Run candidate 模式不改旧 Run 的 stored mode。QS 地址始终必需，用于授权/正文读取；关闭生成不会关闭消息交接。

`QS_AI_MESSAGING_BINDING` 是受审阅的非秘密 JSON，包含 binding_revision、enabled=true、NSQD 映射、四种角色的路径/kid 与 max_in_flight=1。打包验证同主机 TCP→HTTP 映射、角色文件名、kid 和唯一字段；转为 `QS_AI_MESSAGING` 后，绑定摘要覆盖该 JSON 与只读单文件挂载列表。源路径固定在 `/data/infra/qs-ai-messaging/versions/<binding_revision>/`，目标为 `/run/qs-ai-jose/`，create_host_path=false。

**摘要保护的是绑定元数据，不是挂载文件的内容 hash。** key preflight 再检查文件、权限、kid、私/公角色、P-256、alg/use/key_ops；secret 原字节留在主机。TLS 源路径也是主机固定目录，不随 release 复制一份证书。回滚前应保留目标发布所需的 key 版本、TLS 信任和 historical ModelBinding；仅保留 runtime.json 不足以证明这些外部文件仍可用。不能在原 binding revision 下悄悄改连接语义。

## 主机 apply 的实际先后与停机边界

下面顺序来自 [`apply`](../../deploy/serverA/deploy.py)，不能按抽象“迁移、重启”省略中间保护：

1. 取得四仓共用 `/var/lib/fangcun-image-retention/deploy.lock` 与 `/opt/qs-ai/deploy.lock` 的非阻塞 flock。旧锁 inode 不删除或替换；共享锁初始化硬链接要求两个目录处于同一文件系统。
2. 校验 release 未被成功使用、MQ 归属转移允许、归档 hash/身份/提交/架构；load 后保存 loaded-image 绑定，并检查只有一个 qs-ai service。
3. 用目标镜像的临时维护容器做 JOSE key preflight、TLS 文件/私钥匹配预检、数据库 probe。临时容器不启动 server、不领取 Job、不调用模型；不因为 preflight 而并行启动第二个业务执行器。
4. 先比较当前和目标存储布局：0038/0040 的任一方向转换或0039中间态立即拒绝，使用 [模块表与双向迁移](09-模块数据表与双向迁移.md) 的停写维护入口。同布局的兼容迁移才写 verification phase=preflight，**在旧服务尚运行时**执行目标镜像 `alembic upgrade head`，再以 `database_check --require-head` 核对目标全部 heads。迁移失败或后检查失败不进入服务切换，但 MySQL DDL 可能已部分提交。
5. 停旧 release 并核对没有 running 容器，再启动新 release。历史多服务形态先 stop grpc/api 准入，再 stop 所有服务；统一 qs-ai 单进程收到 SIGTERM 后由 supervisor 撤 ready、停止新 attempt 并排空。新的执行器不能在旧执行器仍 running 时启动。
6. Compose up 使用 `--pull never --wait --wait-timeout 120`。核对每个容器 `.Image`，做 live mTLS probe，最后再跑目标镜像 exact-head probe。
7. 全部通过才写 verification phase=ready、state.current=新 release、state.previous=旧 current；删除大体积 image.tar.gz，保留加载镜像与发布材料，再尝试镜像保留助手。

脚本保证的是切换时执行器不重叠，**并未承诺迁移期间数据库停写**。当前链路需要迁移可兼容旧运行代码；若变更要求停写，应先设计并落实独立维护窗口，再使用相应发布方案，不能仅靠 `alembic upgrade` 的返回值宣称原子切换。MySQL DDL 也不是可随业务事务整体回滚的操作。

serverA Compose 的停止宽限210秒、生产 YAML evaluation 排空190秒；MQ publisher 等业务回执/失败移交 drain 后最后停止，HTTP在排空窗口返回不可就绪。宽限超时仍可能留下 leased/dispatching 等持久状态，重启由原租约与回执恢复，不按容器退出状态判断模型是否执行。详细过程见 [生命周期与关闭](../01-运行时/04-生命周期与优雅关闭.md)。

## 当前迁移明确保留哪些历史

本源码实际 Alembic head 为 `0040_module_table_names`；验收使用目标镜像自己的 ScriptDirectory 全部 heads，不能在脚本里永远硬编码这个值。

| 迁移 | 保存/增加的契约 | 升级不能被误读成什么 |
| --- | --- | --- |
| [`0035_runtime_utc_timestamps`](../../migrations/versions/0035_runtime_utc_timestamps.py) | Session created/updated UTC 与 ModelCall created UTC 的 nullable DATETIME(6) | 不推断或回填历史本地时区；NULL 保持未知 |
| [`0036_evaluation_slot_claims`](../../migrations/versions/0036_evaluation_slot_claims.py) | Run execution_mode 默认serial_v1、候选槽 Claims、独立响应回执及唯一 execution 约束 | 不把旧 Run 转成 candidate_v2，也不补造旧响应 |
| [`0037_workflow_messaging`](../../migrations/versions/0037_workflow_messaging.py) | 旧布局的宿主独立 MQ 表/索引及 result_outbox.mq_owned 默认0 | 不自动移交历史结果、不把 Broker 成功当 QS 已接收 |
| [`0038_messaging_observations`](../../migrations/versions/0038_messaging_observations.py) | 八类技术观察、计数0及各自安装 recording_since | 不回填历史完整性；运行启动还检查八类 seed 都存在 |
| `0039_data_consolidation`、`0040_module_table_names` | 五组合并、模块物理表名与完整可逆映射，最终44表 | 不通过普通生产部署原地转换；不改变原ID、正文、回执和恢复状态 |

这四份 downgrade 均显式拒绝删除契约。Alembic 的目标 metadata 不接管外部 SDK 的表所有权；0037 的宿主 DDL 是独立 SQL，不能用 SDK 自动建表代替迁移。迁移和业务资产导入不同：升级 head 不安装新的 Profile/Prompt/Suite，更不批准或激活 Publication。

在**专用隔离库**预演升级时，可按同一目标源码执行：

```sh
uv run alembic upgrade head
uv run alembic check
uv run python -m qs_ai.bootstrap.database_check --require-head
```

配置及测试数据库步骤见上一章。生产 apply 用镜像中的维护命令和冻结 runtime，不应先在笔记本对生产 DSN 跑一遍“试试看”。升级成功仍需检查新迁移相关表、seed、原数据保留和契约恢复；这不是供应商或业务验收。

## 失败在哪一段，下一步就不同

| 失败窗口 | 脚本留下什么 / 自动动作 | 处置重点 |
| --- | --- | --- |
| 归档、identity、MQ key、TLS 或第一次 DB probe | 不切换旧服务；写脱敏 failure.json | 修正目标发布材料和权限，不改运行中业务记录 |
| 迁移或迁移后 exact-head probe | 旧服务未被脚本停止；可能已改部分 schema | 核对 before/current、实际 DDL 和兼容性；不能按“切换没发生”推断库未变 |
| 切换失败且 before.current=after.current、有旧 current | 先停失败的新服务，再核 MQ 转移/旧 key/旧 exact-head，尝试 verify 旧版 | 只有兼容预检通过才恢复；原部署仍返回失败，state 不前移 |
| 切换失败且 heads 已变化、有旧 current | 输出需要兼容性 review，不自动恢复旧版、不 downgrade | 提供识别当前 schema 的修复或兼容代码镜像；查实际容器状态 |
| 首次部署切换失败，无旧 current | Compose down 本次服务 | 没有 previous 可回退；保留库与发布失败材料 |
| 已验证成功后的镜像保留失败 | 只 warning，不回滚健康发布 | 服务发布与清理分别验收，查看 retention audit |

`failure.json` 保存 status、error_type、受限 phase；原数据库驱动/Compose stderr可能有凭据，runner只输出脱敏阶段。verification=preflight不是成功发布。schema 已变化的失败分支不会保证旧服务仍运行或失败新服务已经停止，排障应读取当时状态，不能从旧 state.current 猜测实际进程。

## 三种回退，分别保护未来接单、运行代码和历史数据

| 操作 | 改变什么 | 必须满足什么 |
| --- | --- | --- |
| Publication Rollback / Disable | 同 selector 全局 pointer，影响之后新接单 | QS可信管理员、原 command、expected pointer/active ID；Rollback 重验目标批准证据 |
| 镜像 rollback | 服务代码与冻结 runtime；current/previous 对调 | previous 存在、准确镜像保留、目标识别当前全部 heads、MQ归属/原key可执行、验证通过 |
| 数据恢复 | 从备份重建/恢复持久事实 | 独立停写、恢复到隔离库核证、引用/hash/新增数据冲突与切换方案 |

Publication rollback 不改已有 Session 的冻结配置、原模型调用或 Artifact，也不替代镜像回滚。镜像 rollback 不执行 Alembic downgrade，不删业务表，不把 retryable/expired 转成重发许可。数据恢复不能用上一镜像启动的成功代替。

主机保留的 deploy.py 也支持 rollback；在目标已明确、具备主机操作权限的情况下，从**当前成功 release 的目录**执行：

```sh
python3 /opt/qs-ai/releases/"$QS_AI_CURRENT_RELEASE"/deploy.py rollback
```

[`restore`](../../deploy/serverA/deploy.py) 先校验 previous 的 MQ 转移、镜像与key，读取 current 数据库head及 previous 镜像的离线head契约并拒绝跨存储布局，再做 previous exact-head 检查、停止 current、verify previous；若目标启动失败，它先停目标，重验并恢复原 current，state 不改。只有恢复成功才对调 current/previous。命令不接受任意旧目录作为 previous，不能手改 state.json 绕过校验。

**本次0038/0040转换支持包含新版新增事实的完整回退**：冻结当前0040，完整逆迁移至隔离0038，逐行与往返核验后交换，再启动旧镜像。不能直接恢复首次转换时的旧备份；已启动的runtime可能已经消费MQ命令或确认消息。操作顺序与30分钟/25分钟预算见 [双向迁移步骤](09-模块数据表与双向迁移.md)。

例如 R1 的镜像 head=0036，R2 升级到0038后出现问题：即使 R1 的业务代码可能读部分旧表，`probe(R1, require_head=true)` 仍拒绝0038，不会启动。可行处置是制作包含当前迁移链、能解释现有持久契约的兼容代码镜像。MQ-enabled 发布也不能回到 messaging-disabled；schema同 head 仍须核对 frozen Route、原调用回执、三主题输入/Artifact、恢复授权和持久消息。不能清除 mq_owned、DROP 消息表或重开退役 gRPC scanner 来制造“可回退”。

## 什么算脚本验证通过，什么还需业务证据

[`verify`](../../deploy/serverA/deploy.py) 的 readiness 来自容器健康探针；运行镜像核对与数据库 probe 再分别确认准确镜像和 schema。live [`grpc_probe`](../../src/qs_ai/bootstrap/grpc_probe.py) 用 AI 证书请求退役 Change RPC，默认期待 PERMISSION_DENIED：它验证 TLS/传输拒绝边界，不验证真实 QS 管理权限、参与者授权或一个合法 Start 被接受。MQ组件 ready 表示当前拓扑/组件条件成立，不表示历史 Outbox 已得到 QS 业务 ACK。

运行形态由 [`Dockerfile`](../../Dockerfile) 与 [`serverA compose`](../../deploy/serverA/compose.yaml) 定义：单 qs-ai容器/单 Python 进程，UID10001，只读根，/tmp tmpfs64MiB，1GiB/2CPU，日志每份10MiB×3；HTTP仅映射127.0.0.1:18080，gRPC通过外部 infra-network 的别名访问。读取 `/healthz`、`/readyz` 或部署 SHA 各自只证明对应边界。正式验收还需原发布版本下的管理、授权/撤权、冻结生成/评测、原回执恢复、QS落库确认及客户端展示证据。

成功部署后当前脚本会调用 [`image-retention.py`](../../scripts/cd/image-retention.py)，保护 current、previous、所有容器引用及规则保留的成功镜像；清理失败独立告警。其记录和删除范围见 [镜像保留规则](../../scripts/cd/IMAGE_RETENTION.md)，不能把历史主机权限记录当成本次清理已成功，也不能清掉 previous 的 runtime/key材料。

现有替身测试入口为 [`test_deployment.py`](../../tests/test_deployment.py)、[`test_release_image_identity.py`](../../tests/test_release_image_identity.py)、[`test_image_export.py`](../../tests/test_image_export.py)、[`test_deployment_lock.py`](../../tests/test_deployment_lock.py)、[`test_deploy_scope.py`](../../tests/test_deploy_scope.py)；覆盖坏归档禁止load/迁移、镜像绑定防漂移、迁移失败不切换、旧进程未停阻止新启动、schema不同不自动回滚、准确远端回执和清理失败分离。多数 Docker/SSH动作被替身替换，不能证明现场磁盘、权限或网络。

[`test_mq_deployment.py`](../../tests/test_mq_deployment.py) 另覆盖冻结绑定、只读单文件、真实key角色/权限预检和禁止退回disabled；执行需要JOSE依赖。Compose解析测试需要Docker。实际执行的版本、环境和结果记录在文档闭包或日期证据中。升级后的真实数据保留与恢复要在隔离数据库和完整跨语言环境另行核证；日期绑定的历史清库/验收记录不能作为当前发布命令重复执行。
