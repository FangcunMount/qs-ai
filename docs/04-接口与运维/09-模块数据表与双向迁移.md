# 模块数据表与双向迁移

`0040_module_table_names` 将原 `0038` 的 54 张表收敛为 **44 张**，保留全部业务功能、原始事实和恢复边界。主业务库仍为 `ai`；阶段性迁移库和 30 天隔离备份不计入这 44 张表。表前缀表示存储归属，共用记录不改变事务所有者和组织权限。

本页说明代码中的存储契约与受控操作，不证明生产已经迁移或通过验收。权威映射是 [版本化布局](../../src/qs_ai/maintenance/schema_refactor/layouts.py)，业务字段见 [运行时声明](../../src/qs_ai/infrastructure/persistence/mysql/schema.py)，五张独立技术表仍由 [消息存储](../../src/qs_ai/infrastructure/persistence/mysql/messaging.py)、[序号](../../src/qs_ai/infrastructure/workflow_transport/state_events.py)及[计数](../../src/qs_ai/infrastructure/persistence/mysql/messaging_observations.py)拥有。

## 合并保留的约束

资产、草稿和完成记录统一物理表，但读取、校验和权限仍通过各自 typed ports；保留旧类型的最大长度、排序规则、NULL、版本键、原正文字节及 SHA。Prompt 草稿/命令仍全局唯一，semantic 草稿/命令仍按组织隔离。新条件唯一键不能放宽或扩大原业务约束。

Session request_id 为 NULL 表示没有原外部绑定；绑定后不能换绑。Run 策略字段成对 NULL 表示原来未保存策略，迁移不补造策略。生成与裁判完成保存各自所有列，raw_output 和 normalized_output 都原样保留；正文去重不在此次重构内。

原表的自增计数器下限也随来源 manifest 保存、复制和核验，不能只比较存活行后按 MAX(id) 重建而丢失删除过的高水位。统一资产与草稿新增的内部自增编号不属于原业务自然键，逆转换无需将这些 surrogate 带回旧表。

Job、执行租约、Run checkpoint、候选 claim、响应回执、不可变发布、当前指针、变更记录及 Inbox/Outbox/隔离消息继续分开。已派发但无响应的模型调用保持 unknown；原响应存在时继续恢复完成。表合并不能成为补发模型或重新签名消息的理由。

## 窗口前准备

`0001–0038` 保持历史原样；`0039_data_consolidation` 是五组合并的中间结构，`0040_module_table_names` 是可部署的新结构。运行时只接受镜像自己的完整 head 和结构，禁止启动中间态。普通 deploy/rollback 在跨越该转换边界前拒绝操作，自动部署不会执行此次转换。

结构转换入口为 `python -m qs_ai.maintenance.schema_refactor`，使用 plan、prepare、copy、verify、switch、rollback、cleanup 子命令。连接使用受限环境变量 `QS_AI_DATABASE_URL`；生产 DSN 不写进命令行、普通日志、回执或版本库。维护凭据与应用凭据分开，工具不启动 Broker、模型或业务执行器。

生产通过 GitHub Actions 的 `Schema maintenance serverA` 手动工作流编排这些命令。维护凭据配置在 qs-ai 的 `Settings → Environments → production → Environment secrets`：`MYSQL_MAINTENANCE_USERNAME` 和 `MYSQL_MAINTENANCE_PASSWORD`。RDS 地址和源库从已绑定的生产 release 配置读取，维护账号只在维护容器中使用，不替换应用连接。Secrets 保存凭据；数据库的建隔离库、数据复制、结构检查及换表权限由 RDS 授权提供。

每次操作使用同一 `maintenance_id`、同一份已通过 main 完整 CI 的 `revision`，依次执行：

1. `preflight`：只读检查源结构、账号权限和服务器身份，保持业务运行。
2. `prepare`：按镜像 digest 准备不可变 release、固定新旧镜像和原始配置，并创建隔离迁移库。保持业务运行。
3. `rehearse`：对生产源做一致性私有备份，恢复到隔离副本，验证正向、逆向和未启动业务时的回切，以及固定新旧镜像的领域读取结果。
4. `switch`：仅在同一身份的备份恢复和演练通过后，持有两把部署锁，停止并排空 writer，备份冻结源，全量复制、核验和交换，再核验新运行时并保存发布状态。
5. `status`：只读报告 journal 和实际结构；交换状态未知时先核对事实。`rollback` 负责完整回退，旧普通部署回滚不会跨越这条结构边界。

`preflight` 和 `status` 为只读路径。其他操作要求 `AUTO_DEPLOY_ENABLED=false`。工作流只上传不含凭据和业务正文的摘要回执；完整 JSONL gzip 数据备份、领域原始证据和 journal 保存在 serverA 的私有维护目录，凭据临时文件在每步结束时删除。备份通过单个 InnoDB 一致性只读快照导出原字段字节，恢复使用版本化表定义与经过校验的字段映射；不会执行备份文件携带的任意 SQL。

候选镜像准备成功不代表部署成功。只有 `switch` 或 `rollback` 完成镜像、数据库与服务核验并提交发布状态后，工作流才记录部署基线。生产备份恢复、真实数据演练耗时和生产业务验收必须分别保存实际证据。

计划参数只含 schema、镜像身份及私有 journal 路径；示例中的镜像和迁移标识须替换为本次固定值：

```sh
python -m qs_ai.maintenance.schema_refactor plan \
  --source ai --target "$QS_AI_REFACTOR_TARGET" --archive "$QS_AI_REFACTOR_ARCHIVE" \
  --old-image "$QS_AI_OLD_IMAGE_ID" --new-image "$QS_AI_NEW_IMAGE_ID" \
  --journal "$QS_AI_REFACTOR_JOURNAL"
python -m qs_ai.maintenance.schema_refactor prepare --journal "$QS_AI_REFACTOR_JOURNAL"
```

示例变量须预先绑定本次精确的 ai_refactor_<id>、ai_backup_<id>、两份 sha256 镜像 ID 和绝对私有 journal 路径；它们不含 DSN 凭据。journal 保存阶段、身份和校验事实，保留受限权限。工具持有 `GET_LOCK('qs-ai-schema-cutover', 0)`；操作人员还需持有部署既有 `/var/lib/fangcun-image-retention/deploy.lock` 与 `/opt/qs-ai/deploy.lock`，避免维护窗口内另一个发布或清理改变目标。不要替换或删除锁 inode。

journal 还保存原 source 每一列的 collation map，完整逆迁移必须使用这份原始契约。即使旧 archive 已在 30 天后删除，也必须保留原正向 journal 及其私有独立备份；不能随 archive 到期删除它或用当前默认 collation 重建旧结构。

执行 rollback 或 cleanup 前，先保存最近完整 `switched` / `cleaned` 正向 journal 的稳定副本，以 600 权限存放在独立私有备份位置。若 rollback_pending 经结构核验确认尚未逆交换、随后恢复了当前 0040 服务，下一维护窗口须以该稳定正向副本作为 `--inherit-journal` 创建新反向计划，使用新的目标、归档和 journal 标识；不能修改旧 phase / 停写时间延长预算，也不能沿用上次未完成的目标库。

先在独立 MySQL 8.0.36 和 8.4 完成旧库迁移、新版产生新事实后逆迁移、交换与故障恢复演练。绑定准确 source/target head、镜像、原协议、server UUID、精确表集合、结构、来源摘要及维护锁。确认同一 RDS 实例的 schema 权限、InnoDB、无触发器/视图、无跨库 FK 或名称冲突；未知表、权限不足、来源漂移或无法完整逆映射时不进入停机。

应用账号只保留 `ai.*` 所需的业务权限，不能访问隔离目标或 archive。迁移账号需要源表的 ALTER/DROP、目标表的 CREATE/INSERT，以及复制、验证、建库和 PROCESS 检查所需权限；archive 日常访问使用维护只读账号，到期 cleanup 的删除特权独立授予。必须区分 schema 级授权和表级授权：跨 schema `RENAME TABLE` 不会将表级授权迁移到新名称；若现有应用使用表级授权，须提前为 `ai` 下的新表名及回退旧表名明确配置、验证授权。schema 级 `ai.*` 授权按仍在 `ai` 中的对象生效，不能据此扩大 archive 权限。[MySQL 8.0 RENAME TABLE](https://dev.mysql.com/doc/refman/8.0/en/rename-table.html)、[MySQL 8.4 RENAME TABLE](https://dev.mysql.com/doc/refman/8.4/en/rename-table.html)说明了权限、跨库移动及原子交换条件。

预建隔离目标 schema，保持应用 DSN 的库名为 `ai`。创建 head 会预置八行观察计数，正式复制只在隔离目标中将这组已知 seed 精确替换成当前事实；其他已有目标数据不能覆盖。

## 停写、复制与切换

维护窗口上限 **30 分钟**，从停止原准入开始计时；**25 分钟仍未完成复制和核验时取消交换、恢复当前有效布局**，保留余下时间恢复服务。窗口前必须实测演练耗时；超出预算不得临时降低验证强度。

本地小规模 fixture 通过只证明转换与恢复行为，不能证明生产数据量能在 30 分钟内完成。进入生产窗口前，须以当时完整数据副本、目标 RDS 性能及实际网络条件实测排空、复制、双向验证、交换和恢复耗时，并记录足够的余量。

1. 持有共享部署/镜像保留锁及 qs-ai 专用锁；停止所有应用、维护脚本、定时任务和其他 writer，关闭新准入，等待原服务最多 210 秒排空并确认已停。Broker 保留队列和原 topic/channel，不清理待处理消息。
2. 在冻结后的当前源库取得一致快照及独立可恢复备份。按主键分批流式读取，正向 54→44 转换到隔离目标；源库不执行 DDL 或 DML。
3. 比较每张表的键集合、数量、逐行事实摘要及正反投影；检验原 UUID/外部 ID、原文/BLOB、冻结摘要、引用、NULL、唯一键与 FK。源库再核验无变化。
4. 一条完整的多表 `RENAME TABLE` 将旧 54 表移到精确命名的隔离 archive，将新 44 表移入原 `ai`，包含 `alembic_version`。单条交换结果未知时先探测布局，不盲目重复。
5. 交换后先用只读方式核验完整结构、领域读取及镜像 head，再启动新 runtime，恢复业务开关和入口，核对 readiness、原回执、冻结配置、unknown/响应恢复及业务 ACK，保存实际部署证据。

第 5 步的范围须在窗口前明确：`database_check --require-head` 验证镜像 head 与完整 44 表结构；[audit_assets](../../src/qs_ai/bootstrap/audit_assets.py)仅核对固定 Profile / Prompt / Route / Schema 四类基线（`--referenced-only` 进一步收窄到固定 Profile 引用），不覆盖全部生产资产、策略或组织草稿。[messaging_audit](../../src/qs_ai/maintenance/messaging_audit.py)提供有界的原结果 Outbox、消息 Outbox/Inbox/隔离、模型调用、评测派发及两类完成记录库存和摘要，缺表、截断及未知 head 不能当作完整验收，也不授权恢复或重试。选定组织的草稿、历史、命令/冻结回执及当前业务事实，应在私有核对清单中预先绑定自然键、组织作用域和预期原事实，交换后通过原 typed 读取接口逐项对照；没有一个通用“领域验收 CLI”替代这份清单。这些领域检查需按本次选择的自然键保存证据；无样本业务类型记为未覆盖。本地 fixture 通过不等于已在线上执行。

排空后 copy 所用 `--stopped-at` 是开始停止服务的时间，须为带时区 ISO8601，不能改成复制开始时间缩短已消耗预算。工具必须检查 PROCESS 权限及没有其他连接访问目标源 schema，`--writers-stopped` 是操作前提而不是跳过检查的开关。

```sh
python -m qs_ai.maintenance.schema_refactor copy --journal "$QS_AI_REFACTOR_JOURNAL" \
  --writers-stopped --stopped-at "$QS_AI_WRITERS_STOPPED_AT"
python -m qs_ai.maintenance.schema_refactor verify --journal "$QS_AI_REFACTOR_JOURNAL" \
  --writers-stopped
python -m qs_ai.maintenance.schema_refactor switch --journal "$QS_AI_REFACTOR_JOURNAL" \
  --writers-stopped
```

QS_AI_WRITERS_STOPPED_AT 必须是本次真实维护开始时间，不能复用此前窗口的时间。switch 不启动应用；后续启动和 readiness 核验使用受限主机上已固定镜像及 runtime 的实际 serverA 部署操作，不能通过普通 deploy 越过转换保护。

CLI 超时保护覆盖阻塞查询和提交：预算耗尽时先尝试通过同实例、同账号的控制连接终止本命令自有数据库连接，再取消当前命令。copy、verify、rollback 使用原 25 分钟预算；switch 的确认预算最多 30 分钟，但控制器仍禁止 25 分钟后发起新的 `RENAME TABLE`，过期 pending 只允许短预算探测实际结构。超时或交换结果未知时保持所有 writer 停止及部署锁，先核对 journal 与 active/target/archive 的完整实际布局，不能盲目重复交换或自动恢复旧镜像。操作系统、网络恢复及生产完整数据量的耗时仍须独立演练，这项保护不证明生产切换和恢复已经满足 30 分钟上限。

主机编排中的停止、数据库探测和启动核验共用原停写窗口的剩余时间，重试不重置时钟；超时只停止本命令自己的探测容器。启动失败后，停止可能已经写入的运行时另有一次最多 240 秒的安全清理预算；它不能用于继续换表或延长启动期限，异常处理记录须与正常停写耗时分别报告。

启动 runtime 即视为已经可能写入：MQ 接收/relay、恢复和诊断清理在用户流量开放前也可能更新数据库。源旧库归档只是事实证据，不能在新 runtime 启动后直接覆盖当前库。

## 包含新版新增事实的完整回退

回退时重新冻结**当前 0040 库**，重新创建隔离 `0038 / 54 表`，从当前 44 表全量逆转换，包含新版产生的全部新增、更新、删除、发布、配额、调用、回执和消息确认。以旧 typed 自然键拆回资产与草稿；存储内部 surrogate 可以重新分配，不改任何外部身份或冻结正文。

逆转换必须通过旧约束、旧 decoder、逐行事实及 0040→0038→0040 往返校验；再单条交换将当前 44 表隔离，将完整旧布局移回 `ai`，启动锁定的旧镜像并要求 exact head。**不能用首次迁移时的旧快照覆盖当前事实，也不能只执行 downgrade 或改版本号。**

复制/核验失败时当前库未改变，可恢复当前镜像。交换成功但业务 runtime 尚未启动时可原子交换回原冻结布局；runtime 已经启动后，任何再切换都必须以当时的 active 库重新冻结和全量转换。旧 runtime 启动失败也遵守这条规则，不能直接启用之前的 0040 archive 而丢失旧 runtime 刚消费的命令或 ACK。

需要完整回退时，在相同部署锁保护下停止当前 runtime，再执行：

```sh
python -m qs_ai.maintenance.schema_refactor rollback --journal "$QS_AI_REFACTOR_JOURNAL" \
  --writers-stopped --stopped-at "$QS_AI_WRITERS_STOPPED_AT"
```

回退开始时间同样以本次实际停止当前版本为准。`--runtime-never-started` 只用于确实未启动任何业务 writer 的快速交换：工具仍要求停写和与交换时相同的完整逻辑摘要；不得用它跳过新版新增事实的逆迁移。

如需在停写窗口前预建隔离旧布局，可为当前 `0040` 源库创建独立反向计划，继承原正向 journal；不能从无来源记录的新 journal 猜测旧 collation。此流程与上述 rollback 二选一，目标 `ai_rollback_<id>`、失败归档 `ai_failed_<id>` 和反向 journal 必须使用新的精确身份：

```sh
python -m qs_ai.maintenance.schema_refactor plan \
  --source ai --target "$QS_AI_ROLLBACK_TARGET" --archive "$QS_AI_ROLLBACK_ARCHIVE" \
  --old-image "$QS_AI_OLD_IMAGE_ID" --new-image "$QS_AI_NEW_IMAGE_ID" \
  --inherit-journal "$QS_AI_REFACTOR_JOURNAL" --journal "$QS_AI_ROLLBACK_JOURNAL"
python -m qs_ai.maintenance.schema_refactor prepare --journal "$QS_AI_ROLLBACK_JOURNAL"
```

原正向 journal 必须绑定同一实例、同一 `ai` 及完成交换的 `0038→0040` 计划，允许已完成 archive cleanup。停写后对反向 journal 执行同样的 copy、verify、switch，仍从当时 active 的完整 `0040` 事实转换，仍遵守新窗口实际 `--stopped-at`、25 分钟退出和交换后旧镜像 exact head 核验；prepare 不复制运行中的业务数据。所有相关 journal 都须私有备份并保留，后续重新正向迁移也须使用当时 active 库的新计划。

隔离 archive 保留 **30 天**，限制应用访问。`cleanup --journal "$QS_AI_REFACTOR_JOURNAL"` 必须绑定精确 schema、迁移回执、到期时间、当前源库和引用保护，先检查再清理；它不会删除 `ai`、应用配置、Broker 数据、密钥或运行镜像。30 天保留不等于 30 天任意快照覆盖许可。
