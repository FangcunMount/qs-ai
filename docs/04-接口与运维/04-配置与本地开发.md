# 配置与本地开发

本地开发有三条不同路径：**离线检查不需要数据库；持久化测试需要专用 MySQL；完整服务联调还需要 QS、MQ、TLS、JOSE 密钥和业务资产。** 仓库的 Compose 只提供 MySQL，不能凭数据库 ready 推断统一服务可启动，也不能把缺依赖导致的 skipped 测试记为通过。

本文按业务源码 `766b2aa` 核对，日期为 2026-10-06。下面命令从 qs-ai 仓库根目录执行，数据库例子只用于专用本地测试实例。生产操作见 [部署迁移与兼容回滚](05-部署迁移与兼容回滚.md)。

## Settings 加载的是宿主配置，MySQL 保存业务版本

| 来源 | 保存什么 | 何时使用 |
| --- | --- | --- |
| `configs/default.yaml` + 环境 YAML | 地址、连接池、TLS 路径、MQ 绑定、模型目录/连接、loop/容量、额度默认值与 ceiling | 创建进程的 Settings；运行中不自动重载 |
| 环境变量 / 显式测试参数 | 数据库 URL、供应商凭据，以及上述非秘密字段的覆盖 | 构造 Settings 时；凭据不写入业务资产 |
| 只读挂载文件 | TLS CA/证书/私钥，JOSE 签名与解密私钥、公钥 | 启动检查与连接装配 |
| MySQL quota 版本与 pointer | 组织额度及历史版本 | 后续接单/新槽位检查；原日预留和已 active 槽复用 |
| MySQL 资产、Run、Publication | Profile/Prompt/Route/Schema/Suite/策略及批准证据 | Prepare、评测与接单冻结；已有工作继续用自己的原版本 |
| `integrations/qs_server/*` | 固定来源、初始化原字节、机器 Schema 和对照样本 | 导入/契约检查；文件存在不代表资产已导入或已发布 |

[`Settings.settings_customise_sources`](../../src/qs_ai/config.py) 的优先级从高到低为**显式构造参数 → `QS_AI_` 环境变量 → 合并后的 YAML**。先选 environment，再递归合并 default 与 local/production；嵌套对象逐字段覆盖，列表整体替换。environment 只允许 local / production，默认 local。

例如 default 的 HTTP 是 `0.0.0.0:8000`，local 只覆盖 host 为 `127.0.0.1`；设置 `QS_AI_HTTP__PORT=9000` 后得到 `127.0.0.1:9000`；测试中再传 `Settings(http={"port":7000})` 则得到 `127.0.0.1:7000`，没有丢掉 local 的 host。`__` 是嵌套分隔符；整个 `QS_AI_MESSAGING` / `QS_AI_MODELS` 也可用 JSON 传入。

YAML 的根节点须是字符串键 mapping，禁止 `database_url`、environment 和三种模型凭据键。缺文件、非法 YAML、未知配置字段和已识别字段的非法值都会失败；例如 `QS_AI_HTTP__TYPO` 会进入 HTTP 对象并被拒绝。**完全拼错的顶层环境变量名可能被忽略**，不能仅凭“没报错”确认覆盖已生效。Settings 不加载 `.env` 或 file-secret source；把文件放在根目录并不会自动注入其中的变量。

配置路径先找安装包内 `qs_ai/configs`，再找源码根目录的 configs，不依赖当前工作目录；但 Alembic 与服务 schema 预检使用仓库/镜像中的 `alembic.ini`，这些命令仍应从项目根或镜像 `/app` 执行。wheel 携带 configs 和 Prompt/Route/Evaluation/Schema 文件，MySQL 业务状态并不随 wheel 打包。

可以只输出下面这类非秘密投影来核对有效配置，不输出整个环境或 `get_secret_value()`：

```sh
uv run python - <<'PY'
import json
from qs_ai.config import Settings
s = Settings()
print(json.dumps({
    "environment": s.environment,
    "http": s.http.model_dump(),
    "database_configured": s.database_url is not None,
    "messaging_enabled": s.messaging.enabled,
    "generation_enabled": s.generation.enabled,
    "evaluation_enabled": s.evaluation.enabled,
    "candidate_mode_enabled": s.evaluation.candidate_mode_enabled,
    "evaluation_consumers": s.evaluation.concurrency,
    "evaluation_parallel_calls": s.evaluation.parallel_calls,
    "per_run_parallel_calls": s.evaluation.per_run_parallel_calls,
}))
PY
```

数据库 URL 只接受 `mysql+asyncmy` driver。DeepSeek 新名 `QS_AI_DEEPSEEK_API_KEY` 与旧 `QS_AI_MODEL_API_KEY` 是显式兼容别名；同时设置必须完全一致，否则报脱敏冲突。智谱用独立 `QS_AI_ZHIPU_API_KEY`。设置错误时 `hide_input_in_errors` 保护输入值，但排障仍应保留错误类型与字段，避免打印原 DSN。

## 路径一：离线检查代码、生成物和契约

[`pyproject.toml`](../../pyproject.toml) 支持 Python `>=3.11,<3.14`；CI 和镜像使用 Python 3.11，CI 固定 uv 0.12.13。首次准备锁定依赖执行 `uv sync --locked`，需要取得 uv.lock 指定的包，其中可靠消息 SDK 是带锁定 hash 的固定预发布 wheel。安装依赖是开发环境准备，测试本身使用替身，不要求供应商凭据。

```sh
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run python scripts/generate_qs_proto.py --check
uv run python scripts/generate_workflow_proto.py --check
uv run python scripts/generate_messaging_proto.py --check
uv run python scripts/check_docs.py
uv run pytest -m 'not integration and not interop'
```

三个生成脚本的 `--check` 比较 proto 与仓库生成物，不重写源文件；日常改契约后才使用对应生成入口更新并提交生成物。离线测试排除两种 marker：integration 要隔离 MySQL，interop 要固定 Go 程序或 Go 导出的向量。部分 interop 测试位于 tests 根目录且只有 interop marker，因此仅排除 integration 会留下缺依赖的 skip。

FastAPI factory 和 Dishka 资源图可以在无数据库时测试；`/readyz` 返回 not_configured 是预期结果，不能称完整服务 ready。开发 API factory、维护探针和正式 `bootstrap.server` 的启动要求不同，单独运行 HTTP factory 不会建立 QS/MQ 业务运行链。

## 路径二：在专用本地 MySQL 验证事务

[`compose.yaml`](../../compose.yaml) 的 MySQL 8.4 只绑定 `127.0.0.1:13316`，默认建立 qs_ai 库及本地测试账号，数据保存在 `mysql_data` volume。卷会保留上次数据；若这套实例已经承载需保留的开发记录，另准备专用测试实例再跑以下步骤。集成 fixture 会插入、修改并清理记录，部分迁移测试会操作 schema。

```sh
docker compose up -d --wait mysql
export QS_AI_ENVIRONMENT=local
export QS_AI_DATABASE_URL='mysql+asyncmy://qs_ai:qs_ai_local@127.0.0.1:13316/qs_ai'
export QS_AI_TEST_MYSQL_DSN='mysql://qs_ai:qs_ai_local@127.0.0.1:13316/qs_ai'
uv run alembic upgrade head
uv run alembic check
uv run python -m qs_ai.bootstrap.database_check --require-head
uv run pytest -q tests/integration/test_interpretation.py tests/integration/test_participant_capacity.py
```

这里两个 DSN 名字用途不同：应用/Alembic 读 `QS_AI_DATABASE_URL`；测试 fixture 读 `QS_AI_TEST_MYSQL_DSN`，将其转为 asyncmy，部分替身也使用原 DSN。只设置应用变量会让 fixture 跳过，不会自动对应用库执行测试。账户、host、port 和库名必须指向同一专用实例；示例密码仅是 Compose 的本地固定值。

顺序先迁移再 check：`alembic check` 检查 metadata 是否产生待迁移差异；[`database_check --require-head`](../../src/qs_ai/bootstrap/database_check.py) 核对 MySQL 为兼容的 8+、当前 revision 可识别且与该源码的全部 heads 精确一致。它不证明必需业务资产、MQ 拓扑或模型可执行。迁移失败不要继续跑业务测试：MySQL DDL 可能已有部分提交，需核对版本账本和实际结构后处理，不通过手改 alembic_version 掩盖差异。

默认维护探针只借数据库连接，不运行模型：

```sh
uv run python -m qs_ai.bootstrap.worker
uv run python -m qs_ai.bootstrap.evaluation
```

worker 探针输出 worker_probe/database；evaluation 探针输出 evaluation_probe/database。它们检查连接，并不检查 exact heads 或 MQ；与上面的 database_check 结论分开。`--once` 会领取一个生成 Job，或恢复/推进一个已 Start 的评测步骤，可能外发模型请求、写业务状态；它不是“再深一点的健康检查”。维护执行应绑定隔离数据或明确的处置目标，与常驻执行器的运行范围一并核对。

## 路径三：完整 QS / MQ / AI 联调

[`serve`](../../src/qs_ai/bootstrap/server.py) 的前置检查有实际先后：要求 messaging enabled → 读并校验 TLS → 共享池核对 exact heads → 装配启用的生成/评测依赖 → MQ 读取观测 schema、装配授权/正文连接及传输 → 启动组件并形成 runtime ready。启动只检查，不自动迁移、导入资产或创建失败拓扑。

| 配置或材料 | 完整联调需要什么 | 常见错误的实际含义 |
| --- | --- | --- |
| Database | 已迁移的 AI 专用库，连接用户有业务读写权限 | 连接成功但 heads 不同仍不能启动 |
| TLS | CA、AI 服务证书/私钥，QS 端可信证书与工作负载身份 | 文件存在不等于证书/私钥匹配或 peer 被授权 |
| `grpc.access_address` | QS mTLS 授权与 MessagePayloads endpoint | 不是 AI 自己的 gRPC 监听；MQ enabled 时也必需 |
| `messaging.nsqd` | 显式 TCP address → 同主机 HTTP origin 映射 | 不按4150推断4151，不用发现循环替代配置 |
| JOSE | AI 签名私钥、按 kid 的 AI 解密私钥、QS 签名公钥、QS 接收者公钥 | [`read_key`](../../src/qs_ai/bootstrap/messaging.py) 检查角色、kid、EC P-256 与文件≤64KiB；不把私钥当公钥用 |
| NSQ topology | 三条业务 Topic/Channel，加接收链的失败 Topic/`cb-failed-handler` Channel | [`FailureTopology`](../../src/qs_ai/infrastructure/workflow_transport/mq_failure.py) 只读检查预建且未暂停的失败拓扑，缺失就失败 |
| Model | 按冻结 Route 的 exact binding、凭据与协议，启用阶段所需资产 | 目录 verified 只表示技术能力记录，不等于当前连接成功或质量批准 |
| Publication / Run | 接单 selector 有批准发布；评测 Run 已 Prepare、Start 且有原资产 | 设置 generation/evaluation=true 不创建这些业务对象 |

Topic/Channel 的固定值见 [`workflow_transport.messaging`](../../src/qs_ai/infrastructure/workflow_transport/messaging.py)：commands=`qs.ai.commands.v1` / `qs-ai.commands.v1`，events=`qs.ai.events.v1` / `qs-server.ai-events.v1`，acks=`qs.ai.acks.v1` / `qs-ai.acks.v1`。AI 接收 commands 与 acks，QS 接收 events；两边同时需要可信 JOSE 配置和正文引用读取权限。传输成功与 QS 业务落库确认的区别见 [可靠消息](../03-基础设施/messaging/README.md)。

本地启用监听要显式覆盖三份 TLS 路径、QS 地址和完整 messaging JSON，然后在所有上述依赖已准备好的隔离环境运行：

```sh
uv run python -m qs_ai.bootstrap.server
curl --fail http://127.0.0.1:8000/healthz
curl --fail http://127.0.0.1:8000/readyz
curl --fail http://127.0.0.1:8000/metrics
```

默认 messaging=false，直接运行 server 会报 `MQ runtime is required; legacy gRPC delivery is retired`。关闭 generation/evaluation 可以保留接单、消息交接和治理联调，仍必须准备数据库/MQ/TLS/QS。generation 启用还要求 QS 授权地址及可用 legacy HTTPS 连接或 model bindings；evaluation 要数据库和模型 bindings/legacy 配置。依赖装配成功不验证供应商 API key、余额或输出质量。

## 迁移后还需安装业务资产，安装不等于发布

开发空库没有 Prompt/Profile/Route/Suite。各 `import_*` 命令把 integrations 的固定来源导入不可变身份，返回 inserted 与 activated=false；相同身份相同原字节可复用，不同内容报冲突，不悄悄覆盖。常规基线入口为 import_prompts、import_profiles、import_routes（评测路线需 `--include-evaluation`）、import_schemas、import_evaluation_assets、import_evaluation_suites，均要求 `--imported-by`。

MBTI 根安装另要求 exact source commit 与 `--root v1` 或 `three-topic-v1`，原路线、共享执行/门槛策略和 semantic schema 要先存在；根资产及 Suite 同一事务安装。准确先后与来源证明范围见 [MBTI 模板与方案来源契约](../02-业务模块/governance/02-MBTI模板与方案来源契约.md)。不要把导入完成后的 activated=false 理解为缺一个环境开关：还需方案 Prepare、执行证据、人工审核和 Publish。

只读 [`audit_assets --referenced-only`](../../src/qs_ai/bootstrap/audit_assets.py) 只检查保留基线引用，并明确返回 current_production_inventory_verified=false；[`build_manifest`](../../src/qs_ai/bootstrap/build_manifest.py) 只组装未批准 manifest。它们不能证明完整生产资产清单或激活发布。`bootstrap.integration` 已退役，不能恢复旧 gRPC result scanner。

## CI 比单机数据库测试多证明了哪些边界

[`ci.yml`](../../.github/workflows/ci.yml) 对 MySQL 8.0.36 / 8.4 各跑四个完整分片，除上述离线/迁移检查，还建立独立 QS bridge 数据库、固定 Go bridge/access probe、实际 QS snapshot 向量、隔离 NSQ 和跨语言 MQ probe。两个 Go checkout 分别固定在 `e4c93f7a9ea68ec0a00e34a682f959dc69a895c7` 与 `f637b29dac8537e133559f3877fb82156611e0d9`；不能用“本机 qs-server main 编译成功”替代该 CI 对照。

[`run_tests.py`](../../scripts/ci/run_tests.py) 记录 revision、MySQL 版本、collected/selected/passed/skipped；即使 pytest 返回0，只要分片缺执行或出现 skip 也改为失败。汇总 [`verify_test_shards.py`](../../scripts/ci/verify_test_shards.py) 要求两个 MySQL 版本的全部分片完整且同 revision。镜像 job 另在无网络、只读、非 root 条件核对装配，并运行单进程 smoke；wheel job 在仓库外检查打包资产。

真实供应商探测是另一入口：[`probe_model_bindings.py`](../../scripts/probe_model_bindings.py) 默认只输出单次计划，只有 `--execute` 才外发一次合成请求。它不启用目录、不写批准发布，且不代表真实报告质量。开发测试、隔离互操作、供应商连通性、部署就绪和业务验收应分别记录结果。

本篇验证入口包括 [`test_config.py`](../../tests/test_config.py) 的覆盖/脱敏/非法字段、[`test_container.py`](../../tests/test_container.py) 的 scope 与关闭、[`test_messaging_runtime.py`](../../tests/test_messaging_runtime.py) 的密钥/装配/观测预检，以及 [`test_ci_sharding.py`](../../tests/test_ci_sharding.py) 的完整分片与缺执行拒绝。它们不证明本机已有联调环境；数据库及跨语言测试仍须提供各自依赖。
