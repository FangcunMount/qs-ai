# 语义契约故障恢复

裁判返回了响应，但 decisions 少判了一项、重复判了一项或不符合原 assertions 清单，评测可以保存明确失败并停在 `semantic_recovery_not_allowed`。本入口允许操作者保留这份原失败，授权对**同一候选**再做一次有界语义评判；不会重新生成文案、改冻结策略或把失败输出修成 passed。

入口为受信部署主机的 [`qs_ai.bootstrap.recover_semantic_contract`](../../src/qs_ai/bootstrap/recover_semantic_contract.py)，没有公开 HTTP/治理 RPC。它调用 [`authorize_contract_recovery`](../../src/qs_ai/infrastructure/persistence/mysql/evaluation_contract_recovery.py)，默认完成校验后回滚预览，显式 apply 才提交授权。这里的“成功”最多证明授权已保存，不证明裁判重试完成、质量通过、人工批准或 publication 生效。

## 先确定是契约失败，不是 unknown 或质量没通过

实际 [MissingDecision 集成用例](../../tests/integration/test_semantic_contract_recovery.py) 先生成候选，再让合成裁判从正常 response.decisions 删除最后一条。响应已经返回并保存；本地重建断言时发现缺项，留下 `status=failed / failure.code=semantic_decision_contract_invalid`，而当前冻结策略没有自动放行这个错误，于是阻塞。这是本命令要处理的场景。

| 原持久证据 | 本入口是否适用 | 应走的边界 |
| --- | --- | --- |
| 原语义完成明确 failed，code 为 semantic_decision_contract_invalid；存在 receipt 与非空 normalized_output；当前阻塞恰指它 | 校验其他条件后可预览 | 同候选的一次语义契约例外 |
| dispatching / result_unknown，没有可确认响应 | 不适用 | 原执行到期恢复、unknown 人工处置；不能借契约修复再次收费 |
| 语义执行 succeeded，但某断言 failed 或质量评分低 | 不适用 | 保留候选/质量判断，按原审核与发布门槛处理 |
| provider_rate_limited、网络故障等其他错误 | 不适用 | 冻结策略内对应错误/预算的执行规划，或具体依赖排障 |
| 新候选的生成/输出/安全失败 | 不适用 | 生成与确定性校验链；本命令不会替换候选 |
| 原语义 ordinal 已为 2，或整轮预算无余量 | 不适用 | 原预算终止；不得增加第三次调用 |
| 已有 active claim、取消正在排空，或最后阻塞已变 | 不作为正常修复目标 | 先完成原所有权/取消核对，不能把它当活动 Run 通用维修 |

“响应完整”与“内容判通过”分开检查。补充指令要求裁判逐项返回，仍必须如实标记不满足的断言。一个已经正确判为 failed 的职业适配、身份本质化或未提供事实问题，不能靠此命令争取第二次高分。

## 用原 Run、原候选和两个输出摘要固定目标

从当前组织的 QS 管理查询或受信 AI RPC 取原 Run。`EvaluationManagement/Get` 返回当前 version/status、execution_mode、active_call_count、cancel_draining、创建回执、未知与审核信息；`ListExecutions` 和 `GetExecutionOutput` 在 expected_version 下提供原 invocation/execution、阶段、失败证据和 raw/normalized 字节。QS 对应路由见 [排障与受控恢复](06-排障与受控恢复.md)。这些读取不触发恢复。

准备下列目标事实，不能从当前 active publication 或最新 Prompt 推导旧 Run 的身份：

| 目标事实 | 依据与用途 |
| --- | --- |
| 原 organization_id、run_id、当前 version | 限定本轮和 CAS；不是原创建时 version，也不是 Session version |
| 原 release_fingerprint | 来自该 Run 的 definition/creation receipt，覆盖原冻结 release；不是当前 publication 指针版本 |
| 原失败 execution_id / invocation_id / ordinal | 必须是本次最后阻塞所指的语义执行；不能选上一条失败或其他候选 |
| candidate_id / candidate_output_fingerprint | 绑定已生成候选的 normalized 字节，禁止改文案再续用同一身份 |
| 原语义 output_fingerprint | `sha256:` + SHA-256(原 normalized_output 字节)，不是 raw_output 或候选摘要 |
| failure、receipt、finished_at | 明确失败且有原响应；时间必须与阻塞证据吻合 |
| 原策略与账本使用量 | 目标候选及整轮语义余量；失败、unknown 和成功 dispatch 都计入 |

CLI 不提供 `--candidate-id` 或候选摘要覆盖参数。它按 run_id/execution_id 读取原 SemanticCompletion，自动从这条记录取得候选 ID、候选摘要和裁判摘要，再交给恢复事务逐项核验。`GetExecutionOutput.normalized_sha256` 是不带前缀的十六进制摘要；CLI 的 expected_output_fingerprint 是带 `sha256:` 的裁判输出身份，二者不要误用。

Run 的普通 Get 不返回完整 progress/transitions 和 semantic_contract_recoveries。需要核对最后阻塞、取消意图、授权前后原记录时，在受信维护工具的同一只读事务内使用针对该 Run 的参数化查询；下面是查询形状，参数由工具绑定，不是可直接替换为 UPDATE 的脚本：

```sql
SELECT r.run_id, r.organization_id, r.execution_mode, c.version,
       c.checkpoint_json,
       JSON_UNQUOTE(JSON_EXTRACT(r.definition_json, '$.release_fingerprint'))
           AS release_fingerprint,
       JSON_UNQUOTE(JSON_EXTRACT(r.progress_json, '$.status')) AS status,
       JSON_EXTRACT(r.progress_json, '$.transitions[last]') AS last_transition,
       JSON_EXTRACT(r.progress_json, '$.cancel_requested') AS cancel_requested,
       JSON_EXTRACT(r.progress_json, '$.semantic_contract_recoveries')
           AS contract_recoveries,
       (SELECT COUNT(*) FROM evaluation_slot_claims s
        WHERE s.run_id = r.run_id) AS active_claims
FROM evaluation_runs r
JOIN evaluation_checkpoints c ON c.run_id = r.run_id
WHERE r.run_id = :run_id AND r.organization_id = :organization_id;
```

不要选全库正文来找一条故障。原失败正文仅在已授权的原执行输出查询中读取，保存字节及摘要，避免进入普通日志；表与字段依据为 [schema.py](../../src/qs_ai/infrastructure/persistence/mysql/schema.py)。

恢复事务锁原 checkpoint 和 Run，要求 expected_version 匹配、checkpoint 为空、组织正确、冻结 release 的引用重算摘要等于提交摘要。最后 transition 必须是 `semantic_recovery_not_allowed`，evidence_refs 恰为目标 execution，授权时间不得早于阻塞。

candidate 并发时，原失败可能早于这条“排空后出现”的阻塞。例如 B 于 10:01:02 失败，其他候选于 10:02:00 排空，此时 transition.at 可以是 10:02:00、evidence_at 是 10:01:02。校验要求目标 finished_at 等于 evidence_at（没有该字段则等于 at），且 evidence_at 不晚于 at；不能为匹配而改原失败时间或选最后结束的成功调用。

正常 candidate 完成机制在 claims 排空后才形成该 blocked 状态。恢复函数自身检查 checkpoint 和原证据，**未额外调用 active_claims，也未把 cancel_requested 当作独立拒绝条件**。所以维护前仍应核对 active_call_count/claims 已空、没有需要继续排空的取消意图。若取消意图已存在，它会被保留，worker 停新 dispatch；不能承诺 apply 后一定发生语义重试。

## 参数、预览和 apply 的实际行为

命令读取目标部署环境的 Settings.database_url，自己拥有临时数据库连接池并在 finally 关闭；不启动服务、Broker 或供应商调用。执行人需要对该 Run 的恢复授权以及受信主机/数据库维护权限，CLI 不复用业务 JWT 或 QS 管理角色验证。操作者从当前进程的 OS 有效用户生成 `operator:<账号>`，没有 `--actor` 参数，也不能填写另一个业务用户代签。

| 参数 | 必填与校验意义 |
| --- | --- |
| --run-id | 必填 UUID；原评测 Run |
| --organization-id | 必填整数；恢复事务限定原组织 |
| --expected-version | 必填整数；预览时读到的当前 Run/checkpoint 版本 |
| --execution-id | 必填；最后阻塞对应的原语义 execution，不是 invocation |
| --expected-release-fingerprint | 必填；原冻结 release 的带前缀 SHA-256 |
| --reason | 必填；非空、UTF-8 不超过 1000 bytes、不含 `<`/`>`，说明单次授权原因 |
| --apply | 默认不设置；设置后才提交授权 |
| --expected-output-fingerprint | apply 必须匹配刚核对的原失败裁判输出摘要；预览不要求 |
| --acknowledge-policy-exception-and-cost | apply 必须显式设置，确认策略例外与增加调用费用 |

以下都是占位符，先用准确目标运行预览，不传 apply：

```sh
python -m qs_ai.bootstrap.recover_semantic_contract \
  --run-id '<原评测 Run UUID>' \
  --organization-id '<原组织整数ID>' \
  --expected-version '<当前 Run 版本>' \
  --execution-id '<原失败语义 execution ID>' \
  --expected-release-fingerprint 'sha256:<原 release 的64位摘要>' \
  --reason '<已授权的同候选契约修复原因>'
```

预览调用真实 authorize_contract_recovery：读取/锁定目标、校验全部原证据、在事务内拟写授权与 blocked → collecting，返回后不 commit，由事务关闭回滚。它不保存持久授权、不新增 dispatch，也不触发模型；但不是纯 SELECT，会持有真实事务锁。返回 `mode=preview_rolled_back`，其中 result_version=expected_version+1 是拟议版本，数据库当前版本不应因此改变。

核对返回的 run_id、execution_id、candidate_id、output_fingerprint、release_fingerprint、actor、reason 和 next_action；next_action 固定是 `retry_same_candidate_semantic_once`，existing_generation_outputs 为 preserved。恢复身份 `semantic-contract-recovery/v1`、固定补充指令摘要也必须与目标镜像相符。当前补充指令摘要为 `sha256:de12c0e55a7fe766c4dc4b4b6b339ca211111f85711036c60c78780ab077c816`，来源为 [contract_recovery.py](../../src/qs_ai/domain/evaluation/contract_recovery.py)。

获得这一个目标的正式授权后，在**同组目标参数**上增加以下三项：

```sh
--apply \
--acknowledge-policy-exception-and-cost \
--expected-output-fingerprint 'sha256:<预览的原失败裁判输出摘要>'
```

apply 重新读取原失败，先要求费用确认和裁判摘要匹配，再执行完整恢复事务，成功 commit 后才输出 `mode=applied`。没有 command_id 或幂等 Receipt；重复 apply 不能重放为同一个成功回执，旧 expected_version 会冲突，改新版本后同一授权也会因已处理/不再是精确阻塞而拒绝。并发 apply 最多一份接受，不能用修改版本绕过。

错误仅输出 `status=rejected / error_type` 并退出码 1，不回显 DSN、原正文或驱动异常。异常也可能发生在提交/退出附近；没有收到 applied 不足以证明没保存授权。先读原 Run 的版本、transitions 和 contract_recoveries，确认是否已有本次原 execution 的记录，再决定是否仍需操作，不能盲目重试。

## 匹配与不匹配示例

假设某合成 Run 的当前版本为 58，最后阻塞指向 `semantic:case-01:slot-1:attempt-1`，原候选为 `candidate:case-01:slot-1`，原完成 ordinal=1/status=failed/code=semantic_decision_contract_invalid，有 receipt 与非空 normalized_output。原 release、候选和失败裁判摘要分别记为 R、C、J；这三个字母只表示已核对的不同摘要，不是实际参数值。

| 提交或证据变化 | 判断 | 依据 |
| --- | --- | --- |
| 同组织/Run、version=58、目标原 execution、release=R；预览取得原 candidate/C/J | 可以进入完整预览校验 | 身份来自原记录，未替换候选 |
| apply 延用 version=58、release=R、output=J，且风险确认；期间未发生变化 | 可提交一份授权，拟结果版本为 59 | 原失败、最后阻塞、预算和下一步均须匹配 |
| expected_version=57，或期间其他操作已推进到 59 | 拒绝 | CAS 不是提示数字；应重新读取原意图 |
| output 填成 C、raw SHA 或另一候选裁判摘要 | 拒绝 | expected-output 指原失败 normalized 裁判字节 J |
| 目标换为上一个失败，最后阻塞仍指当前执行 | 拒绝 | transition evidence_refs 必须精确对应 |
| 原完成为 result_unknown，或质量 judged failed 但执行 succeeded | 拒绝 | 缺明确可修复契约失败，不能借例外改变评价 |
| 原目标已有 ordinal=2 后续执行，或目标本身为第二次 | 拒绝 | 不重复授权，不生成第三次 |
| 预览正确后更换 release 或修改候选正文 | 拒绝 | 原冻结 release/候选摘要不可替换 |

预览成功也不是预约：释放锁后别的工作仍可改变版本/阻塞，apply 必须重新校验。判断失败不要通过删 original completion、改 failure.code 或篡改 transition 去让命令接受。

## 授权后怎样核证真正发生了什么

先回读上述针对原 Run 的只读查询：contract_recoveries 增加一条，记录原 execution/candidate、候选摘要 C、原裁判摘要 J、操作者/理由/时间、费用确认、恢复版本和指令摘要；transition 为 semantic_contract_recovery_approved。原 definition_json、冻结策略、生成输出和第一次失败记录应保持。

正常 EvaluationWorker 随后按原证据规划第二次语义调用，使用原 semantic Route、冻结 Prompt/Schema、原候选及 assertions，仅在 task_message 末尾加固定 RECOVERY_INSTRUCTION。要求每个 `(type, scope, ordinal)` 恰好判一次、status/detail 一致，并明确“不满足必须 failed”。来源见 [evaluation_step.prepare_step](../../src/qs_ai/infrastructure/persistence/mysql/evaluation_step.py)。完整性提醒不是改原 Prompt 的字节、目录注册或新的 release。

核证时分别观察：

1. 新 dispatch 使用同 candidate_id/C、新 execution_id/invocation_id、ordinal=2，开始时间不早于授权；没有新的 generation dispatch。
2. 原失败 ordinal=1 的正文、receipt、failure 与 J 仍在；第二次响应和 completion 是追加证据。
3. 原冻结预算不变。当前根每候选最多两次、整轮最多 70 次语义执行；一次失败也计入。完整 35 槽位若只有这一次失败，可能得到 35 generation、36 semantic，而不是删除失败后伪装成 35+35。
4. 第二次若仍契约失败，本轮可以阻塞为 semantic_budget_exhausted，不能再用本入口扩大预算；若产生 unknown，转原 unknown 处置；若执行成功但质量没过，保留真实裁判结论。
5. 剩余候选完成后，闭包、gates、两类人工审核和 publication 各自照常核验；awaiting_review 或本次 applied 都不是批准。发布边界见 [发布证据与生效指针](../02-业务模块/publication/01-发布证据与生效指针设计.md)。

CLI 只提交授权，不调用 management.resolve 的容量再准入包装；后续 worker 仍受开关、模型容量、冻结资产与原执行计划约束。存在 cancel_requested 时更不会因这份授权恢复新发送。未看到新 dispatch，应先核对这些实际条件，不能重复 apply “催运行”。candidate 第二次响应已保存但投影失败时，按原独立回执恢复，仍不再调用供应商；机制见 [执行恢复](../03-基础设施/execution-recovery/README.md)。
