# QS 接入与消息契约

参与者接入的入口是 QS `collection-server` 的 HTTP API。客户端选择自己有权访问的 Testee、测评和当前标准报告，QS 保存报告事实与稳定请求；qs-ai 异步决定准入并生成成果，QS 接收事件后才提供参与者结果读取。提交成功、AI 接单、模型完成、QS 入库和页面展示是五个可分别观察的事实。

本文面向调用这些入口的客户端及 QS 集成开发者。核对基线：qs-ai `d9c3155`、qs-server `2ccc2de`、IAM `c8fc1fe`，2026-10-06。示例 ID 用于说明字段，不表示真实用户或已完成请求。传输事务、失败预算和密钥装配见 [消息基础设施](../03-基础设施/messaging/README.md)。

## 1. 先确定本人有权访问的当前报告

四个现行 HTTP 入口均需登录，并经 `TesteeAccessMiddleware` 检查当前用户能否代表 `testee_id`：

| 方法和路径 | 客户端用途 |
| --- | --- |
| `GET /api/v1/assessments/{id}/ai-workflows/source?testee_id=…` | 读当前报告 ID、版本与 AI 能力预检 |
| `POST /api/v1/assessments/{id}/ai-workflows?testee_id=…` | 保存一次稳定请求并提交异步命令 |
| `GET /api/v1/interpretation/ai-workflow/operations/{command_id}?testee_id=…&assessment_id=…&request_id=…` | 读原命令的提交、传输和接单决定 |
| `GET /api/v1/assessments/{id}/ai-workflows/{request_id}?testee_id=…` | 读 QS 已持久接收的工作流投影与成果 |

旧 `/ai-explanations`、`/ai-explanation/capability` 和导出入口已撤销。不要用旧接口响应拼接新工作流。路由以 [QS collection router][qs-router] 为准。

权限由两类事实共同成立：IAM 持有当前有效的 User → ProfileLink → Profile 关系；QS 持有 Testee 的 `profile_id`、机构及测评归属。QS 通过 IAM SDK 查询 active link，再核验该测评属于该 Testee。`testee_id`、`assessment_id` 和 UUID 都是资源定位值，不能单独授权。IAM 或 QS 授权依赖不可用返回服务不可用，不能解释成“未绑定用户”并继续读取。依据见 [QS 当前授权][qs-access]、[IAM ProfileLink 查询][iam-links]。

从 collection-server 到 apiserver 的参与者委托使用 `x-qs-delegated-subject`。它从已认证用户上下文签出，绑定用户、Testee、可选机构、有效期和以下精确 purpose：

| HTTP 动作 | 委托 purpose |
| --- | --- |
| 来源/能力预检 | `participant_ai_explanation.capability` |
| 提交请求 | `participant_ai_explanation.request` |
| 读结果或原操作 | `participant_ai_explanation.get` |

apiserver 要求启用委托验证；验证 purpose、Testee 和受信工作负载之后，再调用 `ResolveParticipantActor` 重查业务关系。参与者登录可以没有机构 claim，最终 Actor 的机构取自已授权的 QS Testee；若 token 带了机构，则必须匹配。浏览器不填写 Actor，也不签委托。[委托验证][qs-delegation]、[参与者服务][qs-participant-grpc] 是这一边界的实际入口。

以下是一组有效的来源读取形状，假定 QS 当前标准报告为 99、报告内容版本为 `standard-v1`、Outcome 为 101：

```http
GET /api/v1/assessments/42/ai-workflows/source?testee_id=7
Authorization: Bearer <登录令牌>
```

```json
{"code":0,"message":"success","data":{"status":"ready","report_id":"99","source_version":"standard-v1:101","ai_eligibility":{"status":"available"}}}
```

来源状态与 AI 状态必须分别处理：

- `not_ready`：尚无可用当前标准报告，不返回报告 ID/版本。
- `not_applicable`：当前来源不适用新工作流，同样不返回来源身份。
- `ready`：有完整当前报告来源，但 `ai_eligibility` 仍可能为 `unavailable`；例如 `publication_missing`、`publication_paused`、`unsupported_model_version` 或 `asset_invalid`。

预检只读，不创建 Session、不占每日额度、不调用供应商。`available` 是此刻的配置与来源可用性，不承诺稍后准入成功。超时返回 503，不能伪造 `publication_missing`；能力理由的有限集合与场景解码见 [报告 AI 能力预检契约](../02-业务模块/interpretation/04-报告AI能力预检契约.md)。

## 2. 用稳定请求提交；报告事实由 QS 构造

客户端先持久保存本次 `request_id` 和选择的 `report_id`，再发请求。UUID 须为小写标准格式、非全零；报告 ID 为无前导零的正十进制字符串。请求体只有这两个字段：

```http
POST /api/v1/assessments/42/ai-workflows?testee_id=7
Authorization: Bearer <登录令牌>
Content-Type: application/json

{"request_id":"00000000-0000-4000-8000-000000000001","report_id":"99"}
```

当前 MQ 路径返回 HTTP 202，示例完整数据形状为：

```json
{
  "code":0,
  "message":"submitted",
  "data":{
    "request_id":"00000000-0000-4000-8000-000000000001",
    "operation_id":"00000000-0000-4000-8000-000000000001",
    "command_id":"00000000-0000-4000-8000-000000000001",
    "status_url":"/api/v1/interpretation/ai-workflow/operations/00000000-0000-4000-8000-000000000001?assessment_id=42&request_id=00000000-0000-4000-8000-000000000001&testee_id=7",
    "status":"submitted"
  }
}
```

202 表示 QS 原请求、操作记录与命令 Outbox 已提交到数据库。它尚不能证明 qs-ai 接单，更不能证明开始或完成了模型调用。HTTP 形状来自 [handler][qs-http]，标识与原始命令的共同提交来自 [QS command store][qs-command-store]。

对新请求，QS 再读 `ResolveCurrent(assessment_id)`，检查报告的机构、Testee、测评关联，并要求请求的报告 99 仍是当前报告。随后构造 Start：

| MQ Start 字段 | 本例来源 |
| --- | --- |
| `request_id` / envelope `message_id` / `aggregate_key` | 原请求 UUID；三个位置保持一致 |
| `actor.org_id`、`actor.subject_id` | QS 推导的机构和已认证用户 |
| `testee_id`、`assessment_ids` | `"7"`、`["42"]`，当前参与者入口只提交一个测评 |
| `goal` | QS 固定文本 `解读当前标准报告` |
| `evidence[0].report_id` | `"99"` |
| `evidence[0].source_version` | `ContentSchemaVersion + ":" + OutcomeID`，本例 `standard-v1:101` |
| `evidence[0].facts` | 唯一 `ref="standard_report"`，`value` 为 QS 构造的完整报告快照 JSON |

客户端没有输入 Profile、Prompt、Route、publication、模型或报告正文的选项。AI 按冻结事实的场景选择 publication，并在自身事务中固定生成配置。QS 不保存或判断 AI 的 `active_run_id`。MBTI 的事实版本与输出材料另见 [MBTI 报告事实与版本契约](../02-业务模块/interpretation/02-MBTI报告事实与版本契约.md)。

来源读取和提交之间若当前报告由 99 切到 100，新 UUID 携带旧报告 99 会得到冲突，调用方应重新读来源并让用户确认新的工作。已经保存的原 UUID 则先按原请求对账：同一 Actor/Testee/测评/报告返回原操作，不重新取当前报告；换报告、测评或主体复用 UUID 均冲突。这个原请求重放发生在当前访问授权之后，撤销 ProfileLink 不能靠旧 UUID 绕过。原已保存请求也可以在停止新接单时读取/重放。[Participant.Request][qs-participant] 明确了这些检查次序。

## 3. 分别追踪命令决定和成果投影

客户端优先使用 202 给出的 `status_url`。一次尚未得到 AI 回执的读回可以是：

```json
{"code":0,"message":"success","data":{"operation_id":"00000000-0000-4000-8000-000000000001","command_id":"00000000-0000-4000-8000-000000000001","status":"submitted","transport_status":"staged","resource_id":"00000000-0000-4000-8000-000000000001"}}
```

原操作查询按机构、原主体和 `request_id` aggregate 过滤，仅允许参与者的 Start/Change 命令。即便同一用户知道另一请求的 command UUID，也不能拿当前请求查询它；管理员 Retry 的原操作不从这个参与者入口读取。[QS Operation][qs-operation] 保存和返回首接单决定，`transport_status` 独立呈现消息阶段。

| 读到的事实 | 调用方应如何理解 |
| --- | --- |
| `status=submitted`，尚无 `decision` | QS 已保存；AI 首决定尚未抵达 QS |
| `decision/status=accepted` | AI 接受原命令；继续读结果，不显示“解读完成” |
| `rejected` + `code` | 原命令确定性拒绝；保留拒绝及原 UUID，不自动换 UUID |
| `held` 或传输 `held` | 技术挂起，需要运维对账；不能推断供应商从未执行 |
| 结果入口 `status=accepted, version=0` | 原请求存在，但 QS 尚无状态投影；这里的 accepted 不是接单回执 |
| `queued`、`running`、`blocked`、`awaiting_answer` | 工作流状态；可能跳过未送达的中间版本 |
| `completed` | QS 已有经过校验的 Artifact 投影，可读成果 |
| `cancelled` | 已持久取消；不展示为成功成果 |

Start 的 `configuration_unavailable`、`admission_configuration_invalid`、`admission_input_invalid`、`participant_daily_capacity_exceeded` 会留下可重放的 blocked Session，并在 MQ 原决定中表示为 rejected。后来发布新配置不会把这个原请求重放成成功；无冻结配置的拒绝也不能用 ParticipantRetry 补绑定。

结果轮询使用原 `request_id`：

```http
GET /api/v1/assessments/42/ai-workflows/00000000-0000-4000-8000-000000000001?testee_id=7
Authorization: Bearer <登录令牌>
```

完成数据包含 `request_id/status/version/content/artifact_id/report_id/source_version`；Artifact v2 另含 `reference_material` 和 `reference_material_fingerprint`。`content`、`reference_material` 是解析后的 JSON 对象，不是供客户端执行的 HTML。展示须使用随成果保存的报告 99 与版本 `standard-v1:101`，不得把后来当前报告 100 的事实或最新材料拼进旧成果。具体内容 Schema 见 [MBTI 三主题与参考材料契约](../02-业务模块/interpretation/03-MBTI三主题与参考材料契约.md)。

当前公开结果 DTO 不返回内部 Session/Run/调用票据，也不返回 `failure_code` 或问题详情。客户端不能根据 `blocked` 自行判断是否允许新供应商调用；诊断和显式 Retry 由管理入口按原冻结配置、版本及当前权限处理，见 [治理接口与可信委托](03-治理接口与可信委托.md)。Change 在 MQ/proto 中保留 answer/cancel 契约，此处四个参与者 HTTP 路由没有对应提交入口。

## 4. QS Stored 是原事件业务入库证明

AI worker 在模型工作前、接受成果前各调用一次 QS `AIWorkflowAccessService.Authorize`，重新检查当前关系。事实与配置冻结，访问关系仍可能撤销；QS/IAM 临时不可用也不能按授权成功处理。[worker](../../src/qs_ai/application/execution/worker.py) 与 [QSAccessSource](../../src/qs_ai/infrastructure/qs_server/access.py) 实现了两次回查。

QS 接收状态时核对原请求 Actor、Testee、Session 绑定；完成事件还须通过 Artifact 校验，且 `assessment_id/report_id/source_version` 与原请求事实一致。它验证内容指纹、输出 Schema 和 v2 材料关联，不能改写 AI 生成内容。[投影存储][qs-projection] 与 [Artifact 校验][qs-artifact] 是成果读取前的接收边界。

同一事务保存 Inbox、业务投影和最终 ACK Outbox，成功后才能发送 `STORED`。ACK 绑定原 `event_id`、事件种类、aggregate 和原正文 SHA-256；AI 按这些值确认原结果 delivered。ACK 丢失时重投原事件，QS 重发原 ACK，不再次推进业务状态。较旧合法版本可以被保存/确认，但不覆盖较新投影；终态之后更高版本会被拒绝。

因此 Broker PUB 成功、consumer FIN、命令 accepted、QS Stored 各有不同含义。Stored 可以对应迟到的中间状态，也不表示页面已经读取或用户已接受内容。消息结构以 [messaging.proto](../../integrations/workflow/proto/messaging.proto) 为准；事务与失败窗口不在客户端侧复制实现。

## 5. 超时、拒绝与重放处置

| 现象 | 正确处置 |
| --- | --- |
| POST 超时或 503，提交结果不明 | 保留原 UUID/报告 ID，先查原操作；没有可读记录时仍可按原正文重发，不能先换 UUID |
| 400 | 修正 UUID/正整数/必填字段；未确定原提交结果前不另发新工作 |
| 401 / 403 | 重新登录或处理当前 ProfileLink/归属；不以服务证书或已知 UUID 代替用户授权 |
| 404 | 在当前访问范围内未找到原请求/操作；不能据此断言供应商未执行 |
| 409 | 检查来源是否变化、UUID 是否被另一正文占用，按读回事实处理 |
| 429，message 为 `AI runtime command admission is closed for maintenance; operation was not submitted` | 新接单已由运维关闭；读回原操作，等待明确开放；该错误没有每日额度重置承诺 |
| 其他容量 429 | handler 给出距离下一个 UTC 日界线的 `Retry-After`；仍需原操作对账，不能自动新建调用 |
| 原调用 `provider_result_unknown` | 管理者核实原执行并按显式风险确认处置；消息重投不授权重调供应商 |

参与者 HTTP 错误映射与两种 429 的区别见 [handler][qs-http]。标准报告读取、AI 预检、请求提交和结果展示应分别提供界面状态，避免把标准报告 ready 或消息提交显示为 AI 完成。
