# QS 接入与消息契约

现行说明；源码基线 `c977cb9`。命令和结果由 MQ 传递，gRPC 保留治理、授权与正文读取。正文格式见 [消息 proto](../../integrations/workflow/proto/messaging.proto) 与 [工作流 proto](../../integrations/workflow/proto/workflow.proto)。

## 发起、接单与授权

QS 先校验用户与 Testee/报告的业务关系，从自身持久报告构造事实快照，再保存稳定命令和发起证据。组织、主体和事实不得取自未经验证的客户端声明。AI 的服务身份验证不替代 QS 的业务权限。

Start 的 `request_id`、Change/Retry 的 `command_id` 保持稳定；同一身份不同正文冲突。MQ 的命令 ID、正文摘要及原回执一起核对，网络结果未知时查询原操作，不能生成新身份猜测失败。

[CommandReceiver](../../src/qs_ai/infrastructure/workflow_transport/mq_receiver.py) 建立宿主根事务并锁定 Inbox；[WorkflowCommandAdmission](../../src/qs_ai/infrastructure/workflow_transport/command_admission.py) 借用原 AsyncSession 与事务调用既有业务方法。借用事务不会另行提交、回滚根事务或关闭宿主会话。确定性拒绝用局部 SAVEPOINT 撤销本命令写入；技术故障整体回滚。业务状态、事件、Inbox 和首接单回执提交后，才允许 Broker FIN。

重复消息复用原 Inbox/回执，不再次执行业务 CAS。已持久接单但准入 blocked 是合法业务状态，不能当作模型执行成功。执行前、接受成果前和相应管理恢复操作仍使用 [QS 当前授权适配器](../../src/qs_ai/infrastructure/qs_server/access.py) 复核；保存快照不冻结权限。

## 传输与业务确认

| 阶段 | 证明什么 | 后续仍需核实 |
| --- | --- | --- |
| 业务事务提交 Outbox | 命令/事件已持久保存 | 尚未证明 Broker 收到 |
| Broker PUB 确认、消费 FIN | 传输步骤完成 | 尚未证明模型完成或 QS 业务入库 |
| 命令回执 ACCEPTED/REJECTED/HELD | 原命令接单决定 | ACCEPTED 不代表解读完成 |
| QS 保存 Inbox、业务投影和最终 ACK | 原事件获得业务持久接收证明 | 客户端读取/展示仍需验收 |
| AI 验证 ACK 并确认事件 | 原事件身份、种类和正文摘要对应最终确认 | 不批准质量、不转换历史成果 |

解读事件继续保留原 `result_outbox` 的首次 `event_id`、正文、请求关联和创建时间；`mq_owned` 只表示投递归属。AI 在原结果行与新消息 Outbox 同一事务中确认 delivered；错摘要、技术挂起、未移交或身份冲突不能确认。实现见 [MessagingStore](../../src/qs_ai/infrastructure/persistence/mysql/messaging.py)、[StateEventRecorder](../../src/qs_ai/infrastructure/workflow_transport/state_events.py)。

事件无需 Broker 强制顺序。消费者使用原 session/version 或 evaluation event_sequence 处理迟到状态；旧事件可确认但不能覆盖较新投影。首次 wire 与正文持久保存，重投使用原身份，不重新签封成另一事件。MQ 归属不能通过关开关或删除标记退回旧投递器。

## 固定路由、保护与正文引用

| 方向 | Topic | 消费 Channel |
| --- | --- | --- |
| QS → AI 命令 | `qs.ai.commands.v1` | `qs-ai.commands.v1` |
| AI → QS 回执与状态 | `qs.ai.events.v1` | `qs-server.ai-events.v1` |
| QS → AI 最终 ACK | `qs.ai.acks.v1` | `qs-ai.acks.v1` |

路由、生产者/目的地、稳定消息 ID 和正文摘要由 [消息封装](../../src/qs_ai/infrastructure/workflow_transport/messaging.py) 校验。JOSE 签名与加密使用明确的 key role、kid 和 EC P-256；密钥仅由受控文件挂载，日志不输出正文或密钥。

大正文通过精确 `MessagePayloadReference` 读取，绑定生产者、目的地、message_id、机构、原长度与 SHA-256。Payload endpoint 使用 mTLS，读取后仍验证原始 Protobuf 字节；不能用 JSON 重序列化结果代替摘要，不能下载“最新正文”。

NSQD TCP→HTTP 地址映射、Topic/Channel 及 SDK 失败移交拓扑必须由环境事先配置。启动只做有界检查，不猜端口、不自动创建拓扑。技术故障使用外围有界失败预算及失败移交；具体上限和错误处理见 [MQ 装配](../../src/qs_ai/bootstrap/messaging.py)、[失败拓扑](../../src/qs_ai/infrastructure/workflow_transport/mq_failure.py)。
